# Сессия 1. Версионность продукта

## Задача

Не было способа понять, какая сборка запущена. После правок нельзя было
отличить старую сборку от новой: работающий процесс держит сборку в памяти,
а признака версии не было ни в одном месте интерфейса.

## Что было до правок

| Место | Как читалась версия | Проблема |
|---|---|---|
| `AppUpdatePackageService.cs:854` | `AssemblyInformationalVersion` | Своя логика |
| `BisPatchService.cs:1155` | `AssemblyName.Version` | Другая логика |
| `ConfigurationExchangeService.cs:296` | Жёстко `Version = "1.0"` | Не связано с программой |
| `BIS.ERP.csproj` | `<Version>1.0.0</Version>` | Никогда не менялось |
| `AboutSystemDialog.xaml:43` | `Text="Версия 1.0"` | Литерал в разметке |

Версия была объявлена в четырёх местах, три из которых никогда не менялись.

## Созданные файлы

### `version.json` — единственный источник версии

```json
{
  "Major": 1, "Minor": 1, "Patch": 166, "Build": 166,
  "Semantic": "1.1.166",
  "Informational": "1.1.166+2026-10-12T08:00:00Z#166",
  "LastBuildUtc": "2026-10-12T08:00:00Z"
}
```

Поля `Major` и `Minor` правятся вручную, `Patch` и `Build` растут автоматически.

### `Directory.Build.props` — механизм сборки

Три фазы:

```
WriteVersionBumpScript      готовит скрипт инкремента
        ↓
BumpProductVersionFiles     выполняет, получает версию
        ↓
ApplyProductVersion         пишет метаданные сборки
```

Особенности реализации:

| Решение | Причина |
|---|---|
`powershell.exe` вместо `pwsh` | `pwsh` не входит в PATH для MSBuild |
Разбор JSON регулярками | `ConvertFrom-Json -AsHashtable` нет в PowerShell 5.1 |
`WriteCodeFragment` | Не требует экранирования кавычек и точек с запятой |
Метаданные сборки вместо атрибутов версии | Атрибуты создаёт SDK, свойства из цели не успевают |
Исключение `_wpftmp` | WPF собирает проект дважды, версия росла на 2 |

### `Services/AppVersion.cs` — доступ из кода

| Свойство | Значение | Пример |
|---|---|---|
| `Semantic` | Версия без сборки | `1.1.166` |
| `DisplayShort` | Для шапок окон | `1.1.166 (сборка 166)` |
| `Display` | Для диалога «О системе» | `1.1.166 (сборка 166 от 12.10.2026 08:00)` |

# Сессия 2. Акты сверки по FRX

## Задача

Акт сверки по FRX-макету печатал одну организацию и одну строку вместо всех.

## Проблема процесса

Работа шла по скриншотам, и скриншот не различает «данные не дошли»
и «данные не отрисовались». Это привело к нескольким итерациям правок
не в том месте.

## Что было сделано для диагностики

### Найдено расположение данных

| Что | Значение |
|---|---|
Мастер-база | `bis_master` |
Информационная база | `bis_OsOO1_20260908_112439` |

**Данные отчётов лежат не в мастер-базе, а в базе информационной базы.**

### Создан инструмент `.tools/ReconProbe`

Консольное приложение, вызывающее **настоящий код** приложения:
`OrganizationBalanceService`, `ReconciliationActBuilder`, `PrintFormService`.

Позволяет проверять выборку и вывод без запуска окна.

### Создан журнал диагностики

При формировании акта пишется файл рядом с программой:

```
bin\Debug\net8.0-windows\reconciliation-trace.log
```

Содержит: версию сборки, режим, число организаций и движений, след построения,
таблицу акта по строкам, состав упакованного макета.

## Созданный файл `Services/ReconciliationActBuilder.cs` — 519 строк

Логика построения таблицы акта была **продублирована** в `AccountingReportsView`
и недоступна для проверки без запуска окна.

| Что перенесено | Назначение |
|---|---|
| `CreateTable` | Колонки отчёта и служебные колонки макета |
| `LoadMovementsAsync` | Загрузка движений за период |
| `BuildTable` | Построение таблицы со следом для диагностики |
| `AddRow`, `AddSection` | Строки и секции акта |
| `AccountInPair`, `SameAccount` | Сопоставление счетов |
| `MatchesMovementOrganization` | Сопоставление организации |
| `ShortenText`, `IsDocumentTitleText` | Сокращение текста, фильтр заголовка |

**Результат:** отчёт и инструмент используют один код, расхождение невозможно.

## Найденные дефекты

### Дефект 1. Одна организация вместо пяти

**Причина:** макет «Вариант 1» обращается к полям строки **без префикса**:

| Макет | Выражения строки |
|---|---|
| Акт сверки (77 540 б) | `ved.tex`, `ved.debet`, `ved.kredit` |
| Акт сверки вариант 1 (21 078 б) | `tex`, `debet`, `kredit` |

Код требовал префикс обязательно, поэтому поля не опознавались и уходили
в обрамление вместо строк.

**Исправление** в `Services/PrintFormService.cs`, метод `IsReconciliationRowElement`:

```csharp
// Составные выражения (korsch+' - '+kor_sch) не являются полем строки
if (expression.Contains('+') || expression.Contains('('))
    return false;

// Префикс снимается, если он есть, но не является обязательным
var name = Regex.Replace(expression, @"^(?:ved\d*|db_crs?|dbcrs?)[._]", string.Empty);
```

То же в `LooksLikeReconciliationMovementElement` — группа префикса стала
необязательной: `(?:\b(?:ved\d*|db_crs?|dbcrs?)[._])?`.

### Дефект 2. Сегодняшняя дата вместо даты проводки

**Причина:** в FoxPro `date()` — служебная функция. В словаре переменных она
хранится под ключом `date()`, словарь не учитывает регистр, а поиск снимает
скобки — поэтому имя поля `date` попадало на функцию:

```
ExtraFields['date'] = '30.09.2026'   ← правильная дата проводки
Разрешённое 'date'  = '09.10.2026'   ← сегодняшняя дата
```

Второй источник — цикл публикации доп. полей: `NormalizeFieldName("date")`
возвращал `"date"` и перезаписывал значение.

**Исправление** в `Services/PrintFormService.cs`:

- добавлен `ResolveDateVariable` — дата строки имеет приоритет;
- добавлен `IsDateVariableKey` — доп. поля не перезаписывают `date`;
- после цикла значение `date` восстанавливается.

### Дефект 3. Пустые колонки «Дата» и «АРМ»

**Причина:** в привязках элементов макета для этих полей заданы имена колонок базы:

```
Порядок 42  поле: posting_date   выражение: date
Порядок 45  поле: module_code    выражение: prs
```

Код идёт по `MappedFieldName` раньше выражения, а ключей `posting_date`
и `module_code` в данных нет — есть «Дата» и «Модуль».

**Исправление** в `Services/PrintFormService.cs`, метод
`BuildReportPreviewDataForRow` — публикация значений под именами макета:

```csharp
Add("posting_date", rowDate);
Add("module_code", ReadPreviewText(row, "Модуль", "module", "prs", "kod_arm"));
```

### Дефект 4. Содержимое ужималось в одну страницу

**Симптом:** всё на одной странице, строки нечитаемы.

**Подсчёт:** высота содержимого 59 771 при высоте листа 116 471.
`FitArea` растягивал в 1,95 раза — **62 строки на альбомный A4**,
то есть 1,5 мм на строку.

**Исправление** в `Services/PrintFormService.cs`, метод `SplitTemplateIntoPages`:

Отказ от расчёта по высотам в единицах макета. Теперь **строки считаются напрямую**:

```csharp
// Число строк данных на страницу
const int rowsPerPage = 15;
```

| Шаг | Что делает |
|---|---|
1 | Группирует элементы по горизонталям — одна горизонталь = одна строка |
2 | Находит первую строку данных по признаку `IsLikelyDataValue` |
3 | Набирает по 15 строк на страницу |
4 | Высота листа вычисляется из границ этих строк |
5 | Шапка повторяется на каждой странице |

Добавлены методы: `ElementRow` (record), `IsDataRow`, `BuildPage`,
`FindRepeatedHeaderElements`, `SplitByHeight` (для обычных макетов).

# Сессия 3. PDF для ClosedXML и предпросмотры

## Задача

Переход на ClosedXML как замену FRX. В рабочем режиме отчёт формировался
правильно, а в конструкторе предпросмотр показывал другое. Требовался PDF.

## Выясненные обстоятельства

| Факт | Значение |
|---|---|
LibreOffice на машине | **Нет** |
QuestPDF в проекте | **Есть** (2024.7.3) |
PDF-рендерер ClosedXML | **Отсутствовал** — только `RenderToBytes` в Excel |

## Дефект 1. Предпросмотр в конструкторе показывал сырые данные

**Причина:** рабочий режим и конструктор использовали **разные наборы данных**
при одном рендерере.

| Режим | Источник данных |
|---|---|
| Рабочий | `_currentData` — построенный акт: 5 организаций, САЛЬДО, итоги, 73 строки |
| Конструктор | `GetReportDataAsync` — сырые поля справочника: `posting_date`, `amount_kgs` |

**Исправление** в `Views/ReportDesignerWindow.xaml.cs` — добавлен метод
`BuildClosedXmlPreviewDataAsync`, который для акта строит тот же набор:

```csharp
if (!isReconciliationAct)
    return await _reportService.GetReportDataAsync(report, parameters);

var calculation = await new OrganizationBalanceService(context).CalculateAsync(start, end);
var act = builder.BuildTable(pairs, totals, movements, start, end, false, "Все организации");
```

Плюс `ResolvePreviewPeriod` — период из параметров отчёта.

## Дефект 2. Рендерер молча терял колонки

**Причина** в `Services/ClosedXmlReportRenderer.cs`:

```csharp
var visible = columns.Where(c => dataTable.Columns.Contains(c.Field))
```

Колонки, которых нет в данных, **исчезали без предупреждения**.
Совпадали только `debit_account` и `credit_account` — отсюда шапка из трёх колонок.

**Исправление:**

- добавлен `ResolveColumnName` — поиск по нормализованному имени,
  чтобы «Сумма Дт» и `сумма_дт` считались одним полем;
- добавлен `NormalizeFieldKey` — убирает регистр, пробелы, точки,
  подчёркивания и префикс набора данных;
- `PrepareData` публикует колонки под именами `FieldName`, `DisplayName`
  и их нормализованными видами.

## Дефект 3. Предпросмотр в конфигураторе — «нет печатной формы»

**Причина** в `Views/ConfiguratorWindow.xaml.cs`: `PreviewReportDirectAsync`
**всегда** шёл по FRX-пути через `ExportTemplatePreview`.

**Исправление** — определение формата и выбор вывода:

```csharp
if (IsClosedXmlReport(fullReport))
{
    await PreviewClosedXmlReportAsync(fullReport);
    return;
}

// FRX и нативный — PDF, как было
```

Добавлены: `IsClosedXmlReport`, `PreviewClosedXmlReportAsync`,
`BuildClosedXmlPreviewDataAsync`.

## Полезно знать

1. **`version.json` нужно держать в системе контроля версий** — это источник версии.
2. **Сборка с ошибкой тоже увеличивает версию** — инкремент идёт до компиляции.
3. **Приложение держит сборку в памяти** — при запущенном процессе сборка
   в `bin\Debug` не обновляется. Версия в шапке это показывает.
4. **FRX и ClosedXML работают параллельно** — два генератора для сравнения.
5. **PDF для ClosedXML не требует LibreOffice** — только QuestPDF.
6. **Исходники не править скриптами PowerShell 5.1** — портится кириллица.
