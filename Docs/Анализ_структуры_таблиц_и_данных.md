# Анализ структуры таблиц и данных BIS.ERP

> Дата: 16.10.2026. Режим: только анализ, без изменений.
> Источники: `Data/AppDbContext.cs`, `Models/*.cs`, `Docs/PROJECT_SCHEMA.md`, сиды и `EnsureSchema`.

## 1. Четыре слоя хранения в одной БД

| Слой | Таблицы | Создание | Состояние |
|---|---|---|---|
| 1. Ядро EF | `Users`, `MetadataObjects`, `MetadataFields`, `Reports`, `ReportFields`, `Documents`, `Postings`, `Organizations`, `AccountingPeriods` и др. | Migrations + `OnModelCreating` | Частично корректно |
| 2. Метаданные | `MetadataObjects.TableName` -> таблица, `MetadataFields.DbColumnName` -> колонка | `CreateDynamicTableAsync` | Работоспособно, хрупко |
| 3. Динамические | `catalog_*`, `doc_*`, `doc_postings`, `doc_numbering` | `EnsureSchemaAsync`, сиды, `.bispatch` | Главный риск |
| 4. DBF-наследие | `DynamicDocuments`, `DynamicDocumentRows.Data jsonb` | EF + jsonb | Изолировано хорошо |

Про `doc_incoming`: такого имени в проекте нет. Входящие документы распределены по `doc_purchase_invoice` (полученный СФ), `doc_cash_orders Receipt` (ПКО), `doc_advance_payment`.

## 2. Что правильно — сохранить

1. Единый журнал `doc_postings` — все документы пишут туда.
2. Шапка + строки: `doc_sales_invoice_lines`, `doc_purchase_invoice_lines`, `doc_advance_payment_lines (advance_id CASCADE)` — нормализация 1:N верная.
3. Конструктор отчетов: `Reports` -> Fields/Filters/Groups/Parameters, все `CASCADE` + уникальные индексы. Лучший кусок схемы.
4. Периоды: `AccountingPeriods(StartDate,EndDate UNIQUE)`, снимки `(PeriodId,AccountCode UNIQUE)`, проверка `Дт=Кт`.
5. Деньги `numeric`, а не `float`. `jsonb` только для DBF.
6. Уникальности `Users.Login`, `Materials.Code`, `ReportDataSets.Code`.


## 3. Проблемы P0 — критично

P0-1. Три системы создания схемы: EF Migrations, `EnsureSchemaAsync`, `CreateDynamicTableAsync`, плюс `RuntimeSchemaFixService`. Итог — дрейф между базами.

P0-2. Условные FK. `advance_id -> doc_advance_payment` вешается только если шапка существует. Без FK — сироты в `_lines`, `42P01`.

P0-3. Связи без FK: `Posting.DocumentId Guid` без FK, `ReferenceFields JSON`, JOIN через `::text`. Удаление справочника не блокируется.

P0-4. DDL без экранирования: `RenameDocumentTableAsync` без `quote_ident`.

## 4. Проблемы P1 — дубли моделей

P1-1. Три документа: `Document/Row/Movement`, `DynamicDocument/Row`, боевые `doc_*`. Оставить боевыми `doc_*` + `doc_postings`.

P1-2. Два справочника: пустой `Organizations` и боевой `catalog_organizations`. `Posting.OrganizationId` ведет в пустую таблицу.

P1-3. Две точности денег: `numeric(18,2)` и `numeric(15,2)`. Унифицировать на `18,2`.

P1-4. `User.Id int` против `Guid` везде. `InfoBase.Password` открытым текстом.
