# Учёт материалов в BIS ERP

## Сравнение с mat_vpf9_ECF и план развития текущей реализации

Дата анализа: 2 ноября 2026 года.

Документ предназначен для владельца продукта, разработчика и специалиста по учёту. Он объясняет, как устроены расчёты в исходной программе Visual FoxPro, что уже реализовано в BIS.ERP, каких механизмов не хватает и в какой последовательности их добавлять. План сохраняет существующую модель BIS.ERP: три документа ТМЗ, виды операций, метаданные, PostgreSQL, единый журнал проводок и действующий механизм отчётности.

**Основной вывод:** в BIS.ERP создана основа ввода документов ТМЗ, но её пока нельзя считать завершённым количественно-суммовым учётом материалов. Главный недостающий слой — движения и остатки материалов с расчётом себестоимости. Следующие по важности задачи — проведение по смыслу операции, целостность сохранения, отмена проведения, дополнительные расходы и отчёты на основе фактических движений.

Создавать заново существующие окна и копировать все формы FoxPro не требуется. Необходимо развить уже работающие документы и вынести расчёты из окон в проверяемые сервисы.

## 1 Границы анализа и источники

### 1.1 Сравниваемые каталоги

Текущий проект:

`D:\C#\BIS.ERP\BIS.ERP`

Исходный проект:

`D:\C#\Комтек софт-20260323T113058Z-3-001\Комтек софт\программы\МАТЕРИАЛЫ\mat_vpf9_ECF\mat_vpf9_ECF`

В фактическом пути папка называется `МАТЕРИАЛЫ`, без пробела после первой буквы.

### 1.2 Что проверено

В BIS.ERP изучены модель трёх документов ТМЗ, описание схемы, чтение и сохранение строк, пересчёт, диалог, обработчик проведения, общий механизм отмены проведения, участки обновления динамических записей, подготовка ведомости материалов, журнал закупок и продаж и точки интеграции с закрытием периода.

В FoxPro изучены программы `cena_s.prg`, `CENA_RAS.PRG`, `RAS1.PRG` — `RAS6.PRG`, программы формирования проводок, контроля сумм, индексации и восстановления остатков. Из SCX/SCT прочитан исходный текст методов ключевых форм поступления, реализации и перемещения. Методы извлекались по структуре DBF и ссылкам на memo-блоки; бинарные фрагменты компиляции не использовались как доказательство формул.

В исходном дереве обнаружены 158 файлов PRG, 185 SCX и 277 FRX. Это число файлов, а не число самостоятельных функций: есть варианты, вспомогательные библиотеки и старые формы.

### 1.3 Ограничения достоверности

Это статический анализ исходников. Приложения не запускались, базы не изменялись, миграции и пересчёты не выполнялись. Действующая конфигурация конкретной инфобазы BIS.ERP может содержать пользовательские правила и наборы данных, которые не видны из исходного дерева.

В указанном каталоге FoxPro нет рабочих таблиц `matdoc`, `matsw`, `matset`, `ost_mat`, `ost_mol` с хозяйственными данными. Обнаруженные DBF относятся к служебным файлам и библиотеке. Поэтому подтверждены алгоритмы исходников, но не числовая сходимость на реальной базе предприятия. Подключать внешнюю рабочую базу для этого исследования не требовалось.

Статусы ниже имеют точный смысл:

| Статус | Значение |
|---|---|
| Есть | В проверенном коде есть соответствующий механизм |
| Частично | Есть структура или упрощённая обработка, но не полный цикл |
| Не найдено | В проверенном контуре исходников нет завершённого механизма; это не утверждение об отсутствии пользовательской настройки в любой инфобазе |
| Предложение | Целевая реализация, которой ещё нет в проверенном коде |

Основной предмет документа — материалы и ТМЗ. В старом дереве также есть код ОС, МБП, спецодежды и ГСМ. Для них ниже определены границы и отдельные этапы; полный аудит всех расчётов амортизации ОС этим документом не подменяется.

## 2 Что уже реализовано в BIS ERP

### 2.1 Архитектурная основа

Проект — WPF на .NET 8 с PostgreSQL, EF Core и Npgsql. Значительная часть объектов описана метаданными. Состав документов ТМЗ централизован в `Services/InventoryDocumentModel.cs`, создание схемы — в `Services/InventoryDocumentSchemaService.cs`.

Уже предусмотрены три документа:

| Документ | Таблица шапки | Таблица строк |
|---|---|---|
| Поступление ТМЗ | `doc_inventory_incoming` | `doc_inventory_incoming_lines` |
| Выбытие ТМЗ | `doc_inventory_outgoing` | `doc_inventory_outgoing_lines` |
| Внутреннее перемещение ТМЗ | `doc_inventory_movement` | `doc_inventory_movement_lines` |

Шапки и строки связаны через `incoming_id`, `outgoing_id`, `movement_id`. Схема создаёт первичные ключи, связь строк с шапкой с `ON DELETE CASCADE`, индексы по родителю и номеру строки. Наличие этих ограничений в исходнике не заменяет проверки фактической схемы используемой инфобазы.

### 2.2 Восемь видов операций

| Код | Смысл | Документ |
|---|---|---|
| `INCOMING_PURCHASE` | Приобретение | Поступление |
| `INCOMING_PRODUCTION` | Приход из производства | Поступление |
| `INCOMING_ACT` | Приход по акту | Поступление |
| `OUTGOING_SALE` | Реализация | Выбытие |
| `OUTGOING_PRODUCTION` | Расход в производство | Выбытие |
| `OUTGOING_WRITEOFF` | Списание по акту | Выбытие |
| `MOVEMENT_ASSIGNMENT` | Передача в подотчёт | Перемещение |
| `MOVEMENT_AUTO` | Автоматическая передача | Перемещение |

Вид операции выбирается из `catalog_inventory_document_entries`; в шапку записывается `operation_kind`. Эту модель нужно сохранить. Разные виды операций должны управлять расчётом, проверками, движениями и проводками, а не только подписью в форме.

### 2.3 Реквизиты и ввод

В модели шапки описаны 32 поля: номер, дата, вид операции, пачка, бланк, ЭСФ, счёт, организация, сотрудник, тип поставки, налоги, валюта, курс, итоги, транспорт, таможенные и прочие расходы, получатель перемещения и служебные счета.

Строка содержит материал, снимок названия и единицы, счёт, участок, МОЛ, количество, цену, налоговые ставки и суммы, итог и сумму в валюте. Количество хранится с тремя десятичными знаками, цена — с шестью, денежные суммы — с двумя.

Есть специализированный `InventoryDocumentDialog`, выбор материалов и счетов, пересчёт при вводе количества, цены и ставок, загрузка курса и итогов. При сохранении проверяются наличие строк, материала, положительного количества и выбранного вида операции.

### 2.4 Что не нужно делать повторно

Не требуется заново создавать три таблицы документов, справочник видов операций, базовый выбор материала, стандартные поля НДС, валюты и ЭСФ. Не требуется вводить отдельную таблицу для каждой формы FoxPro.

Существующие документы `Docs/ТМЗ_модель_документов.md` и `Docs/InventoryDocumentHowTo.md` полезны как описание основы, но отдельные списки «не сделано» в них уже устарели: окно и базовое проведение в текущем коде присутствуют. При планировании приоритет имеет фактическая реализация.

## 3 Как организован исходный проект FoxPro

### 3.1 Основные сущности

| Сущность FoxPro | Назначение | Соответствие в BIS.ERP |
|---|---|---|
| `MATDOC` | Шапки документов | Три таблицы шапок ТМЗ |
| `MATSW` | Материальные строки | Три таблицы строк ТМЗ |
| `MATSET` | Проводки | Общая таблица `doc_postings` |
| `TDOC6` | Виды документов и программа проводок | Виды операций и обработчики проведения |
| `CENA_S` | Текущее количество, стоимость, средняя цена по материалу, счёту и заказу | Нужен регистр стоимостной оценки |
| `NAL_S` | Количество и стоимость по материалу, участку, МОЛ, счёту и заказу | Нужен регистр аналитических остатков |
| `OST_MAT` | Остатки на дату в сводном разрезе | Нужны снимки периода либо вычисляемый остаток |
| `OST_MOL` | Остатки на дату по участкам и МОЛ | Нужны аналитические снимки периода |
| `KRT`, `OPER_KRT` | Карточный учёт выдачи и возврата | Отдельное расширение после базового учёта |
| `TITLINV`, `INVENT` | Инвентаризация | В BIS.ERP нужны факт, учётное количество и результаты |

Основания: `e1_oper.prg`, `e1_ost.prg`, `cena_s.prg`, `rasch_ost.prg`. Названия назначений восстановлены по ключам и действиям кода, а не по наличию реальных записей таблиц.

### 3.2 Что взять из старой программы

Сохранить нужно предметный смысл: документ состоит из строк, каждая операция изменяет определённые аналитики, стоимость расхода отличается от продажной суммы, дополнительные расходы могут увеличивать стоимость запасов, итог по МОЛ должен сходиться со сводным остатком.

Не переносить напрямую DBF-индексы из строковых склеек, глобальные переменные, `SCATTER/GATHER`, временные файловые таблицы и динамический запуск PRG по имени из данных. В BIS.ERP те же задачи решаются UUID, внешними ключами, транзакциями, сервисами и проверяемыми правилами.

## 5 Формулы BIS ERP

### 5.1 Расчёт строки

Фактический алгоритм `InventoryLineRow.Recalculate()`:

```text
B = Round(Q × P, 2, AwayFromZero)
V = Round(B × rV / 100, 2, AwayFromZero)
S = Round(B × rS / 100, 2, AwayFromZero)
T = Round(B + V + S, 2, AwayFromZero)
```

Где Q — количество, P — цена без налогов, B — база, V — НДС, S — второй налог, T — итог. Оба налога начисляются независимо на одну базу. Итоги документа суммируются из пересчитанных строк.

Пример с условными ставками, используемыми только для демонстрации алгоритма:

| Показатель | Значение |
|---|---:|
| Количество | 10 |
| Цена без налогов | 100,00 |
| База | 1 000,00 |
| Условная ставка НДС | 12% |
| НДС | 120,00 |
| Условная ставка второго налога | 2% |
| Второй налог | 20,00 |
| Итог | 1 140,00 |

Эти ставки не являются утверждением о действующем законодательстве. Документ анализирует программную арифметику; применимость налоговой политики должен подтвердить специалист по учёту.

### 5.2 Ограничения текущего пересчёта

Цена расхода сейчас не выводится из остатка и его стоимости. Поле `Price` используется общей формулой и для поступления, и для выбытия, и для перемещения. Поэтому введённая продажная цена может стать основанием единственной проводки расходного документа, хотя себестоимость и выручка имеют разный смысл.

`Recalculate()` всегда пересоздаёт базу и налоги из количества, цены и ставок. Ручная правка вычисляемой суммы, если она доступна пользователю, не является устойчивым способом корректировки: следующий пересчёт её заменит.

В формуле строки нет транспорта, таможни и прочих расходов. Их поля шапки сами по себе не изменяют стоимость материала.

### 5.3 Валюта

В диалоге отображение валютного итога рассчитывается как `Round(Total / Rate, 2)` при положительном курсе; при неположительном курсе показывается `0,00`.

При сохранении `BuildItemData()` использует курс только при видимом валютном блоке; иначе сохраняет валютный итог равным общему итогу. При проведении берётся курс из шапки, и при его отсутствии сумма в валюте становится нулём. Таким образом, отображение, сохранение и проведение имеют разные правила для отсутствующего курса и скрытого блока.

`InventoryLineRow.AmountCurrency` сохраняется в таблицу строк, но сам `Recalculate()` её не вычисляет; проводка считает валютную сумму заново из общей суммы строки. Необходимо определить один авторитетный источник валютной суммы.

### 5.4 Предлагаемый контракт расчёта

Расчёт должен принимать явные параметры: режим ввода цены, валюту, курс на дату, налоговую политику, способ распределения расходов и вид операции. Возвращать нужно отдельно цену и базу документа, налоги, сумму расчётов с контрагентом, стоимость запасов и округления.

Формулы должны выполняться в одном сервисе как при предварительном отображении, так и при сохранении и проведении. Видимость контрола не должна определять экономический результат.

## 6 Формулы FoxPro и различия

### 6.1 Прямой расчёт

Обозначения: B — стоимость без налогов, V — НДС, S — второй налог, v и s — ставки в долях единицы. Денежные результаты в программах округляются до двух знаков, цены в ряде преобразований — до четырёх.

| Файл | База НДС | База второго налога | Итог |
|---|---|---|---|
| `RAS1.PRG` | B | B + V | B + V + S |
| `RAS2.PRG` | B | B | B + V + S |
| `RAS3.PRG` | B + S | B | B + V + S |

`RAS2` по структуре налоговых баз ближе всего к текущему BIS.ERP. Но равенство баз не означает идентичности поведения: FoxPro часто заполняет сумму только если она равна нулю, а BIS.ERP безусловно пересчитывает поля. Различаются обработка ручных значений, порядок преобразования валюты и точность цены.

На базе 1 000,00 и условных ставках 12% и 2%:

| Алгоритм | НДС | Второй налог | Итог |
|---|---:|---:|---:|
| RAS1 | 120,00 | 22,40 | 1 142,40 |
| RAS2 и текущая схема BIS.ERP | 120,00 | 20,00 | 1 140,00 |
| RAS3 | 122,40 | 20,00 | 1 142,40 |

У RAS1 и RAS3 одинаковый общий итог в этом примере, но разные суммы отдельных налогов. Сверка только по итогу документа такую ошибку не выявит.

### 6.2 Обратный расчёт от суммы с налогами

| Файл | Расчёт базы от итога T | Последующие действия |
|---|---|---|
| `RAS4.PRG` | `Round(T / ((1+s) × (1+v)), 2)` | НДС от B, второй налог от B + V; разница округления относится во второй налог |
| `ras5.prg` | `Round(T / (1+s+v), 2)` | НДС от B, второй налог как остаток `T − B − V` |
| `RAS6.PRG` | Та же составная формула базы, что у RAS4 | Задумана обратная схема с НДС на B + S, но валютная ветвь содержит подозрительные присваивания |

В методах формы `fma1_21` выбор идёт по `v_formula`: 11 → RAS1, 12 → RAS2, 13 → RAS3, 21 → RAS4, 22 → RAS5, 23 → RAS6. Это подтверждает наличие механизма выбора, но не доказывает, что все шесть вариантов использовались в конкретной рабочей базе.

Для режима с независимыми налогами: итог 1 140,00 при тех же условных ставках даёт базу 1 000,00, НДС 120,00 и второй налог 20,00. Такой обратный ввод в текущем `InventoryLineRow.Recalculate()` отсутствует.

### 6.3 Что нельзя переносить без исправления

В RAS1 есть вычисление `sumdox_v` из `sum / kurs_v`, тогда как RAS2 и RAS3 используют `sumdox / kurs_v`. По окружающему коду `sum` и `sumdox` могут означать разные суммы; это требует проверки контрольным сценарием.

В RAS4–RAS6 отдельные ветви восстановления цены от итоговой суммы используют `sumdox`, хотя проверяется `sumsum`. Это потенциальная зависимость от ранее заполненных переменных, а не универсальная формула.

В RAS6 проверка `SUMNDS_v` управляет присваиванием `sumnal_v`; далее выражение для НДС присваивается в `sumNAL_v`, а не в `sumnds_v`. По тексту исходника это явная несогласованность имён. Повторять её в C# нельзя.

Предлагается реализовать математические режимы с явными названиями, а не переносить шесть PRG буквально. Сначала закрепить текущий режим «оба налога от базы», затем добавить обратный ввод и только нужные исторические варианты. Для каждого режима хранить версию и снимок параметров в документе.

## 7 Дополнительные расходы

### 7.1 Что делает FoxPro

В методах `fma1_11.scx/sct` транспорт, таможня и прочие расходы распределяются на строки пропорционально сумме. Отбираются строки, у которых счёт имеет признак материального `buxsch.pr_sch=1`.

Для каждого вида расхода:

```text
Base = сумма SUM по подходящим строкам
Expense_i = Round(TotalExpense × SUM_i / Base, 2)
Difference = TotalExpense − сумма Expense_i
```

В коде есть исправление погрешности. Комментарий говорит о строке с максимальной суммой, однако рядом выполняется `LOCATE FOR buxsch.pr_sch=1`. Поэтому безопасно утверждать наличие компенсации разницы, но не универсальное правило выбора максимальной строки без анализа действующего порядка записей.

При нулевой общей сумме есть ветвь обнуления распределений. При ненулевой сумме шапки, но отсутствии подходящей базы требуется отдельная защита: наличие старого кода не гарантирует обработку всех нулевых знаменателей.

### 7.2 Как расходы входят в оценку

В `cena_s.prg` для обычного документа стоимость движения включает:

```text
SUM + SUM_TR + SUM_TAM + SUM_ITD
+ для приходной группы SUMNAL + NAL_TR + NAL_TAM + NAL_ITD
```

НДС в это выражение не добавляется. Это конкретное поведение исторического алгоритма, а не универсальное правило для любой организации и налоговой операции. В других методах форм встречаются отдельные корректировки временных стоимостных таблиц; потому полную оценку нужно проверять по целому сценарию.

В `f_prov11.prg` выделены отдельные проводки транспорта, таможни, прочих расходов, налога с продаж, акциза и НДС. В BIS.ERP такой детализации в обработчике ТМЗ сейчас нет.

### 7.3 Что реализовать в BIS ERP

Поля расходов шапки уже есть. Нужно дополнить их структурой расходов и распределений. Для каждого расхода хранить вид, сумму, налоговые компоненты, контрагента/счёт расчётов при необходимости, признак включения в стоимость и способ распределения.

Для первого этапа достаточно распределения по стоимости. Распределение по количеству допустимо только для сопоставимых единиц; по весу — после появления достоверного веса. Пользовательская ручная раскладка должна сохраняться явно и проверяться на равенство общему расходу.

Пример: две строки с базой 600,00 и 400,00, транспорт 100,00. Распределения 60,00 и 40,00; стоимость поступления до иных включаемых компонентов — 660,00 и 440,00.

Пример округления: три равные базы и расход 100,00. После округления 33,33 + 33,33 + 33,33 возникает разница 0,01. Правило должно детерминированно назначить её одной строке, например строке с наибольшей базой, а при равенстве — с меньшим номером. Итог распределения обязан стать ровно 100,00.

Необходимо отличать стоимость запасов от суммы обязательства поставщику товара. Если транспорт оказал другой контрагент, его сумма не должна автоматически увеличивать долг перед поставщиком материала.

## 8 Остатки и себестоимость

### 8.1 Исторический алгоритм

`CENA_S` группируется по материалу, счёту и заказу. `NAL_S` дополнительно различает участок и МОЛ. При расходе уменьшаются количество и стоимость, при приходе увеличиваются. Средняя цена обновляется по выражению `IIF(KOL#0, ST/KOL, 0)`.

В форме перемещения `fma1_31` встречается выбор цены из `nal_z.cena_ed`. Следовательно, в старой программе есть как сводная средняя цена, так и оценка в аналитическом разрезе. Нельзя без отдельного решения утверждать, что во всех документах применяется одна глобальная средняя цена.

Параметр `kk` в `cena_s.prg` и `CENA_RAS.PRG` позволяет выполнить прямое изменение и обратное изменение. Это пример необходимой обратимости, но для BIS.ERP одной смены знака недостаточно, если после документа появились зависимые расходы.

### 8.2 Состояние BIS ERP

Наличие `site_id`, `responsible_person_id`, `Quantity` и `Price` не создаёт регистр. В проверенном обработчике проведения ТМЗ нет записи количества, материала и МОЛ в отдельный журнал движений, нет получения средней цены на дату, нет проверки доступного остатка.

`Models/Material.cs` содержит `Quantity`, `Price` и текстовый `Warehouse`. Такая карточка не заменяет историю движения по датам, участкам и МОЛ. Текущие динамические документы ссылаются на метаданный справочник материалов; не следует создавать второй источник остатков на основании старой EF-модели.

### 8.3 Предлагаемый способ оценки

Для первой версии рекомендуется скользящая средняя стоимость. До реализации нужно закрепить разрез оценки: например инфобаза, собственная организация при её отдельном учёте, материал и счёт хранения; участок и МОЛ могут либо входить в ключ оценки, либо быть только количественной аналитикой. Выбор должен соответствовать учётной политике и контрольным примерам.

Скользящая средняя в выбранном разрезе:

```text
После прихода:
Qnew = Qold + Qin
Cnew = Cold + Cin
Average = Cnew / Qnew, если Qnew != 0

Расход:
Cout = Round(Qout × AverageBeforeMovement, 2)
Qnew = Qold − Qout
Cnew = Cold − Cout
```

Если списывается весь остаток, расходу передаётся вся оставшаяся стоимость, чтобы после списания не оставались копейки при нулевом количестве.

Пример: остаток 10 единиц стоимостью 1 000,00; приход 5 единиц стоимостью 800,00. Общий остаток 15 и 1 800,00, средняя цена 120,00. Расход 4 единиц стоит 480,00, остаток — 11 единиц и 1 320,00. Если продажная цена 200,00, база реализации — 800,00; она не меняет себестоимость 480,00.

### 8.4 Порядок документов

Для одной даты нужен устойчивый порядок: дата/время хозяйственной операции, последовательность проведения или другой сохранённый бизнес-порядок. UUID допустим только как последний технический критерий равенства, а не как замена согласованной хронологии.

Изменение старого прихода может изменить стоимость всех последующих расходов. На первом этапе безопаснее запрещать отмену при зависимых последующих движениях и объяснять причину. Позже добавить управляемый пересчёт от выбранной даты с предварительным списком затронутых документов.

### 8.5 Перемещения и остатки

Перемещение создаёт две связанные записи: минус у источника, плюс у получателя. Количество и общая стоимость в пределах одной инфобазы сохраняются. Равенство счетов хранения не отменяет движение между разными участками или МОЛ.

Если разрез оценки включает склад/МОЛ, стоимость принимающей стороны должна увеличиться на переданную стоимость, а средняя цена пересчитаться по её остатку. Если оценка общая по материалу и счёту, внутреннее перемещение не изменяет сводную стоимость оценки.

## 9 Проводки по видам операций

### 9.1 Что делает текущий обработчик

`MetadataService.ProcessInventoryDocumentAsync()` определяет только, является ли документ поступлением. Для поступления дебет берётся из строки, кредит — из шапки; для выбытия и перемещения — наоборот.

Сумма проводки берётся из `LineTotal`, а если он равен нулю — из `AmountWithoutTax`. Проводки с неположительной суммой, пустыми счетами либо равными счетами пропускаются. Если хотя бы одна проводка создана, документ получает `is_posted=true`.

`operation_kind` не участвует в выборе алгоритма внутри этого обработчика. Общие `PostingRules` проверяются в `PostDocumentAsync()` после специальной ветки ТМЗ, поэтому простое добавление правил метаданных не изменит эту ветку.

### 9.2 Требуемое экономическое поведение

Ниже перечислены роли счетов, а не обязательные номера. Номера должны браться из плана счетов и настройки организации.

| Операция | Движение запасов | Бухгалтерский смысл |
|---|---|---|
| Приобретение | Плюс количество и стоимость поступления | Запасы / расчёты с поставщиком; учитываемый отдельно НДС — отдельной записью; включаемые расходы — в стоимость |
| Приход из производства | Плюс количество и оценка выпуска | Запасы / производственные затраты либо иной согласованный источник |
| Приход по акту | Плюс количество и согласованная оценка | Запасы / источник излишков или иной счёт по акту |
| Реализация | Минус количество и себестоимость | Отдельно списание себестоимости, выручка, налоги и расчёты с покупателем |
| Расход в производство | Минус количество и себестоимость | Производственные затраты / запасы с аналитиками назначения |
| Списание по акту | Минус количество и себестоимость | Потери либо иной счёт основания / запасы |
| Передача в подотчёт | Минус источник, плюс получатель | Аналитическая передача; бухгалтерская запись зависит от принятой схемы |
| Автоматическая передача | То же, но с явно определённым правилом подбора | Нужна спецификация автоматического заполнения; название вида не означает готовый алгоритм |

Для продажи необходимо использовать счёт хранения, дохода и себестоимости материала либо настройки вида операции. Такие поля уже есть в метаданном справочнике; наличие полей нужно связать с реальным проведением.

### 9.3 Связь с общим журналом

Сохранить `doc_postings` как единый журнал. Для записей ТМЗ обеспечить прямую связь с документом и при необходимости строкой, роль проводки и признак происхождения. Нельзя искать и удалять записи только по номеру документа: номера могут совпадать в разных типах и периодах.

Общий модуль должен заполняться последовательно: текущая вставка ТМЗ передаёт `module_code=NULL`. Это требует проверки фильтров и закрытия модуля; не следует считать все такие записи гарантированно правильно классифицированными последующей логикой.

A06 также требует контрольного воспроизведения с действующими правами и конфигурацией. Защиту следует разместить в сервисе независимо от доступности кнопки в конкретном окне.

Текущий `PostDocumentAsync()` уже имеет общую транзакцию бухгалтерского проведения и проверку даты. Не нужно писать в плане «транзакций и защиты периода нет вообще». Проблемы — раздельное сохранение шапки/строк, отсутствие регистров ТМЗ и недостаточная проверка всех участвующих данных.

## 11 Целевая архитектура

### 11.1 Сохранить действующие точки входа

```text
DynamicDocumentWorkView
  → InventoryDocumentDialog
    → сервис документа ТМЗ
      → проверка → расчёт → сохранение шапки и строк

MetadataService.PostDocumentAsync
  → сервис проведения ТМЗ
    → стратегия operation_kind
    → расчёт стоимости и движений
    → doc_postings
    → статус документа

Отчёты и закрытие периода
  → единый источник движений и остатков ТМЗ
```

Это схема предлагаемого развития. Новые имена сервисов ниже условные и не означают, что файлы уже существуют.

### 11.2 Ответственность сервисов

| Предлагаемый компонент | Ответственность | Что переиспользовать |
|---|---|---|
| `InventoryDocumentService` | Общая транзакция записи, версия, статус | Метаданные и существующие таблицы |
| `InventoryCalculationService` | Цена, база, налоги, валюты, итоги | Математику `InventoryLineRow.Recalculate`, но без зависимости от окна |
| `InventoryExpenseAllocationService` | Раскладка дополнительных расходов | Существующие поля шапки после уточнения структуры |
| `InventoryValuationService` | Средняя цена, стоимость расхода, перерасчёт | Единый журнал движений |
| `InventoryPostingService` | Полный цикл проведения/отмены | Общий `PostDocumentAsync`, `doc_postings`, журнал событий |
| `InventoryBalanceService` | Остаток на дату и доступность | Движения и снимки периода |
| Источник отчётных данных ТМЗ | Обороты, остатки, контрольные расхождения | `ReportDataSetService`, существующие средства отчётности |

Не создавать отдельную систему печати или параллельный журнал проводок. Использовать действующие механизмы BIS.ERP и включать новые наборы данных и макеты в конфигурацию.

### 11.3 Что должно оставаться в конфигурации

В метаданных/настройках хранить состав видов операций, доступные реквизиты, роли счетов, налоговые политики, методы распределения и привязки отчётов. Алгоритмы транзакционной целостности, блокировок, округления и средней стоимости — в ядре.

Если для проводок используется общий конструктор правил, сначала расширить его контракт до строк и рассчитанных компонентов ТМЗ и изменить порядок диспетчеризации. Прикладные правила не должны обходить обязательное создание складских движений.

## 12 Изменения данных

Все перечисленные ниже таблицы и поля — проектные предложения. Конкретные имена нужно согласовать с принятым стилем миграций; создавать их в рамках данного анализа не требуется.

### 12.1 Дополнения существующих документов

| Сущность | Предлагаемые сведения | Причина |
|---|---|---|
| Шапка | Версия записи, версия расчёта, режим цены, политика налогов | Воспроизводимость и защита от перезаписи |
| Строка | Цена продажи отдельно от оценки запаса; себестоимость единицы и расхода | Разделение разных экономических сумм |
| Строка | Режим ввода, исходная валютная сумма и курс/снимок политики при необходимости | Повторяемый пересчёт |
| Строка перемещения | Явная семантика источника и получателя | Однозначное движение |
| Строка/аналитика | UUID счёта при целевом переходе со строковых кодов | Устойчивые ссылки с сохранением совместимости |
| Шапка или отдельная связь | Идентификатор связанного документа счёта-фактуры | Защита от двойных проводок и двойного журнала |

`organization_id` в текущей шапке используется в блоке контрагента. Перед добавлением многокомпанейного разреза нельзя автоматически объявлять его идентификатором собственной организации. Нужно отдельно определить собственную организацию и контрагента; если каждая инфобаза ведёт одну организацию, часть ключа задаётся самой инфобазой.

Заказы не следует включать в обязательный ключ только потому, что они есть в FoxPro. Если предприятие учитывает материалы по заказам, добавить ссылку и обеспечить её во всех движениях, остатках, расходах и отчётах.

### 12.2 Журнал движений

Предлагаемая сущность `inventory_movements`:

| Группа | Поля по смыслу |
|---|---|
| Идентификация | Id, инфобаза через подключение, собственная организация при необходимости |
| Источник | Тип/таблица документа, Id документа, Id строки, версия проведения |
| Хронология | Дата операции, устойчивый порядок, время регистрации |
| Аналитика | Материал, счёт хранения, участок, МОЛ, заказ при включённом учёте |
| Результат | Количество со знаком, стоимость со знаком, вид движения |
| Оценка | Метод/версия расчёта, стоимость единицы, валюта оценки при необходимости |
| Обратимость | Ссылка на исходное движение/пару перемещения, статус либо сторно |

Выбрать один подход к отмене: удаление автоматически созданных движений открытого периода с аудитом либо сторнирующие записи. Смешивать оба способа без правила нельзя, иначе отчёты задвоят результат.

Для перемещения записи источника и получателя связываются одним идентификатором операции. Уникальное ограничение по источнику, версии и роли движения должно защищать от повторной вставки.

### 12.3 Остатки и снимки

Первичный источник истины — движения и документ ввода начальных остатков. Текущая таблица остатков может служить ускорителем, но должна пересобираться из истории.

Снимки периода содержат ключ аналитики, начальные количество и стоимость, приход, расход, конечные количество и стоимость, версию расчёта и связь с периодом. Механизм `FixedAssetPeriodBalances` использовать как архитектурный пример интеграции с периодом, но не как готовую таблицу материалов.

Нужны индексы по аналитическому ключу и дате, источнику движения и периоду. NULL в необязательных аналитиках требует согласованной уникальности: два одинаковых остатка с NULL не должны появляться из-за особенностей уникальных индексов PostgreSQL.

### 12.4 Расходы и распределения

Лучше хранить отдельные строки дополнительных расходов и их распределения на строки документа. Это позволит не размножать наборы колонок для каждого нового вида расхода и учитывать разных поставщиков услуг.

Для каждого распределения сохранять исходный расход, целевую строку, базу, распределённую сумму, налоговые компоненты, включаемую стоимость и корректировку округления. Итог каждой группы сверяется с исходным расходом.

## 13 Сохранение и проведение

### 13.1 Сохранение черновика

1. Прочитать прежнюю версию документа и проверить его статус.
2. Проверить старую и новую дату на доступность изменения.
3. Проверить все строки и ссылки, соответствие вида операции документу.
4. Рассчитать суммы в общем сервисе.
5. В одной транзакции записать шапку, строки и распределения.
6. Обновить версию документа; при конфликте показать, что документ изменён другим пользователем.
7. Завершить транзакцию и согласованно зарегистрировать событие.

Для атомарности сервис строк должен уметь работать в переданном подключении и транзакции. Простая внешняя обёртка вокруг существующего `ReplaceLinesAsync()` проблему не решит: он самостоятельно открывает другое подключение.

### 13.2 Проведение

1. Заблокировать документ и проверить версию/статус.
2. Проверить период и разрешённый вид операции.
3. Получить строки в согласованном снимке данных.
4. Разрешить счета из UUID или старого кода и проверить роли.
5. Проверить все строки до создания результатов.
6. Рассчитать налоги, расходы, стоимость поступления или себестоимость расхода.
7. Заблокировать затрагиваемые остатки в одинаковом порядке ключей и повторно проверить наличие.
8. Создать движения и бухгалтерские записи в одной транзакции.
9. Проверить контрольные равенства и полноту строк.
10. Записать версию расчёта и статус проведённого документа.

Не допускать успешное проведение «корректной части» документа. Если бизнесу нужна частичная отгрузка, она должна оформляться отдельным документом с явной связью с заказом, а не скрытым пропуском строк.

### 13.3 Отмена и перепроведение

Проверить период, права и зависимости. Удалить либо сторнировать только автоматические результаты данного документа по прямой ссылке. Ручные проводки сохранять или обрабатывать согласно отдельному согласованному правилу; нельзя безусловно стирать их вместе с автоматически рассчитанными.

Если документ влияет на оценку последующих расходов, отмена либо блокируется с перечнем зависимых документов, либо запускает контролируемый пересчёт всей цепочки. Перепроведение должно быть одной транзакционной операцией, а не последовательностью независимых «отменить» и «провести».

### 13.4 Конкурентность

Один `_contextAccess` защищает отдельный экземпляр сервиса, но не несколько рабочих мест. Нужны ограничения и блокировки на стороне PostgreSQL. Для отсутствующей строки остатка требуется также защита создания ключа: блокировка только существующих строк не предотвращает гонку первого прихода/расхода.

Повтор команды после тайм-аута не должен создавать повторные движения. Перед повтором проверяется сохранённая версия проведения/идентификатор операции. Два одновременно проведённых документа не должны списать больше доступного количества.

## 14 Изменения интерфейса

Сохранить текущее окно и адаптировать его по виду операции.

| Вид | Что показывать и проверять |
|---|---|
| Приобретение | Поставщик, расчёты, цена приобретения, налоги, дополнительные расходы и стоимость поступления |
| Реализация | Покупатель, продажная цена, налоги, доступное количество и отдельная себестоимость |
| Расход/списание | Источник, получатель затрат или основание акта, количество, расчётная себестоимость |
| Перемещение | Источник и получатель, наличие, передаваемое количество и стоимость |
| Приход по акту | Основание и способ оценки, связь с инвентаризацией при её наличии |

Подпись счёта строки должна соответствовать роли. Нельзя во всех документах оставлять «Дебет», если в расходе это счёт кредита/хранения.

Добавить понятные состояния «Черновик», «Проведён», «Требует пересчёта» при появлении зависимых изменений. Для проведённого документа открывать просмотр и отдельные команды отмены/перепроведения по правам.

В строке расхода показывать остаток на дату и доступное количество. Отображаемый остаток информационный: окончательная проверка всё равно выполняется внутри транзакции проведения.

Для валюты показывать направление курса и единицу котировки, дату курса и исходную валютную сумму. Запретить проведение валютного документа с отсутствующим или неположительным курсом, если курс необходим выбранному режиму.

## 15 Отчёты и контроль

### 15.1 Почему существующей ведомости недостаточно

`DocumentationMetadataSeedService.EnsureInventoryReportsAsync()` создаёт «Ведомость наличия материалов» с источником «Справочник материалов» и полями кода, названия, единицы, номера, вида, счёта хранения и активности. В этом определении нет количественных остатков и оборотов.

При наличии пользовательского набора данных в конкретной инфобазе фактическое поведение отчёта может отличаться. Но штатное определение исходника не подтверждает готовую ведомость фактического наличия.

### 15.2 Минимальный набор

| Отчёт | Основные данные | Контроль |
|---|---|---|
| Остатки на дату | Материал, счёт, участок, МОЛ, количество, стоимость, средняя цена | Сумма аналитик равна своду |
| Оборотная ведомость | Начало, приход, расход, конец по количеству и стоимости | Начало + приход − расход = конец |
| Карточка движения | Документы в устойчивом порядке, движения и остаток после каждой операции | Возможность объяснить любой остаток |
| Материальный отчёт МОЛ | Остатки и движения конкретного МОЛ | Сверка с общим остатком |
| Анализ себестоимости | Оценка перед расходом, списанное количество, рассчитанная стоимость | Отдельно от выручки |
| Дополнительные расходы | Исходный расход, база, распределение, округление | Распределено ровно исходной сумме |
| Контроль проведения | Документы, строки, движения и проводки | Нет частичного проведения и потерянных связей |
| Инвентаризационная ведомость | Учётное количество, факт, расхождение | Отдельная фиксация недостачи и излишков |

### 15.3 Проверки периода

Перед закрытием модуля ТМЗ: нет непроведённых обязательных документов периода, отрицательных остатков при запрете перерасхода, необъяснимой стоимости при нулевом количестве, несбалансированных перемещений и расхождений стоимостного регистра с соответствующими бухгалтерскими счетами.

Нельзя сравнивать сумму всех проводок с итогом документа простой арифметикой: при реализации одна сумма отражает выручку, другая — себестоимость. Контроль должен учитывать роли записей и тип операции.

### 15.4 Журнал закупок и продаж

В `BalanceService.GetPurchaseSalesJournalAsync()` все поступления ТМЗ относятся к закупкам, все выбытия — к продажам по имени документа. При текущих восьми видах операций это слишком грубо: приход из производства не является покупкой у поставщика, а списание по акту не является реализацией.

Нужно выбирать документы по `operation_kind`, корректно брать `vat_total` и `sales_tax_total` и исключать повторное отражение, если связанному документу ТМЗ соответствует отдельная счёт-фактура. В исходнике журнала используются названия/ключи налоговых полей, которые следует сверить с возвращаемым словарём актуальной модели.

## 16 Специальные операции и границы модулей

### 16.1 Инвентаризация

Приход по акту и списание по акту — результат инвентаризации, но не сама инвентаризация. Нужны дата фиксации, состав комиссии/основание при необходимости, участок и МОЛ, учётное количество на дату, фактическое количество, расхождение и связь с корректирующими документами.

Не заменять факт новым расчётом при каждом открытии. Изменение документов после даты фиксации должно обозначать необходимость сверки, а не незаметно менять подписанный результат.

### 16.2 Малоценные предметы и спецодежда

В `f_prov22.prg` и `f_prov31.prg` есть дополнительные записи износа МБП по настроенному проценту `proc_mbp`, счетам МБП и износа. Это отдельная предметная политика. Для BIS.ERP потребуются срок/правило погашения, карточка выдачи, получатель, возврат, списание и состояние предмета.

Тип материала «Малоценка» или «Спец.одежда» не доказывает реализацию такого цикла. Сначала решить, нужен ли этот контур предприятию и должен ли он использовать часть существующего модуля ОС.

### 16.3 ГСМ

В `cena_s.prg` документ 41 имеет специальную обработку, в `f_prov41.prg` списывается `kol_gsm`; также в индексации есть `PUTLIST`. Это подтверждает особый учёт ГСМ, но не раскрывает автоматически все нормы расхода и параметры путевого листа.

Если нужен этот функционал, отдельно описать транспорт, путевые листы, остаток в баке, заправки, пробег/моточасы, норму и отклонение. Не пытаться реализовать его только переименованием обычного списания.

### 16.4 Основные средства

В исходном дереве есть операции ОС. В BIS.ERP уже есть специализированные обработчики покупки, ввода в эксплуатацию, амортизации, консервации, переоценки, комплектации и выбытия, а также остатки ОС по периодам. Дублировать их в материалах не требуется.

Нужно определить границу: когда материал становится ОС, какой документ передаёт стоимость, где хранится связь исходной строки и карточки актива и как исключается двойное отражение. Детальное сравнение формул амортизации ОС проводить отдельным исследованием, если оно включается в следующую задачу.

## 17 Перенос данных

### 17.1 Начать с инвентаризации источника

Сначала получить копию фактической базы, определить кодировку, набор таблиц, даты, полноту связей и применяемые настройки. В изученном каталоге исходников хозяйственных таблиц нет, поэтому сейчас нельзя обещать автоматический перенос всех остатков и документов.

Существующий `DbfParserService` использовать для чтения формата, но отдельно реализовать предметное сопоставление материалов, МОЛ, участков, счетов, налогов, документов и остатков.

### 17.2 Варианты запуска

| Вариант | Что переносить | Применение |
|---|---|---|
| Остатки на дату запуска | Справочники, аналитические остатки, начальную стоимость | Быстрее и проще для первого перехода |
| История документов | Всё выше плюс шапки, строки и связи | Нужна история в новой системе и подтверждена оценка |
| Архив отдельно | Остатки в BIS.ERP, старые документы доступны для чтения отдельно | Допустимо, если устраивает аудит и пользователей |

Полную историю нельзя перепроводить новым алгоритмом и одновременно требовать автоматического совпадения всех исторических сумм. Возможные пути: сохранить исторические рассчитанные суммы как исходные снимки либо согласовать расхождения нового пересчёта.

### 17.3 Сопоставление

Для старых ключей хранить таблицу соответствия: источник, таблица, старый код/ключ, новый UUID, результат проверки и контрольная сумма записи. Повторный импорт не должен создавать дубли.

Материал сопоставлять по устойчивому коду и дополнительным признакам, не только по названию. Участок и МОЛ различать; историческое совпадение ФИО не доказывает одну сущность. Заказы сохранять, если они включены в целевую аналитику.

### 17.4 Контроль перед запуском

Сверить количество и стоимость по материалу/счёту, затем по участку/МОЛ и заказу при его наличии. Сверить общие бухгалтерские остатки и связанные обязательства отдельно. Список несовпадений должен быть документом для разбора, а не автоматически перенесённым остатком на фиктивного МОЛ.

В `rasch_ost.prg` старой программы расхождения записываются на служебные значения «Сбойные ситуации». Это объясняет исторический способ восстановления, но не является рекомендуемым способом миграции в BIS.ERP.

## 18 Этапы реализации

Сроки ниже намеренно не выражены в календарных датах: без рабочей базы, согласованной политики оценки и выбранного объёма миграции такая оценка была бы недостоверной. Каждый этап имеет проверяемый результат и зависит от предыдущего.

### Этап 0 Зафиксировать правила и контрольные примеры

**Результат:** согласованная краткая спецификация учётной политики ТМЗ.

Определить разрез средней цены, допустимость отрицательного остатка, порядок документов одной даты, используемые налоговые режимы, включение расходов в стоимость, роли счетов, границу со счётом-фактурой и собственную организацию. Выбрать реальные обезличенные примеры покупки, продажи, списания и перемещения.

**Приёмка:** для каждого примера вручную утверждены ожидаемые движения, остатки и проводки. Базовая формула BIS.ERP не меняется молча ради сходства с FoxPro.

### Этап 1 Исправить целостность существующего документа

**Приоритет:** P0. **Зависимость:** этап 0 для правил статуса, остальное можно готовить независимо.

Объединить запись шапки и строк, запретить редактирование проведённого документа, разрешать UUID счёта в код, проверять все строки перед проведением, проверять старую и новую дату. Сохранить номера и прямые связи документов.

Точки изменения: `InventoryDocumentDialog`, `InventoryDocumentLineService`, `MetadataService` и новый координатор записи при необходимости.

**Приёмка:** ошибка на последней строке откатывает весь документ; ни одна строка не теряется при проведении; счёт в проводке соответствует коду плана счетов. На этом этапе модуль всё ещё не объявляется полным складским учётом.

### Этап 2 Ввести движения и начальные остатки

**Приоритет:** P0. **Зависимость:** этапы 0–1.

Создать журнал движений, ключ аналитики, документ/механизм ввода начальных остатков и остаток на дату. Добавить защиту от дублирования и блокировку остатков. Сделать простой диагностический просмотр движения материала.

**Приёмка:** приход, расход и перемещение дают ожидаемые количественные остатки; сумма двух сторон перемещения равна нулю по количеству и стоимости; два одновременных списания не создают скрытый перерасход.

### Этап 3 Реализовать стоимость и дополнительные расходы

**Приоритет:** P0/P1. **Зависимость:** этап 2.

Добавить скользящую среднюю, стоимость расхода, правило полного списания остатка, распределение расходов и раздельные суммы продажи/оценки. Утвердить точность и правила округления. Сохранить версию расчёта.

**Приёмка:** примеры из разделов 7–8 сходятся до копейки; при полном расходе нет остаточной стоимости; дополнительные расходы распределены полностью.

### Этап 4 Проведение по восьми видам и отмена

**Приоритет:** P0/P1. **Зависимость:** этапы 2–3.

Ввести стратегии по `operation_kind`, отдельные роли проводок и использование счетов материала/операции. Реализовать отмену, проверку последующих зависимостей, согласованный аудит и повтор команды без дублирования.

**Приёмка:** продажа создаёт отдельные выручку и списание себестоимости; производственный расход не становится продажей; отмена восстанавливает исходное состояние либо объяснимо блокируется из-за зависимостей.

### Этап 5 Объединить налоги и валюту

**Приоритет:** P1. **Зависимость:** согласованные правила этапа 0; общий расчёт готовится параллельно с проектированием этапов 2–4 без выпуска непроверенной схемы.

Вынести текущие формулы, добавить режим цены с налогами/без налогов и только требуемые исторические варианты баз. Унифицировать валютную сумму шапки, строк и проводок; учитывать единицу котировки и курс на дату. Действующие документы не пересчитывать новой политикой автоматически.

**Приёмка:** отображение, сохранённые данные и проводки согласованы; повторное открытие не меняет итог; смена справочной ставки не меняет проведённый документ.

### Этап 6 Отчёты и закрытие периода

**Приоритет:** P1. **Зависимость:** этапы 2–5.

Создать реальные ведомости остатков, оборотов и МОЛ, карточку движения, отчёт распределений и диагностику расхождений. Исправить отбор закупок/продаж. Встроить ТМЗ в существующее закрытие периода и снимки.

**Приёмка:** все контрольные равенства соблюдены; закрытый период защищён; повторное формирование отчёта воспроизводит результат.

### Этап 7 Миграция и опытная эксплуатация

**Приоритет:** до запуска в рабочий учёт. **Зависимость:** этапы 1–6.

Разработать импорт на копии реальной базы, сформировать протокол сверки и инструкцию перехода. Выполнить полный цикл на одном периоде и нескольких рабочих местах, проверить восстановление после сбоя. Определить момент прекращения ввода в старой программе и процедуру отката запуска.

**Приёмка:** утверждён протокол остатков и расхождений; повторный импорт не дублирует сущности; операции пользователей не требуют ручного исправления регистров.

### Этап 8 Расширения по потребности

Инвентаризация с фактом, карточный учёт спецодежды/МБП, ГСМ, заказы, преобразование номенклатуры и расширенная производственная оценка. Для каждого — отдельная спецификация и критерии. Не делать эти подсистемы условием первой работающей версии, если предприятие ими не пользуется.

### Минимальный объём завершённого базового контура

Восемь видов операций с корректным результатом, начальные остатки, движения, стоимость, налоги и валюта по согласованной политике, отмена, защита периода, ведомость остатков и оборотов. Наличие одного окна ввода и проводок без регистра не соответствует этому критерию.

## 20 Решения которые нужно зафиксировать

| Вопрос | Предлагаемая отправная точка | Почему нельзя оставлять неявным |
|---|---|---|
| Метод оценки | Скользящая средняя | От него зависят все последующие расходы |
| Разрез оценки | Материал и счёт; МОЛ/участок уточнить по политике | FoxPro использует несколько уровней цен |
| Отрицательный остаток | Запрет для обычного проведения | Иначе требуется отдельная обработка отрицательной стоимости |
| Налоги | Сохранить текущий режим как самостоятельную политику | Исторические варианты дают разные компоненты |
| Цена пользователя | Явно «без налогов» либо «с налогами» | Сейчас смысл определяется формулой без переключателя |
| Дополнительные расходы | Раскладка по стоимости с детерминированной копейкой | Должна сходиться шапка и строки |
| НДС в стоимости | Настройка по операции/налоговому основанию | Историческая формула не универсальна |
| Заказы | Включать только при реальной потребности | Аналитика влияет на всю модель остатков |
| Счёт-фактура | Определить владельца выручки и налоговых проводок | Нельзя проводить дважды одну хозяйственную операцию |
| Старые документы | Не пересчитывать автоматически | Новая формула может изменить историю |
| Отмена задним числом | Сначала запрет при зависимостях | Полный пересчёт требует отдельного управления |
| Собственная организация | Отдельно от контрагента либо задана инфобазой | Текущий `organization_id` нельзя переосмыслить без анализа |
| Миграция | Начальные остатки как первый рассматриваемый вариант | Полная история существенно расширяет объём работ |

Эти решения нужны перед изменением учётного поведения. Они не препятствуют подготовке транзакционного сохранения, разрешения счетов, проверки полноты строк и изоляции расчётного сервиса.
