# Версионность продукта: что сделано

Документ описывает внедрённую систему автоматической версионности BIS ERP:
архитектуру, механизм сборки, доступ из кода, показ в интерфейсе, запись в базу
данных, проверку и историю изменений.

Дата составления: 09.10.2026. Текущая версия на момент составления: `1.1.19`.

---

## 1. Задача

До внедрения версионности в проекте не было единого способа понять, какая
сборка запущена. Это приводило к конкретной проблеме: после правок нельзя
было отличить старую сборку от новой, потому что работающий процесс держит
сборку в памяти, а признака версии не было ни в одном месте интерфейса.

Дополнительно версия читалась в разных местах по-разному, а в диалоге
«О системе» была жёстко зашита строка «Версия 1.0», не связанная ни с чем.

### Что требовалось

1. Версия должна увеличиваться **автоматически при каждой сборке**.
2. Формат — стандартный: `1.1.1`, `1.1.2` и далее.
3. Актуальная версия должна попадать **в базу данных при выгрузке**.
4. Версия должна быть **видна в интерфейсе**.

---

## 2. Что было раньше

До внедрения в проекте уже существовали разрозненные механизмы версий:

| Место | Как читалась версия | Проблема |
|---|---|---|
| `AppUpdatePackageService.cs:854` | `AssemblyInformationalVersion`, затем `AssemblyName.Version` | Своя логика |
| `BisPatchService.cs:1155` | `AssemblyName.Version` | Другая логика |
| `ConfigurationExchangeService.cs:296` | Жёстко зашито `Version = "1.0"` | Не связано с программой |
| `BIS.ERP.csproj` | `<Version>1.0.0</Version>` | Никогда не менялось |
| `AboutSystemDialog.xaml:43` | `Text="Версия 1.0"` в разметке | Литерал, не данные |

**Вывод:** версия была объявлена в четырёх местах, три из которых никогда
не менялись, а два читали её из разных источников.

## 3. Архитектура решения

```
                    version.json                    ← единственный источник
                         │
                         │ читает и увеличивает
                         ▼
              Directory.Build.props                ← механизм сборки
                         │
                         │ пишет метаданные сборки
                         ▼
                   BIS.ERP.dll                     ← носитель версии
                         │
                         │ читает один раз при старте
                         ▼
                  AppVersion.cs                    ← единая точка доступа
                         │
     ┌───────────────────┼───────────────────┬──────────────────┐
     ▼                   ▼                   ▼                  ▼
 Рабочее окно     Конфигуратор      «О системе»        Выгрузка конфигурации
                                                              │
                                                              ▼
                                                  MetadataConfigurations
```

**Принцип:** версия объявляется один раз, увеличивается автоматически,
читается через одну точку доступа, показывается везде одинаково.

## 4. Источник версии: version.json

Файл создан в корне проекта — `version.json`.

```json
{
  "Major": 1,
  "Minor": 1,
  "Patch": 19,
  "Build": 19,
  "Semantic": "1.1.19",
  "Informational": "1.1.19+2026-10-09T08:04:27Z#19",
  "LastBuildUtc": "2026-10-09T08:04:27Z"
}
```

### Назначение полей

| Поле | Тип | Кто меняет | Назначение |
|---|---|---|---|
| `Major` | число | **Вручную** | Несовместимые изменения, требующие миграции данных |
| `Minor` | число | **Вручную** | Новая функциональность без ломки совместимости |
| `Patch` | число | Автоматически | Исправления, растёт при каждой сборке |
| `Build` | число | Автоматически | Сквозной счётчик сборок |
| `Semantic` | строка | Автоматически | Готовая версия вида `1.1.19` |
| `Informational` | строка | Автоматически | Полная версия с датой и номером сборки |
| `LastBuildUtc` | строка | Автоматически | Время последней сборки в UTC |

### Формат строки версии

```
1.1.19+2026-10-09T08:04:27Z#19
└──┬─┘ └─────────┬─────────┘└┬┘
   │             │           └── номер сборки
   │             └────────────── время сборки в UTC
   └──────────────────────────── версия Major.Minor.Patch
```

> **Важно.** Файл `version.json` должен быть в системе контроля версий.
> Он не попадает под `obj/` и `bin/`, потому что лежит в корне проекта.

## 5. Механизм сборки: Directory.Build.props

Файл создан в корне проекта. MSBuild подхватывает его автоматически и применяет
ко всем проектам в дереве.

### Общая структура

```
WriteVersionBumpScript      готовит скрипт инкремента
        ↓
BumpProductVersionFiles     выполняет скрипт, получает версию
        ↓
ApplyProductVersion         пишет метаданные сборки
        ↓
GenerateAssemblyInfo        SDK создаёт AssemblyInfo
        ↓
CoreCompile                 компиляция
        ↓
CopyVersionFileToOutput     копирует version.json рядом с программой
```

### Фаза 1. Скрипт инкремента

Цель `WriteVersionBumpScript` формирует файл `obj/bump-version.ps1`.
Скрипт не хранится в репозитории — он создаётся при каждой сборке, поэтому
не может устареть.

Что делает скрипт:

1. Читает `version.json` регулярными выражениями.
2. Увеличивает `Patch` и `Build` на единицу.
3. Формирует строку `Semantic` и `Informational`.
4. Записывает файл обратно в кодировке UTF-8 без BOM.
5. Печатает две строки для MSBuild: `VERSION=…` и `INFORMATIONAL=…`.

```powershell
$patch = $patch + 1
$build = $build + 1
$semantic = '{0}.{1}.{2}' -f $major, $minor, $patch
$stamp = (Get-Date).ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ssZ')
$informational = '{0}+{1}#{2}' -f $semantic, $stamp, $build
[System.IO.File]::WriteAllLines($path, $lines, (New-Object System.Text.UTF8Encoding($false)))
```

**Почему PowerShell, а не встроенные средства MSBuild.** MSBuild не умеет
увеличивать число в JSON-файле и записывать его обратно без сторонних задач.
PowerShell есть на любой Windows, поэтому зависимостей не добавляется.

**Почему используется `powershell.exe`, а не `pwsh`.** `pwsh` (PowerShell 7)
не входит в PATH для процесса MSBuild. Проверено на практике: команда
завершалась кодом 9009 «команда не найдена».

**Почему JSON разбирается регулярными выражениями, а не `ConvertFrom-Json`.**
Параметр `-AsHashtable` появился только в PowerShell 6. Windows PowerShell 5.1
его не поддерживает. Регулярные выражения работают в обеих версиях.

### Фаза 2. Метаданные сборки

Цель `BumpProductVersionFiles` выполняет скрипт и извлекает версию из вывода:

```xml
<ProductVersion>…VERSION=(\d+\.\d+\.\d+)…</ProductVersion>
<ProductBuildNumber>…#(\d+)…</ProductBuildNumber>
<ProductInformational>…INFORMATIONAL=(\S+)…</ProductInformational>
```

Затем `ApplyProductVersion` записывает метаданные через стандартную задачу
`WriteCodeFragment` — она сама формирует корректный C#-код:

```csharp
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductVersion", "1.1.19")]
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductBuild", "19")]
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductInformational", "1.1.19+2026-10-09T08:04:27Z#19")]
```

**Почему метаданные, а не атрибуты версии.** Атрибуты `AssemblyVersion`,
`FileVersion` и `InformationalVersion` создаёт сам SDK. Если задавать их из
цели, значения не успевают примениться, потому что свойства задаются внутри
цели уже после вычисления. Метаданные же попадают в отдельный файл, который
добавляется в компиляцию напрямую.

**Почему `WriteCodeFragment`, а не свой файл.** Попытка сформировать файл
вручную через `WriteLinesToFile` требовала экранировать кавычки, точки
с запятой и знаки доллара в атрибутах MSBuild. `WriteCodeFragment` принимает
имена атрибутов и параметры как элементы — экранирование не нужно.

### Фаза 3. Копирование файла версии

Цель `CopyVersionFileToOutput` копирует `version.json` в каталог вывода.
Выполняется **после** `CopyFilesToOutputDirectory`, когда каталог вывода
уже известен:

```xml
<Copy SourceFiles="$(_VersionJsonPath)" DestinationFolder="$(TargetDir)" SkipUnchangedFiles="true" />
```

### Условия выполнения

```xml
Condition="Exists('$(_VersionJsonPath)')
           And '$(DesignTimeBuild)' != 'true'
           And '$(BuildingProject)' == 'true'
           And !$([System.String]::Copy('$(MSBuildProjectFile)').Contains('_wpftmp'))"
```

| Условие | Зачем |
|---|---|
| `Exists('version.json')` | Защита от запуска в проектах без файла |
| `DesignTimeBuild != true` | Не увеличивать версию при работе в конструкторе IDE |
| `BuildingProject == true` | Не запускать при простом вычислении свойств |
| Исключение `_wpftmp` | WPF создаёт временный проект и цель срабатывала дважды |

## 6. Грабли, которые были пройдены

При внедрении обнаружены и устранены четыре ошибки. Они описаны, чтобы
при изменении механизма не наступить на них снова.

### Ошибка 1. `pwsh` не найден

**Симптом:**
```
error MSB3073: выход из команды "pwsh -NoProfile -NonInteractive -File …" с кодом 9009
```

**Причина:** `pwsh` (PowerShell 7) не входит в PATH для процесса MSBuild.

**Решение:** использовать `powershell.exe` — Windows PowerShell есть на любой
системе и всегда доступна через PATH.

### Ошибка 2. Двойной инкремент версии

**Симптом:** за одну сборку версия вырастала на две:
```
Версия продукта: 1.1.4 (сборка 4)
Версия продукта: 1.1.5 (сборка 5)
```

**Причина:** WPF создаёт временный проект `<Имя>_<хеш>_wpftmp.csproj`, который
тоже применяет `Directory.Build.props` и выполняет цель ещё раз.

**Решение:** исключить временный проект по имени файла:
```xml
!$([System.String]::Copy('$(MSBuildProjectFile)').Contains('_wpftmp'))
```

### Ошибка 3. Пустые метаданные в сборке

**Симптом:** в сгенерированном файле оказывались пустые значения:
```csharp
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductVersion", "")]
```

**Причина:** цель записи файла зависела от цели вычисления версии, но свойства
`$(ProductVersion)` задавались **внутри** цели вычисления. MSBuild вычисляет
свойства цели в момент её выполнения, а к моменту генерации файла они ещё
не были установлены.

**Решение:** вынести вычисление в отдельную цель и объявить её зависимостью:
```xml
<Target Name="ApplyProductVersion"
        BeforeTargets="CoreCompile"
        DependsOnTargets="BumpProductVersionFiles">
```

### Ошибка 4. Свойства версии не влияли на атрибуты сборки

**Симптом:** `AssemblyVersion` и `FileVersion` оставались `1.0.0.0`, несмотря
на правильную версию в свойствах.

**Причина:** атрибуты сборки создаёт цель SDK `GenerateAssemblyInfo`, которая
выполняется до `CoreCompile` и не видит свойства, заданные в цели, привязанной
к `CoreCompile`.

**Решение:** отказаться от попытки влиять на атрибуты версии и использовать
метаданные сборки, которые добавляются в компиляцию отдельным файлом.

### Побочная проблема. Наследование подпроектом

`Directory.Build.props` из корня наследуется **всеми** проектами в дереве,
включая `BIS.ERP.Updater`, где нет `version.json`.

**Симптом:**
```
error MSB3030: не удалось скопировать файл "BIS.ERP.Updater\version.json" — файл не найден
```

**Решение:** условие `Exists('$(_VersionJsonPath)')` в целях и проверка перед
копированием.

## 7. Единая точка доступа: AppVersion

Файл `Services/AppVersion.cs` — статический класс, читающий версию из метаданных
сборки один раз при первом обращении.

### Открытые свойства

| Свойство | Тип | Пример | Назначение |
|---|---|---|---|
| `Semantic` | string | `1.1.19` | Версия без номера сборки. Основное значение |
| `Build` | int | `19` | Номер сборки |
| `Full` | string | `1.1.19.19` | Полная версия |
| `BuildUtc` | string | `2026-10-09T08:04:27Z` | Время сборки в UTC |
| `BuildLocalText` | string | `09.10.2026 14:04` | Время сборки по местному времени |
| `Display` | string | `1.1.19 (сборка 19 от 09.10.2026 14:04)` | Подробная подпись для диалога «О системе» |
| `DisplayShort` | string | `1.1.19 (сборка 19)` | Короткая подпись для шапки окна |
| `ProductText` | string | `BIS ERP 1.1.19.19` | Строка для протокола |

### Как читается версия

```csharp
private static string ReadMetadata(string key, string fallback)
{
    var value = Assembly.GetExecutingAssembly()
        .GetCustomAttributes<AssemblyMetadataAttribute>()
        .FirstOrDefault(attribute => string.Equals(attribute.Key, key, StringComparison.Ordinal))
        ?.Value;

    return string.IsNullOrWhiteSpace(value) ? fallback : value.Trim();
}
```

Время сборки извлекается из строки `Informational`:

```csharp
var informational = ReadMetadata(InformationalKey, string.Empty);
var plusIndex = informational.IndexOf('+');       // 1.1.19+2026-10-09T08:04:27Z#19
var tail = informational[(plusIndex + 1)..];
var hashIndex = tail.IndexOf('#');
return (hashIndex >= 0 ? tail[..hashIndex] : tail).Trim();
```

### Почему метаданные, а не чтение файла

`version.json` копируется рядом с программой, но читать версию из файла
ненадёжно: файл можно потерять, заменить или испортить при обновлении.
Метаданные находятся **внутри** сборки и не могут с ней разойтись.

## 8. Показ версии в интерфейсе

Версия выводится в трёх местах. Формат зависит от места: в шапках окон —
короткий (`AppVersion.DisplayShort`), в диалоге «О системе» — подробный
(`AppVersion.Display`) с датой сборки.

### Рабочее окно

Место: левая панель, в шапке под названием системы.

```
┌─────────────────────────────┐
│          🏢  BIS ERP        │
│      версия 1.1.22 (сборка  │
│                    22)      │
│  ОСОО1 · Администратор      │
└─────────────────────────────┘
```

Версия выводится **под** названием системы, а не рядом с ним. Это сделано
намеренно: при размещении рядом длинная подпись наезжала на название
«BIS ERP» и перекрывала его.

Элемент разметки: `VersionText` в `Views/MainWorkWindow.xaml`.
Дополнительно версия выводится в заголовке окна:

```
BIS ERP - Рабочий режим — версия 1.1.22 (сборка 22)
```

### Конфигуратор

Место: левая панель, под строкой «Режим конфигуратора».

```
┌──────────────────────────────────┐
│  🏢  BIS ERP                     │
│      Режим конфигуратора         │
│      версия 1.1.22 (сборка 22)   │
│      Инфобаза: ОСОО1             │
│      [ Патч: 1.0.5 ]             │
└──────────────────────────────────┘
```

Элемент разметки: `VersionText` в `Views/ConfiguratorWindow.xaml`.

> **Не путать два значения.** Значок «Патч» показывает версию применённого
> обновления **базы данных** (`BisPatchService`) — это независимая величина.
> «Версия» — версия **программы**.

### Диалог «О системе»

Обе версии выводятся **в одной строке, выравнивание слева**:

```
Версия программы: 1.1.22 (сборка 22 от 09.10.2026 14:04)   •   Версия конфигурации: 1.1.22
```

Подробная версия с датой сборки показывается только здесь. В шапках окон она
сокращена до «версия и сборка», чтобы не перекрывать другие элементы.

Версия программы — из `AppVersion.Display`.
Версия конфигурации — из таблицы `MetadataConfigurations`, поле `Version`.
Если выгрузок ещё не было, выводится `не задана`.

Разметка диалога: горизонтальная панель с тремя элементами —
`VersionProgramText`, разделитель `•` и `ConfigurationVersionText`.

**Что было исправлено:**

1. В разметке было жёстко зашито `Text="Версия 1.0"` — литерал, не связанный
   ни с программой, ни с базой. Заменено на именованный элемент
   `ConfigurationVersionText`, заполняемый из данных.
2. Обе версии стояли по краям строки, из-за чего подробная подпись обрезалась.
   Теперь они идут подряд с выравниванием слева.

### Ошибка размещения в шапке окна

При первом внедрении версия была помещена **внутрь горизонтальной панели**
рядом с названием системы:

```xml
<!-- Было: версия в одной строке с названием -->
<StackPanel Orientation="Horizontal">
    <Border .../>                        <!-- логотип -->
    <TextBlock x:Name="SystemNameText"/> <!-- BIS ERP -->
    <TextBlock x:Name="VersionText"/>    <!-- версия наехала на название -->
</StackPanel>
```

Подробная подпись вида `версия 1.1.21 (сборка 21 от 09.10.2026 14:04)`
оказалась шире доступного места и перекрыла название «BIS ERP».

**Решение:** версия вынесена **под** название отдельной строкой, формат
сокращён до «версия и сборка»:

```xml
<!-- Стало: версия отдельной строкой под названием -->
<StackPanel HorizontalAlignment="Center">
    <StackPanel Orientation="Horizontal">
        <Border .../>
        <TextBlock x:Name="SystemNameText"/>   <!-- BIS ERP -->
    </StackPanel>
    <TextBlock x:Name="VersionText"/>          <!-- версия ниже -->
</StackPanel>
```

Подробная версия с датой сборки перенесена в диалог «О системе», где места
достаточно.

## 9. Запись версии в базу данных

### В файл выгрузки конфигурации

Модель `Models/ConfigurationPackage.cs` дополнена тремя полями:

| Поле | Тип | Содержимое |
|---|---|---|
| `ApplicationVersion` | string | `1.1.19` |
| `ApplicationBuild` | int | `19` |
| `ApplicationBuildUtc` | string | `2026-10-09T08:04:27Z` |

Заполняются в `ConfigurationExchangeService.BuildPackageAsync`:

```csharp
var package = new ConfigurationPackage
{
    ExportedAt = DateTime.UtcNow,
    ApplicationVersion = AppVersion.Semantic,
    ApplicationBuild = AppVersion.Build,
    ApplicationBuildUtc = AppVersion.BuildUtc,
    …
};
```

В файле выгрузки это выглядит так:

```json
{
  "Format": "BIS.Configuration",
  "Version": 2,
  "ExportedAt": "2026-10-09T08:10:00Z",
  "Application": "BIS ERP",
  "ApplicationVersion": "1.1.19",
  "ApplicationBuild": 19,
  "ApplicationBuildUtc": "2026-10-09T08:04:27Z"
}
```

**Совместимость.** Существующие файлы выгрузки читаются без изменений:
новые поля имеют значения по умолчанию, десериализация старых файлов
не вызывает ошибок.

### В таблицу MetadataConfigurations

Поле `Version` существовало и раньше, но содержало жёстко зашитое `"1.0"`.
Теперь при каждой выгрузке и загрузке записывается текущая версия программы:

```csharp
config.IsInitialized = true;
config.UpdatedAt = DateTime.UtcNow;
// Версия конфигурации всегда соответствует версии программы,
// которой сделана последняя выгрузка или загрузка.
config.Version = AppVersion.Semantic;
await _context.SaveChangesAsync();
```

### Чтение версии конфигурации

Добавлен метод только для чтения — для показа в диалоге «О системе»:

```csharp
public async Task<string> GetConfigurationVersionAsync()
{
    var version = await _context.MetadataConfigurations
        .AsNoTracking()
        .OrderByDescending(item => item.UpdatedAt)
        .Select(item => item.Version)
        .FirstOrDefaultAsync();

    return string.IsNullOrWhiteSpace(version) ? "не задана" : version;
}
```

### Проверка через SQL

```sql
SELECT "Id", "Version", "UpdatedAt"
FROM "MetadataConfigurations"
ORDER BY "UpdatedAt" DESC
LIMIT 5;
```

Поле `Version` должно совпадать с версией программы, которой сделана
последняя выгрузка или загрузка.

private static string GetCurrentAppVersion()

## 13. Как пользоваться

### Обычная работа

Ничего делать не нужно. При каждой сборке версия увеличивается сама.
В выводе сборки появляется строка:

```
Версия продукта: 1.1.20 (сборка 20)
```

### Выпуск минорной версии

Открыть `version.json`, поднять `Minor` и обнулить `Patch`:

```json
"Minor": 1,      →    "Minor": 2,
"Patch": 19,     →    "Patch": 0,
```

При следующей сборке версия станет `1.2.1`, дальше будет расти сама.

### Выпуск мажорной версии

Так же, но поднимается `Major`:

```json
"Major": 1,      →    "Major": 2,
"Minor": 1,      →    "Minor": 0,
"Patch": 19,     →    "Patch": 0,
```

Результат следующей сборки: `2.0.1`.

### Что важно помнить

1. **`version.json` — источник версии**, его нужно держать в системе контроля
   версий. Он не игнорируется через `.gitignore`.
2. **Сборка с ошибкой тоже увеличивает версию.** Инкремент выполняется до
   компиляции. Это осознанный выбор: номер сборки — сквозной счётчик попыток.
3. **Приложение держит сборку в памяти.** Если программа запущена во время
   сборки, файлы на диске обновятся, но процесс продолжит работать со старой
   версией. Версия в шапке это покажет.
4. **`Patch` растёт и на отладочных сборках**, поэтому номера идут с пропусками
   между выпусками. Это нормально: смысл для пользователя несут `Major` и `Minor`.
