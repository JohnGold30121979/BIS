# ТМЗ. Миграция аналитики строк, атомарное сохранение и отображение НСП

Дата разбора — 5 ноября 2026 года.

## Что произошло

В журнале базы партнёра при сохранении документа ТМЗ зарегистрирована ошибка PostgreSQL:

```text
42703: столбец "line_analytics" в таблице "doc_inventory_incoming_lines" не существует
POSITION: 458
```

После ошибок записи строк журнал также показывал сообщения о занятых номерах 5, 6 и 7. Запись об отключении модуля «Основные средства» относится к отображению модуля в рабочем окне.

Старый порядок сохранения объясняет, как могли появиться документы без строк:

1. Диалог вызывал `CreateDynamicRecordAsync` или `UpdateDynamicRecordAsync`. Сервис записывал шапку документа.
2. Диалог отдельно вызывал `ReplaceLinesAsync`. Сервис строк открывал другое подключение и начинал собственную транзакцию.
3. При ошибке `42703` откатывалась транзакция строк. При создании шапка оставалась в базе и занимала номер. При редактировании изменения шапки могли сохраниться, хотя строки оставались прежними.

Сам журнал не показывает фактическое состояние документов с этими номерами. Его можно проверить запросом ниже.

## Почему колонка могла отсутствовать

Колонка входит в модель строк ТМЗ. Сервис построения схемы умеет добавлять отсутствующие колонки, но миграция модели `2026.10.21.01` разовая. Если она уже отмечена в `schema_migrations`, открытие базы пропускает этот шаг. В результате база могла сохранить схему таблиц, созданную до добавления аналитики строк.

## Миграция 2026.11.05.01

В [SchemaMigrationService.cs](../Services/SchemaMigrationService.cs) зарегистрирован повторяемый шаг:

```csharp
new("2026.11.05.01",
    "Аналитика строк документов ТМЗ: колонка line_analytics",
    true,
    EnsureInventoryLineAnalyticsAsync)
```

Шаг берёт список таблиц и определение колонки из [InventoryDocumentModel.cs](../Services/InventoryDocumentModel.cs):

```csharp
private static async Task EnsureInventoryLineAnalyticsAsync(AppDbContext context)
{
    var (column, definition) = InventoryDocumentModel.LineColumns
        .Single(item => item.Column == "line_analytics");
    var statements = InventoryDocumentModel.Documents.Select(document =>
        $"ALTER TABLE IF EXISTS public.\"{document.LinesTable}\" ADD COLUMN IF NOT EXISTS \"{column}\" {definition};");

    await context.Database.ExecuteSqlRawAsync(string.Join("\n", statements));
}
```

Приложение выполняет эквивалентный SQL при открытии базы:

```sql
ALTER TABLE IF EXISTS public.doc_inventory_incoming_lines
    ADD COLUMN IF NOT EXISTS line_analytics text NOT NULL
    DEFAULT (json_build_object()::text);

ALTER TABLE IF EXISTS public.doc_inventory_outgoing_lines
    ADD COLUMN IF NOT EXISTS line_analytics text NOT NULL
    DEFAULT (json_build_object()::text);

ALTER TABLE IF EXISTS public.doc_inventory_movement_lines
    ADD COLUMN IF NOT EXISTS line_analytics text NOT NULL
    DEFAULT (json_build_object()::text);
```

Для существующих строк при добавлении колонки значением аналитики становится текст `{}`. При повторном запуске существующая колонка и её данные сохраняются. Если таблица отсутствует, шаг пропускает её. Шаг не удаляет документы и не восстанавливает строки, запись которых ранее завершилась ошибкой.

## Сохранение документа

[Диалог ТМЗ](../Views/Dialogs/InventoryDocumentDialog.xaml.cs) проверяет строки перед записью. Должна остаться хотя бы одна строка, в каждой строке должен быть выбран материал и указано количество больше нуля. Кнопка сохранения блокируется на время обработки, а диалог закрывается с успешным результатом после завершения сохранения.

Диалог передаёт шапку и список строк одним вызовом:

```csharp
var data = BuildItemData();
var lines = _lines.ToList();

if (_recordId.HasValue)
{
    await _metadataService.UpdateDynamicRecordAsync(_document.Id, _recordId.Value, data, lines);
    SavedRecordId = _recordId.Value;
}
else
{
    SavedRecordId = await _metadataService.CreateDynamicRecordAsync(_document.Id, data, lines);
}
```

В [MetadataService.cs](../Services/MetadataService.cs) создание и редактирование открывают транзакцию перед записью шапки, если передан список строк:

```csharp
await using var transaction = inventoryLines == null
    ? null
    : await _context.Database.BeginTransactionAsync();
```

После записи шапки сервис вызывает `SaveInventoryLinesAsync`. Метод находит таблицу строк и колонку связи по модели ТМЗ и передаёт их в `ReplaceLinesAsync`:

```csharp
private Task SaveInventoryLinesAsync(
    MetadataObject metadata, Guid recordId, IReadOnlyList<InventoryLineRow> lines)
{
    var definition = InventoryDocumentModel.Documents.First(item =>
        string.Equals(item.Table, metadata.TableName, StringComparison.OrdinalIgnoreCase));

    return new InventoryDocumentLineService(_context).ReplaceLinesAsync(
        definition.LinesTable, definition.ParentColumn, recordId, lines);
}
```

[InventoryDocumentLineService.cs](../Services/InventoryDocumentLineService.cs) использует подключение и транзакцию контекста. В этой транзакции он удаляет прежние строки документа и вставляет новый набор. Пустой набор отклоняется до удаления строк:

```csharp
if (lines.Count == 0)
    throw new InvalidOperationException("Добавьте хотя бы одну строку с материалом и количеством.");

var transaction = (NpgsqlTransaction)(_context.Database.CurrentTransaction?.GetDbTransaction()
    ?? throw new InvalidOperationException("Строки ТМЗ сохраняются в транзакции документа."));
var connection = (NpgsqlConnection)_context.Database.GetDbConnection();
```

При создании увеличение счётчика номера выполняется после успешной записи строк. Общая транзакция фиксируется после выполнения операций сохранения, перед записью события в журнал:

```csharp
if (transaction != null)
    await transaction.CommitAsync();
```

Если вставка строки завершится ошибкой, выход из метода освободит незавершённую транзакцию. При создании новая шапка исчезнет при откате. При редактировании откатятся изменения шапки, удаление прежних строк и вставка новых.

## Сумма налога с продаж в строках

До изменения сумма налога с продаж входила в итоги документа ТМЗ, а отдельной колонки в гриде строк не было. Колонка **«Сумма НСП»** теперь расположена рядом с НДС в форме документа и в просмотре строк выбранного документа в журнале. Она показывает уже рассчитанное значение `SalesTaxAmount` с двумя десятичными знаками и доступна только для чтения. Формулы расчёта, запись сумм и итоговый блок используют прежнюю логику.

Привязка в [форме ТМЗ](../Views/Dialogs/InventoryDocumentDialog.xaml):

```xml
<DataGridTextColumn Header="Сумма НСП"
                    Binding="{Binding SalesTaxAmount, Converter={StaticResource DecimalInputConverter}, ConverterParameter=N2}"
                    Width="100" IsReadOnly="True"/>
```

[Грид строк в журнале ТМЗ](../Views/DynamicDocumentWorkView.xaml) использует ту же привязку и формат. Для этого изменения интерфейса отдельная миграция не требуется.

В разделе «Финансы» проверены два места:

- В [форме счёта-фактуры](../Views/Dialogs/InvoiceEditDialog.xaml) колонка уже выводила `SalesTaxAmount` под заголовком «Сумма НП». Заголовок заменён на «Сумма НСП».
- В [гриде строк счетов-фактур](../Views/InvoiceWorkView.xaml) заголовок «Налог с прод» заменён на «Сумма НСП». Из [настройки режима регистрации счетов-фактур по НДС](../Views/InvoiceWorkView.xaml.cs) убрано скрытие этой колонки.

Для проверки интерфейса открыть документ ТМЗ и счёт-фактуру с ненулевым НСП. Сверить суммы по строкам с итогом «Налог с продаж» и проверить колонку в просмотре строк обоих журналов, включая режим регистрации счетов-фактур по НДС. После изменений сборка прошла. Отображение в запущенном приложении не проверялось.

## Участок, сотрудник и проверка при добавлении документа

Поступление, выбытие и внутреннее перемещение ТМЗ используют общую форму [InventoryDocumentDialog](../Views/Dialogs/InventoryDocumentDialog.xaml). При добавлении строки колонка «Участок» раньше зависела от аналитики счёта строки. Пока счёт не был выбран или у него не было соответствующей связи, колонка либо ячейка могла быть скрыта.

«Участок» теперь постоянно виден как штатная колонка грида. Из XAML убран триггер скрытия ячейки по `Analytics[sites].IsApplicable`. В [инициализации формы](../Views/Dialogs/InventoryDocumentDialog.xaml.cs) связь `sites` оставлена в списке штатных полей, чтобы динамический механизм аналитики не добавлял вторую колонку:

```csharp
_lineAnalyticsColumns = new BIS.ERP.Views.Controls.LineAnalyticsColumns(LinesGrid,
    _metadataService, lineAccountAnalytics, catalogs.ToList(), _lines,
    row => ((InventoryLineRow)row).AccountCode, nameof(InventoryLineRow.AccountCode),
    nativeLinks: new[] { "materials", "sites", "currencies" }, afterColumn: AccountColumn);
```

Участок можно выбрать кнопкой «?» или ввести вручную. Форма сопоставляет введённый код или наименование со справочником «Участки» или «Участки (новые)». Выбранный идентификатор сохраняется в `site_id` строки.

Для сотрудника действует условие по счёту. В гриде строк аналитика из справочника «Сотрудники (Списочный состав)» доступна в строках, где у счёта включена «Связь со списочным составом». [Механизм аналитики строк](../Views/Controls/LineAnalyticsColumns.cs) показывает колонку, если условие выполняется хотя бы для одной строки. Поле «Сотрудник» в шапке зависит от того же признака у счёта шапки и сохраняется в `employee_id` шапки.

### Защита от создания шапки без строк

Форма убирает пустые строки, проверяет наличие хотя бы одной строки и требует материал и положительное количество. Дополнительная проверка в [CreateDynamicRecordAsync](../Services/MetadataService.cs) выполняется до вставки шапки. Она охватывает вызовы сервиса в обход формы и распознаёт документ ТМЗ по имени или канонической таблице:

```csharp
if (metadata.ObjectType == "Document" &&
    (IsInventoryDocumentName(metadata.Name) || InventoryDocumentModel.Documents.Any(item =>
        string.Equals(item.Table, metadata.TableName, StringComparison.OrdinalIgnoreCase))) &&
    (inventoryLines == null || inventoryLines.Count == 0))
{
    throw new InvalidOperationException("Добавьте хотя бы одну строку с материалом и количеством.");
}
```

Если список передан, шапка и строки записываются в общей транзакции. При ошибке записи строк новая шапка откатывается.

### Проверка в приложении

Для каждого из трёх видов ТМЗ на тестовой базе:

1. Добавить строку без выбора счёта. Проверить, что «Участок» уже виден. Выбрать участок, заполнить обязательные поля и сохранить документ. После повторного открытия проверить сохранённый участок.
2. Выбрать счёт строки с включённой «Связью со списочным составом» и проверить доступность выбора сотрудника. Добавить строку со счётом без этой связи и проверить доступность поля в каждой строке. Отдельно проверить поле шапки при смене счёта шапки.
3. Попробовать сохранить новый документ без строк и с одной пустой строкой. Убедиться, что форма выводит предупреждение и новая шапка в журнале не появляется.
4. При проверке сервиса вызвать `CreateDynamicRecordAsync` для каждого вида ТМЗ без списка строк и с пустым списком. В обоих случаях должна возникнуть ошибка до вставки шапки.

После изменений сборка прошла. Эти сценарии в запущенном приложении и на базе партнёра не выполнялись.

```sql
SELECT table_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN (
      'doc_inventory_incoming_lines',
      'doc_inventory_outgoing_lines',
      'doc_inventory_movement_lines'
  )
  AND column_name = 'line_analytics'
ORDER BY table_name;
```

### Проверка существующих поступлений без строк

Запрос только читает данные. Он выводит шапки поступлений, у которых нет ни одной строки. В результатах можно сверить документы из журнала по идентификатору, времени создания и номеру в карточке документа.

```sql
SELECT h."Id", h."CreatedAt"
FROM public.doc_inventory_incoming AS h
WHERE NOT EXISTS (
    SELECT 1
    FROM public.doc_inventory_incoming_lines AS l
    WHERE l.incoming_id = h."Id"
)
ORDER BY h."CreatedAt" DESC;
```
