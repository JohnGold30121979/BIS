Пример из `f_prov8.prg`:

```foxpro
M.D_NUCH = IIF(SEEK(M.SCH_DOX,'BUXSCH','IBUXSCH') AND BUXSCH.SV_O,
               IIF(!EMPTY(kod_orgp),kod_orgp,KOD_ORG),1)
```

В исходнике эта формула записана одной строкой. Здесь она разбита для чтения.

Важно для точности сравнения: в FoxPro интерфейс различается между формами. Некоторые поля размещены в шапке, некоторые в строках; справочник может открываться щелчком по заголовку колонки. Отдельная форма внутреннего перемещения ТМЗ в проверенном наборе этих форм не подтверждена. Реализация BIS.ERP применяет запрошенный пользователем единый интерфейс строк ко всем трём своим документам ТМЗ.

## Реализация BIS.ERP

Общие формы: `InvoiceEditDialog` для обеих счет-фактур, таблица затрат `FinanceDocumentDialog` для авансовых платежей, `InventoryDocumentDialog` для трёх документов ТМЗ.

- Связи определяются существующим `AccountAnalyticsRegistry`, по настройкам «Связи счетов со справочниками» и флагам выбранного счёта строки.
- Дополнительные колонки появляются рядом со счётом строки. Таблица показывает объединение нужных колонок всех строк; в каждой строке отображаются редакторы только её аналитики.
- В ячейке можно набрать точный номер/код из справочника либо нажать соседнюю кнопку «?». После разрешения показываются код и наименование; хранится идентификатор записи.
- Перед сохранением проверяется однозначность непустого введённого значения. Несуществующий или неоднозначный код нужно исправить либо выбрать запись через «?». Пустое значение не объявляется обязательным этим изменением.
- Действуют также дополнительные активные связи, добавленные пользователем в настройки, а не только организации и сотрудники.
- Материал в ТМЗ остаётся штатным обязательным реквизитом строки. Штатная колонка участка переключается по связи счёта с участками; дублирующая колонка не создаётся. В авансовых платежах сохраняется существующий механизм валюты/курса из шапки.
- В авансовом документе аналитика шапки определяется парой счетов; организация/сотрудник счёта затрат вводятся отдельно в строке.
- При временном скрытии колонки значения сохраняются в строке, чтобы переключение счёта не уничтожало введённое. Это осознанное отличие от некоторых обработчиков FoxPro, которые очищают отдельные реквизиты.
- Для динамических ссылок добавлено поле `line_analytics` в таблицы строк. В нём сохраняется JSON со значениями по кодам связей: идентификатор, код, наименование, текст. Идемпотентное добавление поля включено в штатные процедуры подготовки схемы. Сами строки по-прежнему хранятся в отдельных таблицах.

Это изменение реализует ввод, проверку и сохранение аналитики строк. Сверка выше показывает, что FoxPro также использует раздельную аналитику сторон проводки; полный перенос этого механизма в формирование проводок и отчёты BIS.ERP в данное изменение не входит.

## Проверки

Автоматический сценарий: `Tests/LineAnalyticsRegression`. Проверяет объединение колонок, доступность по счёту конкретной строки, привязку ручного ввода, разрешение номера в идентификатор, неоднозначные/неизвестные коды, сериализацию/восстановление идентификатора и названия, переключение счёта, пользовательскую связь и режим просмотра.

Команда:

```powershell
dotnet run --no-restore --project Tests/LineAnalyticsRegression/LineAnalyticsRegression.csproj -p:SkipProductVersionBump=true
```

Отдельно повторён `Tests/DocumentGridEditingRegression`: фиксация суммы без смены фокуса и замена выделенного значения проходят.

Итог: оба сценария PASS, включая штатный участок и размещение новых колонок после счёта. Сборка основного проекта завершилась без ошибок. В выводе остались CS0414 (существующее неиспользуемое поле) и NU1900 (недоступен сетевой источник аудита NuGet).

Проверка окон с реальной базой и полный цикл сохранения/открытия в PostgreSQL требуют проверки на рабочем экземпляре; в этой сессии они не выполнялись. Исходная база FoxPro и рабочие данные пользователя не изменялись.
