# План нормализации модели данных BIS.ERP — что делать и как сделать правильно

> Дата: 16.10.2026. Статус: план к исполнению, код не меняем этим документом.
> Связанный документ: `Docs/Анализ_структуры_таблиц_и_данных.md` (оценка 6.1/10).
> Цель: из «3 систем создания схемы + условные FK + дубли справочников» прийти к одной управляемой модели: EF — для ядра, MetadataService — только для `catalog_*/doc_*`, все связи — безусловные FK или явно запрещённые удаления.

## 0. Принципы целевой модели (читать перед шагами)

1. **Один путь создания схемы.** Статика — только EF Migrations. Динамика (`catalog_*`, `doc_*`) — только `MetadataService.CreateDynamicTableAsync`. Запретить `CREATE TABLE` в `EnsureSchemaAsync`, сидах, `RuntimeSchemaFixService` (оставить ему только роль проверки/дрейфа, не починки).
2. **Связи — фактами БД, а не договорённостями.** Каждый `*_lines.parent_id → doc_* NOT NULL ON DELETE CASCADE` — реальный FK. Каждая ссылка на справочник — либо FK, либо `RESTRICT` + проверка в сервисе. Никаких «если шапка существует, тогда FK».
3. **Имена и типы — канон.** `catalog_*` — справочники, `doc_*` — документы (шапка), `doc_*_lines` — строки, `reg_*`/`doc_postings` — регистры. PK — `uuid`, деньги — `numeric(18,2)`, даты проведения — `timestamptz`, GUID-ссылки — `uuid`, а не `text`.
4. **Сначала стоп-кран, потом красота.** Фазы идут от защиты данных (P0) к красоте (P2/P3). Нельзя начинать с индексов, пока сироты возможны.

### Целевая карта слоёв

```
ЯДРО (EF Migrations, статичные таблицы):
  Users, InfoBases, MetadataObjects/Fields/Calculations/PostingRules,
  MetadataModules/Items, Reports/*, AccountingPeriods/ModuleStates,
  AccountOpeningBalances, AccountTurnoverSnapshots, FinancialReportLines,
  TaxJournalRecords, LocalizationEntries, RegulatedReportTemplates

СПРАВОЧНИКИ (динамика, catalog_*):
  catalog_organizations (единственный!), catalog_plan_schetov,
  catalog_currencies, catalog_employees, catalog_assets, catalog_cash_desks...

ДОКУМЕНТЫ (динамика, doc_* + doc_*_lines):
  doc_sales_invoice + _lines(invoice_id), doc_purchase_invoice + _lines,
  doc_cash_orders, doc_advance_payment + _lines(advance_id),
  doc_payment_orders, doc_exchange_diff...

РЕГИСТРЫ (движения, только запись через проведение):
  doc_postings (центральный журнал), проводки СФ/кассы/п-п/авансов/курсовых
  + снимки/остатки (пересчёт, не ручной ввод)

ИМПОРТ (изолированно):
  DynamicDocuments + DynamicDocumentRows(Data jsonb), DbfMetadata
  LEGACY READ-ONLY: Document/DocumentRow/DocumentMovement, Organizations,
  Postings(static), Materials/FixedAssets(static) — пометить Obsolete, новых ссылок не делать
```

## Фаза 0. Инвентаризация и стоп-кран (0.5–1 день, без риска)

**Зачем:** нельзя чинить схему, не зная расхождение баз. У вас уже есть дрейф: одна база прошла `RenameDocumentTableAsync`, другая — нет.

**Шаги:**

0.1. Снять фактическую схему каждой боевой базы:
```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema='public' AND (table_name LIKE 'catalog\_%' OR table_name LIKE 'doc\_%')
ORDER BY 1;
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE connamespace='public'::regnamespace AND contype='f' ORDER BY 1;
SELECT indexname, indexdef FROM pg_indexes WHERE schemaname='public' ORDER BY tablename;
```

0.2. Найти сирот и дубли до любых миграций (только SELECT):
```sql
-- строки авансов без шапки (если FK нет — покажет проблему)
SELECT l.* FROM doc_advance_payment_lines l
LEFT JOIN doc_advance_payment h ON h."Id"=l.advance_id WHERE h."Id" IS NULL LIMIT 100;
-- то же для СФ
SELECT l.* FROM doc_sales_invoice_lines l
LEFT JOIN doc_sales_invoice h ON h."Id"=l.invoice_id WHERE h."Id" IS NULL LIMIT 100;
SELECT l.* FROM doc_purchase_invoice_lines l
LEFT JOIN doc_purchase_invoice h ON h."Id"=l.invoice_id WHERE h."Id" IS NULL LIMIT 100;
-- проводки на несуществующие документы (сигнал, не приговор — DocumentId полиморфен, см. 3.4)
SELECT p."Id", p."DocumentId", p."DocumentType" FROM doc_postings p LIMIT 100;
-- дубли имён таблиц в метаданных
SELECT "TableName", count(*) FROM "MetadataObjects" GROUP BY 1 HAVING count(*)>1;
SELECT "MetadataObjectId", "DbColumnName", count(*) FROM "MetadataFields" GROUP BY 1,2 HAVING count(*)>1;
```

0.3. Зафиксировать канон имён в `PROJECT_SCHEMA.md`: `catalog_*`, `doc_*`, `doc_*_lines(parent_id)`, `doc_postings`. Любое новое имя мимо канона — отклонять на ревью.

**Готово, когда:** есть выгрузка схемы 2+ баз, список сирот пуст или выписан, канон имён записан.

## Фаза 1. P0 — закрыть потерю данных (1–2 дня, наивысший приоритет)

### 1.1. Экранировать весь DDL (SQL-инъекция через имя таблицы)

**Проблема:** `RenameDocumentTableAsync` клеит `oldTable/targetTableName` из `MetadataObjects` (редактируется в конфигураторе) в `to_regclass('public.{oldTable}')` и `ALTER TABLE ""{oldTable}""`.

**Как правильно:**
- Никогда не конкатенировать идентификаторы. Только `format('... %I ...', var)` или `quote_ident(var)` в Postgres, `QuoteIdentifier()` в C# (уже есть в `AdvancePaymentService` — переиспользовать).
- Пример правильно:
```sql
DO $$ BEGIN
  IF to_regclass(format('public.%I', old_table_param)) IS NOT NULL THEN
    EXECUTE format('ALTER TABLE %I RENAME TO %I', old_table_param, new_table_param);
  END IF;
END $$;
```
- Файлы: сидинг метаданных (`EnsureFinanceDocumentTableNamesAsync`/`RenameDocumentTableAsync`), `MetadataService.CreateDynamicTableAsync`, патчи `.bispatch`.
- Проверка: вставить в имя тестового объекта кавычку/пробел — DDL обязан либо корректно отработать, либо отклонить имя валидацией `^[a-z][a-z0-9_]{0,60}$`.

### 1.2. Сделать FK безусловными (убрать «если шапка существует»)

**Проблема:** `AdvancePaymentService.EnsureSchemaAsync` добавляет `FK advance_id → шапка` только при `to_regclass(...) IS NOT NULL`. Порядок запуска решает наличие FK.

**Как правильно — 3 правила:**
1. Шапка создаётся раньше строк. Всегда. `EnsureDocumentTableAsync(шапка)` → затем `EnsureSchemaAsync(строки)`.
2. FK создаётся отдельной идемпотентной операцией `EnsureForeignKeyAsync`, которая дожимает старые базы:
```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='fk_adv_lines_header') THEN
    ALTER TABLE doc_advance_payment_lines
      ADD CONSTRAINT fk_adv_lines_header FOREIGN KEY (advance_id)
      REFERENCES doc_advance_payment("Id") ON DELETE CASCADE;
  END IF;
END $$;
```
3. Колонка-родитель — `uuid NOT NULL`, а не nullable text. Nullable parent = сироты по дизайну.

**Матрица FK (сделать все):**

| Строки | Родитель | FK | Удаление шапки |
|---|---|---|---|
| `doc_sales_invoice_lines.invoice_id` | `doc_sales_invoice."Id"` | `NOT NULL CASCADE` | строки уходят вместе |
| `doc_purchase_invoice_lines.invoice_id` | `doc_purchase_invoice."Id"` | `NOT NULL CASCADE` | то же |
| `doc_advance_payment_lines.advance_id` | `doc_advance_payment."Id"` | `NOT NULL CASCADE` | то же |
| `doc_fixed_asset_movement_lines.doc_id` | `doc_fixed_asset_movement` | `NOT NULL CASCADE` | то же |
| `ReportFields/ReportFilters/ReportGroups/ReportParameters/ReportElementMappings.ReportId` | `Reports."Id"` | уже `CASCADE` в EF — проверить физически в БД | — |
| `ReportDataSetFields.ReportDataSetId` | `ReportDataSets."Id"` | `CASCADE` | — |
| `MetadataFields/Calculations/PostingRules.MetadataObjectId` | `MetadataObjects."Id"` | `CASCADE` | — |

**Готово, когда:** повторный прогон сидинга на старой базе без шапки сам создаёт шапку + FK, запросы сирот из 0.2 возвращают 0 строк.

### 1.3. Запретить удаление справочника с живыми ссылками

**Проблема:** `catalog_organizations`, валюты, счета удаляются, а `doc_*`/`doc_postings` ссылаются строковым GUID через `::text` — БД не блокирует.

**Как правильно (два эшелона):**
- Эшелон БД: где тип колонки уже `uuid` — настоящий FK `ON DELETE RESTRICT`. Где `text` — сначала миграция типа (см. 3.3), затем FK.
- Эшелон сервиса: в диалоге удаления справочника перед `DELETE` выполнить `SELECT count(*) FROM doc_* WHERE org_id=:id` + `doc_postings`; если >0 — запрет с текстом «есть N документов/проводок», кнопка «Показать».
- Никогда `ON DELETE CASCADE` со справочника на документы — удаление контрагента не должно сносить СФ.

## Фаза 2. Один путь создания схемы (2–3 дня)

**Проблема:** статичные таблицы едут через EF Migrations, а `ReportDataSets/ReportDataSetFields`, `RegulatedReportTemplates`, `DeletedStandardReports` — через `EnsureSchemaAsync` сырым SQL. Плюс `RuntimeSchemaFixService` чинит старые базы `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` при каждом старте.

**Как правильно:**

2.1. Разделить ответственность раз и навсегда:
- `DbContext + Migrations` — владелец всех таблиц без префикса (`Reports`, `Metadata*`, `Accounting*`, `ReportDataSets`, `RegulatedReportTemplates`, ...).
- `MetadataService.CreateDynamicTableAsync` — владелец только `catalog_*` / `doc_*` / `doc_*_lines`.
- Всё остальное (`EnsureSchemaAsync` в отчётных сервисах, `RuntimeSchemaFixService`-починки, `CREATE TABLE` в сидах) — удалить после переноса в миграции.

2.2. Конкретно по файлам (порядок важен):
1. Добавить `DbSet` + конфигурацию для таблиц, которых нет в `AppDbContext`: `ReportDataSets`, `ReportDataSetFields` (уже есть — проверить маппинг), `RegulatedReportTemplates`, `DeletedStandardReports` (строковый PK `Code` — отдельная конфигурация `HasKey(e => e.Code)`).
2. `dotnet ef migrations add UnifyReportingSchema` → проверить SQL (`Script-Migration`) глазами: только `CREATE TABLE IF NOT EXISTS`-эквиваленты, без потери данных.
3. Прогнать миграцию на копии боевой базы. Сверить `pg_constraint`/`pg_indexes` до и после.
4. Удалить `EnsureSchemaAsync` из `ReportDataSetService`, `RegulatedReportTemplateService`, `StandardReportDeletionService`. Оставить один вызов `db.Database.MigrateAsync()` при старте.
5. `RuntimeSchemaFixService` перевести в режим «детектор дрейфа»: сравнивает ожидаемую схему с `information_schema`, пишет в `events`/лог, ничего не чинит молча. Починка — только миграцией.

2.3. Патчи `.bispatch` (AES-GCM, `schema.sql` + `metadata.json`): запретить в `schema.sql` всё, кроме `ADD COLUMN IF NOT EXISTS` и `CREATE INDEX IF NOT EXISTS` на динамических таблицах. Переименования таблиц — только через миграцию с бэкапом `FrxBackup_*/NativeBackup_*` по образцу `Docs/FRX_удаление_план_и_скрипты.md`.

**Готово, когда:** `grep -r "CREATE TABLE" Services/ --include=*.cs` возвращает только `MetadataService` (динамика) и тесты; запуск на пустой базе и на старой базе даёт одинаковую схему.

## Фаза 3. Справочники и документы — убрать дубли (3–5 дней)

### 3.1. Один справочник организаций: `catalog_organizations`

**Проблема:** статичная `Organizations` (модель `Models/Organization.cs`, `DbSet Organizations`) пуста (0 строк), а боевая — `catalog_organizations` с `is_primary/director/chief_accountant`. `Posting.OrganizationId → Organizations.Id` ведёт в пустоту, отчёты идут в `catalog_*` через `::text`.

**Как правильно:**
1. Объявить `Organization`, `Document/DocumentRow/DocumentMovement`, статичные `Posting/Material/FixedAsset` (там где боевым стал `catalog_*`) как `[Obsolete("Legacy, только чтение")]`. Запретить новые ссылки (ревью-правило).
2. Миграция переноса (если в `Organizations` вдруг есть строки): `INSERT INTO catalog_organizations SELECT ... WHERE NOT EXISTS`, затем сверка `count(*)`.
3. `DbSet Organizations` не удалять сразу (сломаются навигации `Posting.Organization`) — сначала переключить навигации на `Guid OrganizationRef` без FK (переходный этап), затем удалить таблицу миграцией.
4. То же для плана счетов: канон — `catalog_plan_schetov` (`Code UNIQUE`), `ChartOfAccount` — legacy. Для материалов/ОС — аудит: какой справочник боевой, второй — obsolete.

### 3.2. Канон колонок справочника и документа

Шапка `doc_*` обязана иметь минимум:
```
"Id" uuid PK DEFAULT gen_random_uuid(),
doc_number text NOT NULL, doc_date timestamptz NOT NULL,
organization_id uuid NULL REFERENCES catalog_organizations("Id") ON DELETE RESTRICT,
currency_id uuid NULL, amount numeric(18,2) NOT NULL DEFAULT 0,
is_posted boolean NOT NULL DEFAULT false, is_active boolean NOT NULL DEFAULT true,
created_at timestamptz NOT NULL DEFAULT now(), created_by text NULL,
row_version bigint NOT NULL DEFAULT 1
+ UNIQUE(doc_number, doc_date) там где нумерация в пределах дня/года
```
Строки `doc_*_lines`:
```
"Id" uuid PK, parent_id uuid NOT NULL REFERENCES doc_*("Id") ON DELETE CASCADE,
line_no int NOT NULL, account_code text, amount numeric(18,2),
+ UNIQUE(parent_id, line_no)
```

### 3.3. Типы: `uuid` вместо `text` для GUID, `numeric(18,2)` для денег, `timestamptz` для дат

Миграция типа безопасно (образец для каждой ссылки):
```sql
-- 1. чистка мусора
SELECT DISTINCT organization_id FROM doc_postings
WHERE organization_id IS NOT NULL AND organization_id !~ '^[0-9a-f-]{36}$' LIMIT 20;
-- 2. смена типа
ALTER TABLE doc_postings ALTER COLUMN organization_id TYPE uuid USING organization_id::uuid;
-- 3. FK
ALTER TABLE doc_postings ADD CONSTRAINT fk_postings_org
  FOREIGN KEY (organization_id) REFERENCES catalog_organizations("Id") ON DELETE RESTRICT;
-- деньги
ALTER TABLE "Postings" ALTER COLUMN "Amount" TYPE numeric(18,2);
```

### 3.4. Полиморфный `DocumentId` в проводках — оформить явно

**Проблема:** `Posting.DocumentId Guid` без FK, потому что указывает то в `doc_sales_invoice`, то в `doc_cash_orders`. Сейчас это «висячая» колонка.

**Как правильно (выбрать один вариант и держать):**
- Вариант А (рекомендую): `doc_postings(document_id uuid NOT NULL, document_table text NOT NULL CHECK (document_table LIKE 'doc\_%'), document_number text)` + составной индекс `(document_table, document_id)` + проверка в `PostingService`: перед вставкой проводки шапка обязана существовать (`SELECT 1 FROM <table> WHERE "Id"=:id`). Удаление проведённого документа запрещено пока есть проводки (сначала «распровести»).
- Вариант Б: отдельные таблицы проводок на документ — отвергнуть, ломает единый журнал.
- `TaxJournalRecord.SourceRecordId` — то же правило: пара `(SourceTable, SourceRecordId)`.

## Фаза 4. Индексы и уникальности (1 день, после FK)

**Проблема:** в `OnModelCreating` нет `HasIndex` для `Postings`, динамические таблицы без индексов — ОСВ/журнал за год идут Seq Scan.

**Как правильно — минимум:**

```csharp
modelBuilder.Entity<MetadataObject>().HasIndex(o => o.TableName).IsUnique();
modelBuilder.Entity<MetadataField>().HasIndex(f => new { f.MetadataObjectId, f.DbColumnName }).IsUnique();
modelBuilder.Entity<MetadataModule>().HasIndex(m => m.Code).IsUnique();
modelBuilder.Entity<ReportDataSetField>().HasIndex(f => new { f.ReportDataSetId, f.DbColumnName }).IsUnique();
```

```sql
CREATE INDEX IF NOT EXISTS ix_postings_doc ON doc_postings(document_table, document_id);
CREATE INDEX IF NOT EXISTS ix_postings_date ON doc_postings(doc_date);
CREATE INDEX IF NOT EXISTS ix_sales_lines_parent ON doc_sales_invoice_lines(invoice_id);
CREATE INDEX IF NOT EXISTS ix_purch_lines_parent ON doc_purchase_invoice_lines(invoice_id);
CREATE INDEX IF NOT EXISTS ix_adv_lines_parent ON doc_advance_payment_lines(advance_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_adv_lines ON doc_advance_payment_lines(advance_id, line_no);
```

**Проверка:** `EXPLAIN ANALYZE` журнала за год — Seq Scan на `doc_postings` обязан исчезнуть.

## Фаза 5. Метаданные — из строковых связей в проверяемые (2 дня)

5.1. Валидация при сохранении метаданных (в `MetadataService`, до DDL):
- `TableName` — regex `^(catalog|doc|reg)_[a-z][a-z0-9_]{0,60}$`, уникальность.
- `DbColumnName` — `^[a-z][a-z0-9_]{0,60}$`, уникальность в пределах объекта.
- `ReferenceCatalog` — обязан существовать в `MetadataObjects` с `ObjectType='Catalog'`.
- `BalanceTable/MovementTable` — обязаны существовать (`to_regclass`) или быть пустыми.
- `ReferenceFields` JSON — оба поля обязаны существовать в объекте.

5.2. `CreateDynamicTableAsync` — добавить проверку «колонка есть, но тип другой → миграция типа, а не пропуск».

5.3. `MetadataPostingRule` — проверять выражения на существующие поля объекта.

**Готово, когда:** нельзя сохранить метаданные со ссылкой на несуществующий справочник/поле.

## Фаза 6. Аудит, номера, безопасность (1–2 дня)

6.1. Аудит: к `doc_*` и `doc_postings` добавить `created_by`, `updated_at`, `row_version bigint DEFAULT 1`. Физ. `DELETE` из журнала запретить, документы — только через «распровести → пометить».
6.2. Номера: `UNIQUE(doc_number)` или `UNIQUE(doc_number, doc_date)` + выдача в транзакции (`SELECT ... FOR UPDATE`).
6.3. Даты: проведение — `timestamptz`, дата документа — `date`. `DateTime.UtcNow` только для `created_at`.
6.4. Секреты: `InfoBase.Password` шифровать (DPAPI), в логах — без пароля.

## Фаза 7. Приёмка — SQL-контроль (0.5 дня)

```sql
SELECT count(*) FROM doc_advance_payment_lines l LEFT JOIN doc_advance_payment h ON h."Id"=l.advance_id WHERE h."Id" IS NULL;
SELECT count(*) FROM doc_sales_invoice_lines l LEFT JOIN doc_sales_invoice h ON h."Id"=l.invoice_id WHERE h."Id" IS NULL;
SELECT count(*) FROM (SELECT "TableName" FROM "MetadataObjects" GROUP BY 1 HAVING count(*)>1) d;
SELECT document_table, count(*) FROM doc_postings GROUP BY 1;
SELECT sum(debit)-sum(credit) FROM doc_postings WHERE doc_date BETWEEN :p1 AND :p2;
```

Плюс функционально: СФ → провести → журнал → открыть двойным кликом → распровести → удалить; удаление контрагента с документами (отказ); переименование с кавычкой (отказ); параллельная выдача номеров (без дублей).

## Порядок и оценка

| Фаза | Срок | Риск |
|---|---|---|
| 0. Инвентаризация | 0.5–1 д | нет |

| 2. Один путь схемы | 2–3 д | средний |
