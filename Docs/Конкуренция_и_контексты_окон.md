# Конкуренция запросов и контекст на окно: счёт-фактуры и финансы

Документ фиксирует, почему у партнёров при тестировании выскакивали ошибки
параллельных запросов, что переведено на отдельные подключения в модулях
«Счёт-фактуры» и «Финансы» и каким кодом это сделано.

Дата: 29.10.2026. Версия на момент работ: `1.1.76x`.

Связанные документы:

- `Docs/Конкуренция - AccountingPeriodService.pdf` — разбор перевода
  `AccountingPeriodService` на `IAppDbContextFactory`;
- `Docs/Ошибка_DbContext_в_редакторе_модулей.md` — почему общий `DbContext`
  нельзя использовать из двух async-потоков;
- `Docs/Отчёт_2026-10-16.md` — история с общими воротами `DbContextGate`
  и решение переходить на контекст на операцию/окно.

---

## 1. Симптом

Партнёры при тестировании получают ошибки вида:

```
System.InvalidOperationException: A second operation was started on this context
instance before a previous operation completed. ...
Npgsql.NpgsqlOperationInProgressException: A command is already in progress
```

Ошибки появляются не в одном конкретном месте, а когда в MDI открыто несколько
вкладок и они одновременно грузят данные, либо когда диалог открывается поверх
загружающегося списка.

Это не конкуренция в PostgreSQL: сервер прекрасно переносит параллельные запросы
с **разных соединений**. Падает клиент — EF Core и Npgsql запрещают две команды
на **одном** `DbContext`/соединении.

---

## 2. Причина

`MainWorkWindow` создаёт **один** `AppDbContext` и **один** `MetadataService`
и раздаёт его всем вкладкам:

```csharp
var context = await _infoBaseManager.GetCurrentDbContextAsync();
_metadataService = new MetadataService(context);
…
var invoiceView = new InvoiceWorkView(invoiceDocument, _metadataService);
var financeView = new FinanceDocumentWorkView(financeDocument, _metadataService);
var cashOrderView = new CashOrderWorkView(cashOrderDocument, _metadataService);
var paymentView = new PaymentOrderWorkView(paymentDocument, _metadataService);
var postingsView = new PostingsView(postingsDocument, _metadataService);
```

Дальше это же сервис уходит в диалоги:

```csharp
var dialog = new InvoiceEditDialog(_documentMetadata, _metadataService, _invoiceService);
var dialog = new FinanceDocumentDialog(_documentMetadata, _metadataService);
var dialog = new PaymentOrderDialog(_documentMetadata, _metadataService);
var dialog = new CashOrderDialog(_documentMetadata, _metadataService, orderKind);
```

Проблема проявляется, когда на одном контексте накладываются две операции:

| Что накладывается | Пример |
|---|---|
| Загрузка двух вкладок | пользователь открыл «Счёт-фактуры» и «Платёжные поручения», обе вкладки получили `Loaded` |
| Загрузка списка и строк | смена выделения в списке, пока идёт `LoadData` (оба на `_invoiceService`) |
| Диалог и список | диалог открыт и грузит справочники, а вкладка под ним перезагружается |
| `Task.Run` в диалоге | `CashOrderDialog` и `PaymentOrderDialog` грузят данные в фоне (`Task.Run(...)`) |
| `async void`-обработчики | повторный `Loaded`/клик, пока предыдущая загрузка не завершилась |

Одинаковые вкладки получают один и тот же объект — EF отвечает
`A second operation was started…`, Npgsql — `A command is already in progress…`.

---

## 3. Решение

Правило: **одно окно/диалог — одно подключение**. Контекст создаётся на окно
(а не на всё приложение), живёт, пока окно открыто, и не делится с другими окнами.

Почему не «контекст на каждую операцию» сразу:

- в проекте уже есть частичный перевод на `IAppDbContextFactory`
  (`AccountingPeriodService`, отчёты), но полный переход — отдельный крупный этап
  (34 сервиса, 61 точка в окнах, см. `Docs/Отчёт_2026-10-16.md`);
- «контекст на окно» даёт главный эффект — окна перестают ронять друг друга —
  при небольшом и обратимом изменении;
- дальше окна можно переводить на контекст-на-операцию по одному, не ломая всё сразу.

Важно: новое подключение — это **не новое TCP-соединение**. Npgsql держит пул,
поэтому `new AppDbContext(connectionString)` дешёвый, а параллелизм окон реальный.

---

## 4. Код

### 4.1. `Services/MetadataService.cs` — независимый экземпляр сервиса

Метод `CreateIndependentContext()` был приватным (использовался внутри сервиса).
Он стал публичным, и рядом появился `CreateIndependent`:

```csharp
/// <summary>
/// Безопасное создание независимого контекста для изоляции параллельных запросов.
/// Каждый вызов возвращает НОВОЕ короткоживущее соединение, чтобы исключить
/// ошибку "A command is already in progress" при одновременном чтении/записи.
/// </summary>
public AppDbContext CreateIndependentContext()
{
    // Если есть фабрика — используем её (безопасно и контролируемо через DI).
    if (_contextFactory != null)
        return _contextFactory.CreateDbContext();

    if (!string.IsNullOrEmpty(_connectionString))
    {
        return new AppDbContext(_connectionString);
    }

    // Фолбэк: собственное соединение на основе строки подключения текущего контекста.
    var connString = _context?.Database.GetConnectionString()
        ?? AppSettings.Instance.GetMasterConnectionString();
    return new AppDbContext(connString);
}

/// <summary>
/// Экземпляр сервиса на СВОЁМ подключении (окно, диалог, фоновая задача).
///
/// Окна и диалоги не должны делить один контекст: он не переносит параллельных
/// команд, и одно окно ловит «A second operation was started on this context
/// instance…» из-за загрузки в другом окне. Своё подключение даёт окнам
/// независимость и позволяет им действительно работать параллельно.
///
/// Контекст живёт столько же, сколько окно/диалог. Вызывающий может получить
/// его же через <see cref="CreateIndependent(out AppDbContext)"/>, чтобы
/// построить на этом подключении другие сервисы (например, InvoiceService).
/// </summary>
public MetadataService CreateIndependent(out AppDbContext context)
{
    context = CreateIndependentContext();
    return _contextFactory == null
        ? new MetadataService(context)
        : new MetadataService(context, _contextFactory);
}

/// <summary>То же, что <see cref="CreateIndependent(out AppDbContext)"/>, без контекста.</summary>
public MetadataService CreateIndependent() => CreateIndependent(out _);
```

Строка подключения берётся из текущего контекста (`_connectionString`), поэтому
матчить базу вручную не нужно: окно продолжает работать с той же инфобазой.

### 4.2. Окна (вкладки MDI)

В каждом конструкторе — одна строка. Поле `_metadataService` остаётся `readonly`,
меняется только то, что в него кладут **свой** экземпляр, а не общий.

`Views/InvoiceWorkView.xaml.cs`:

```csharp
_documentMetadata = documentMetadata;
// Своё подключение: вкладки MDI не должны делить контекст — иначе
// загрузка одного окна роняет запросы другого («A second operation…»).
_metadataService = metadataService.CreateIndependent();
```

`Views/FinanceDocumentWorkView.xaml.cs`:

```csharp
_documentMetadata = documentMetadata;
// Своё подключение на вкладку: контекст не переносит параллельных команд.
_metadataService = metadataService.CreateIndependent();
```

`Views/PaymentOrderWorkView.xaml.cs` — то же:

```csharp
_documentMetadata = documentMetadata;
_metadataService = metadataService.CreateIndependent();
```

`Views/CashOrderWorkView.xaml.cs` — то же:

```csharp
_documentMetadata = documentMetadata;
_metadataService = metadataService.CreateIndependent();
```

`Views/PostingsView.xaml.cs` — то же:

```csharp
_document = document;
// Своё подключение на вкладку: контекст не переносит параллельных команд.
_metadataService = metadataService.CreateIndependent();
```

### 4.3. Диалоги

`Views/Dialogs/FinanceDocumentDialog.xaml.cs` (оба конструктора):

```csharp
_document = document;
// Диалог работает на своём подключении: окно-список может перезагружаться
// одновременно, а один контекст параллельных команд не переносит.
_metadataService = metadataService.CreateIndependent();
```

`Views/Dialogs/PaymentOrderDialog.xaml.cs` (оба конструктора) и
`Views/Dialogs/CashOrderDialog.xaml.cs` (три конструктора):

```csharp
_document = document;
// Своё подключение: загрузка идёт в Task.Run, контекст окна делить нельзя.
_metadataService = metadataService.CreateIndependent();
```

`Views/Dialogs/InvoiceEditDialog.xaml.cs` — здесь диалогу нужен не только
`MetadataService`, но и `InvoiceService`, поэтому оба строятся на **одном**
новом подключении:

```csharp
_document = document;
ApplyAccountFieldLabels();

// Диалог работает на своём подключении: окно-список и другие вкладки
// могут грузиться одновременно, а один контекст параллельных команд
// не переносит («A second operation was started…»). InvoiceService
// строится на том же подключении, чтобы диалог был сам с собой
// последовательным. Параметр invoiceService оставлен для совместимости
// вызовов — его состояние (Configure) здесь выставляется заново.
_metadataService = metadataService.CreateIndependent(out var dialogContext);
_invoiceService = new InvoiceService(dialogContext);
_invoiceService.Configure(document);

_editId = editId;
```

Почему `InvoiceService` пересоздаётся, а не берётся переданный: переданный
принадлежит окну-списку (у него своё подключение). Если диалог будет писать
через него, окно и диалог снова начнут делить контекст.

### 4.4. «Счёт-фактуры»: последовательность внутри окна

У `InvoiceWorkView` остаётся один общий на окно `InvoiceService` (своё подключение),
но его методы могут наложиться: загрузка списка, смена выделения (строки документа)
и удаление. Поэтому добавлены «ворота» окна — **свой** семафор, не глобальный
`DbContextGate` (глобальный дал бы взаимоблокировку с сервисом, см. отчёт 16.10):

```csharp
/// <summary>
/// Последовательный доступ к _invoiceService: загрузка списка и выбор строки
/// (строки счёта-фактуры) могут наложиться друг на друга — у сервиса одно
/// подключение, параллельные команды оно не переносит.
/// </summary>
private readonly System.Threading.SemaphoreSlim _invoiceGate = new(1, 1);
private bool _isLoadingInvoices;
```

Загрузка списка:

```csharp
private async Task LoadDataAsync()
{
    if (_invoiceService == null || _isLoadingInvoices)
        return;

    await _invoiceGate.WaitAsync();
    _isLoadingInvoices = true;
    try
    {
        StatusText.Text = "Загрузка...";
        var postedCount = await _invoiceService.EnsureSavedInvoicesPostedAsync();
        var invoices = await _invoiceService.GetInvoicesAsync();
        …
    }
    catch (Exception ex)
    {
        StatusText.Text = "Ошибка загрузки";
        MessageBox.Show($"Ошибка загрузки: {ex.Message}", "Ошибка", MessageBoxButton.OK, MessageBoxImage.Error);
    }
    finally
    {
        _isLoadingInvoices = false;
        _invoiceGate.Release();
    }
}
```

Смена выделения (строки документа):

```csharp
await _invoiceGate.WaitAsync();
try
{
    LinesGrid.ItemsSource = await _invoiceService.GetLinesAsync(selected.Id);
}
finally
{
    _invoiceGate.Release();
}
```

Удаление (сначала удалить под воротами, потом перезагрузить список — `LoadDataAsync`
сам берёт те же ворота, поэтому внутри них перезагрузку не вызываем):

```csharp
await _invoiceGate.WaitAsync();
try
{
    await _invoiceService.DeleteInvoiceAsync(selected.Id);
}
finally
{
    _invoiceGate.Release();
}

await LoadDataAsync();
```

Заодно `OnLoaded` больше не создаёт сервис/контекст **на каждое** появление вкладки
(раньше это был лишний контекст на каждое переключение):

```csharp
private async void OnLoaded(object sender, RoutedEventArgs e)
{
    if (_invoiceService == null)
    {
        var context = await ServiceLocator.InfoBaseManager.GetCurrentDbContextAsync();
        await new InvoiceMetadataSeedService(context).EnsureAsync();
        _invoiceService = new InvoiceService(context);
        _invoiceService.Configure(_documentMetadata);
        await _invoiceService.EnsureSchemaAsync();
        _invoiceEsfExchangeService = new InvoiceEsfExchangeService(context, _invoiceService);
    }

    await LoadDataAsync();
}
```

### 4.5. «Проводки»: защита от повторного `Loaded`

`Views/PostingsView.xaml.cs`: `Loaded` может сработать повторно (переприкрепление
вкладки MDI), а загрузка идёт на своём контексте. Добавлен флаг:

```csharp
private bool _isLoading;

private async Task LoadData()
{
    if (_isLoading)
        return;

    _isLoading = true;
    try
    {
        …
    }
    finally
    {
        _isLoading = false;
    }
}
```

### 4.6. Где взяли контекст «по образцу»

В проекте уже были места, которые открывают своё подключение на операцию —
на них и опирались:

```csharp
var context = await ServiceLocator.InfoBaseManager.GetCurrentDbContextAsync();
var postingService = new PostingService(context);
…
```

`GetCurrentDbContextAsync()` каждый раз возвращает **новый** `AppDbContext`
(одноимённый метод в `InfoBaseManager`), поэтому такой код уже безопасен.
Проблема была только у окон/диалогов, которые получали общий сервис.

---

## 5. Почему это ещё и быстрее

1. **Окна больше не блокируют друг друга.** Раньше все вкладки работали через
   один контекст: пока одна грузится, вторая ждёт или падает. Теперь у каждой
   своё подключение — загрузки идут параллельно.
2. **Нет лишнего создания контекстов при переключении вкладок.** `InvoiceWorkView`
   раньше на каждый `Loaded` создавал новый `InvoiceService`/контекст; теперь —
   один раз.
3. **Меньше глобальных ворот.** `DbContextGate` остаётся для записи (изменения
   метаданных, схемы), но чтения разных окон больше не сериализуются.
4. **Пул соединений.** Npgsql переиспользует соединения, поэтому «свой контекст
   на окно» не увеличивает число TCP-подключений к удалённой базе.

запущенное приложение держит `bin\Debug\net8.0-windows\BIS.ERP.exe`).

код `concurrency-isolation`:

- создаёт корневой `MetadataService` (как `MainWorkWindow`);

## 7. Что осталось

1. **Освобождать контексты окон/диалогов.** Сейчас контекст живёт до сборки
   мусора: `MetadataService` не реализует `IDisposable`. Варианты:
   - сделать `MetadataService` владельцем контекста (`CreateIndependent` ставит
     флаг «мой») и вызывать `Dispose()` в `Closed` диалога и при закрытии вкладки;
   - либо перевести окна на `await using var db = await factory.CreateAsync()`
     внутри каждой операции (канон EF Core).
2. **Перевести остальные окна** тем же приёмом: справочники (`CatalogDataView`),
   отчёты (`AccountingReportsView`, `ReportPreviewWindow`), конфигуратор.
   Правило то же: окно/диалог не получает общий `MetadataService`, а создаёт
   свой (`CreateIndependent`) или контекст на операцию.
3. **Долгоживущие сервисы** (`MetadataService`, `InvoiceService`, `PostingService`)
   в перспективе — на `IAppDbContextFactory`, как `AccountingPeriodService`
   в `Docs/Конкуренция - AccountingPeriodService.pdf`. Тогда «контекст на окно»
   станет «контекст на операцию» и ворота `DbContextGate` можно будет убрать.
4. **Общий `_metadataService` в `MainWorkWindow`** пока остаётся для навигации и
   тех окон, которые ещё не переведены. Переведённые окна его игнорируют —
   параметр конструктора сохранён для совместимости вызовов.
