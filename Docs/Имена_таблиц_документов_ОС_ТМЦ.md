# Имена таблиц документов ОС и ТМЦ — канон и приведение в порядок

**Дата:** 20.10.2026
**Область:** `doc_asset_*` (модуль `FixedAssets`), `doc_inventory_*` (модуль `Inventory`)
**Единственный источник истины в коде:** `Services/DocumentTableNames.cs`

---

## 1. Правило

| Что | Шаблон | Пример |
|---|---|---|
| Шапка документа ОС | `doc_asset_<смысл>` | `doc_asset_purchase` |
| Шапка документа ТМЗ | `doc_inventory_<смысл>` | `doc_inventory_incoming` |
| Строки документа | `<имя шапки>_lines` | `doc_inventory_incoming_lines` |
| Первичный ключ | `<имя таблицы>_pkey` | `doc_inventory_incoming_pkey` |

Запрещено:

* `doc_asset_<12 hex>` и `doc_inventory_<12 hex>` — хеш-имена (решение от 17.10.2026, `Docs/План_нормализации_модели_данных.md` §0.3);
* `doc_incoming` / `doc_outgoing` — имена вне префикса модуля (исторический случай, подлежит переименованию);
* русские имена и пробелы в идентификаторах.

Смысловая часть — английская, snake_case, без сокращений, которые не читаются однозначно (`receipt`, `issue`, `transfer`, `assignment`, `writeoff`).

## 4. Как старые имена приводятся к канону

Три независимых механизма, все идемпотентны.

### 4.1 Что не сработало 20.10.2026 (диагностика)

Два независимых дефекта:

1. **EF-миграция не применяется к существующим базам.** `Database.MigrateAsync()` вызывается только в `InfoBaseManager.CreateInfoBaseAsync` — при создании новой инфобазы. Открытие существующей базы идёт через `RuntimeSchemaFixService` → `SchemaMigrationService` (журнал `schema_migrations`), поэтому записи `20261020101500_...` в `__EFMigrationsHistory` и не появилось.
2. **Runtime-нормализатор падал на первом же документе:** `42703: столбец "p0" не существует`. Параметры (`@p0`) внутри `DO $$ ... $$` не подставляются: тело блока — это строка, и PL/pgSQL читает `@p0` как обращение к колонке `p0`. Ошибка глушилась в `catch` и попадала в лог строкой «Не удалось привести имена таблиц документов ОС/ТМЦ к канону».

Обе причины устранены: DDL теперь собирается через `format('%I')` в обычном SELECT и выполняется отдельной командой, а нормализация зарегистрирована шагом в `SchemaMigrationService` — он выполняется при каждом открытии базы.

### 4.2 Шаг `SchemaMigrationService` `2026.10.20.01` — основной механизм

* Версия `2026.10.20.01`, **разовый** шаг (`Repeatable = false`): после успешного прогона фиксируется в `schema_migrations` и больше не выполняется. Если прогон упал — запись не создаётся, и шаг повторится при следующем открытии.
* Журнал: таблица `schema_migrations` (не `__EFMigrationsHistory`).
* Вызов: `RuntimeSchemaFixService.EnsureAsync()` → `SchemaMigrationService.EnsureAsync()` при открытии рабочего окна (`MainWorkWindow.xaml.cs:458`) — до сидинга документации.
* Логика: `DocumentTableNameNormalizer` — идёт по реестру, переименовывает таблицу, **сразу** фиксирует `MetadataObjects.TableName`, затем PK в `<таблица>_pkey`.
* Ошибка одного документа не блокирует остальные: она возвращается как `SkippedReason` и пишется в лог (`Migration`, `doc-names`).

Проверка:

```sql
select version, description, applied_at, last_run_at, runs
from schema_migrations
order by version desc
limit 5;
```

У разового шага `applied_at = last_run_at`, `runs = 1`. Если `runs` растёт — значит шаг падает и повторяется при каждом входе: смотреть лог `Миграция 2026.10.20.01 … не выполнена`.

### 4.3 EF-миграция `20261020101500_NormalizeDocumentTableNames`

Нужна для баз, которые проходят через `Database.MigrateAsync()`: создание новой инфобазы и любое будущее применение миграций. На уже открытых базах не выполняется — см. 4.1.

* Идёт по списку 24 документов, находит запись в `MetadataObjects` по имени.
* Если `TableName` уже канонический — пропускает.
* Если физическая таблица есть, а целевой нет — `ALTER TABLE ... RENAME TO`, затем переименование PK в `<таблица>_pkey`.
* Если таблицы нет — правит только метаданные (следующее создание пойдёт под каноническим именем).
* Если существуют **обе** таблицы — не делает ничего и пишет `NOTICE`: отвязывать метаданные от таблицы с данными нельзя автоматически.
* `Down()` — no-op: хеш-имена невосстановимы, откат создал бы ложное впечатление обратимости.
* Список в миграции — **снимок на 20.10.2026**; источник истины — реестр `DocumentTableNames`, его использует шаг 4.2.

### 4.4 Runtime-нормализатор из сидинга

Дополнительно вызывается в `DocumentationMetadataSeedService.EnsureAsync()` — конфигуратор, тесты и сценарии, где `RuntimeSchemaFixService` не вызывался. На нормальной базе это no-op, потому что шаг 4.2 уже всё сделал.

Покрытие:

| Сценарий | EF-миграция | Шаг 4.2 | Сидинг 4.4 | Скрипт 4.5 |
|---|---|---|---|---|
| Новая база | да (no-op) | да (no-op) | да (no-op) | — |
| Существующая база, вход в приложение | нет | **да** | да (no-op) | — |
| Копия без входа в приложение | нет | нет | нет | **да** |
| База с обеими таблицами | NOTICE | warning в лог | warning в лог | NOTICE |

### 4.5 Автономный скрипт `Docs/normalize_doc_table_names.sql`

Тот же DO-блок для ручного прогона в любой базе — когда не сработали ни миграция,
ни старт приложения (восстановленная копия, база на другом сервере, проверка перед
переключением). В конце скрипта — три контрольных SELECT: документы и их таблицы,
остатки хеш-имён, сверка метаданных с физическими таблицами.

```
psql -h localhost -p 5432 -U postgres -d <база> -f normalize_doc_table_names.sql
```

## 5. Конфликты и ручное вмешательство

| Ситуация | Поведение | Что делать |
|---|---|---|
| `doc_incoming` и `doc_inventory_incoming` существуют одновременно | обе остаются, метаданные не меняются, пишется предупреждение | сравнить `count(*)`, перенести данные вручную, лишнюю таблицу удалить, повторить вход |
| Метаданные указывают на несуществующую таблицу | `TableName` переводится на канон, таблица создастся позже | ничего |
| Документ переименован пользователем в конфигураторе | имя не найдено в реестре — документ не нормализуется | добавить имя в `DocumentTableNames` либо вернуть штатное имя |
| Хеш-имя в базе, которой нет в списке | не трогается | добавить пару в реестр и в миграцию |

Диагностика — журнал приложения (`logs/system_*.log`), источник `DocumentationMetadataSeedService`, строки `doc-names` / `->`.

## 6. Проверка

```sql
-- 1. Все документы ОС/ТМЦ и их таблицы (ожидаем канон)
SELECT "Name", "TableName"
FROM "MetadataObjects"
WHERE "ObjectType" = 'Document'
  AND ("TableName" LIKE 'doc\_asset\_%' OR "TableName" LIKE 'doc\_inventory\_%'
       OR "TableName" IN ('doc_incoming', 'doc_outgoing'))
ORDER BY "Name";

-- 2. Остались ли хеш-имена
SELECT "Name", "TableName"
FROM "MetadataObjects"
WHERE "TableName" ~ '^doc_(asset|inventory)_[0-9a-f]{12}$';

-- 3. Сверка метаданных с физическими таблицами
SELECT m."Name", m."TableName",
       (to_regclass(format('public.%I', m."TableName")) IS NOT NULL) AS table_exists
FROM "MetadataObjects" m
WHERE m."ObjectType" = 'Document'
  AND m."TableName" LIKE 'doc\_%'
ORDER BY table_exists, m."Name";

-- 4. Имена PK (ожидаем <таблица>_pkey)
SELECT c.relname AS table_name, con.conname AS pk_name
FROM pg_constraint con
JOIN pg_class c ON c.oid = con.conrelid
WHERE con.contype = 'p' AND c.relname LIKE 'doc\_asset\_%' OR c.relname LIKE 'doc\_inventory\_%'
ORDER BY 1;
```

Ожидаемый результат после нормализации: запрос 2 — 0 строк; запрос 3 — `table_exists = true` для всех существующих документов; запрос 4 — имена по шаблону `<таблица>_pkey`.

## 7. Границы этого шага

Сделано только **имяведение**:

* реестр и константы,
* автоматическое переименование существующих таблиц (шаг `SchemaMigrationService` + EF-миграция + runtime-вызов при сидинге + SQL-скрипт),
* переименование таблицы строк движения ОС в `doc_asset_movement_lines`,
* создание новых документов ТМЦ сразу под каноническими именами.

**Не сделано и относится к следующему шагу («архитектура данных»):**

* документы ОС по-прежнему **не создаются** — нет 17 объектов метаданных и таблиц;
* нет решения по табличным частям (`<шапка>_lines`) для остальных документов;
* нет остатков и складского учёта ТМЦ;
* не решено, применяются ли миграции при открытии существующей инфобазы.
