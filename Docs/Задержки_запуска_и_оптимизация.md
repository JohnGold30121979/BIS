# Задержки запуска на удалённой базе: замеры и что сделано

Документ фиксирует, почему BIS.ERP медленно открывал информационную базу по VPN,
как это измерялось, что именно исправлено и какие цифры получились.
Все числа — из реальных логов приложения (`logs/system_20261022.log`).

Дата: 22.10.2026.

---

## 1. Исходная жалоба

- База удалённая, доступ через VPN.
- Дерево конфигуратора строилось «долго», при нажатии кнопки вылетало
  `Npgsql.NpgsqlOperationInProgressException: A command is already in progress`.
- Субъективно запуск занимал около 10 секунд и больше.

Замеры показали: **27,6 секунды** на первом замере, из них 20 секунд — один этап.

---

## 2. Как измеряли

Добавлен `Services/StartupProfiler.cs`. Каждый этап запуска оборачивается в замер:

```csharp
await StartupProfiler.MeasureAsync("Посадка документации",
    () => new DocumentationMetadataSeedService(context).EnsureAsync());
```

В системный лог пишется строка:

```
2026-10-22 08:58:28.348	Warning	Admin	Startup	⏱ Посадка документации: 6639 мс (с запуска 10710 мс)
```

Правила чтения:

- `⏱ <этап>: <мс> мс` — длительность самого этапа;
- `(с запуска N мс)` — накопительное время от старта приложения;
- этапы **≥ 1000 мс** пишутся уровнем `Warning`, чтобы их было видно без фильтрации;
- остальные — `Info`.

Замеры стоят в двух местах:

| Окно | Этапы |
|---|---|
| `MainWorkWindow` | Схема и миграции, Предустановленные справочники, Посадка документации, Посадка счетов-фактур, Печатные формы (2), Стандартные отчёты, Дерево навигации |
| `ConfiguratorWindow` | Схема и миграции, Посадка документации, Посадка счетов-фактур, Печатные формы (2), Стандартные отчёты |

Дерево измеряется по наборам отдельно: метаданные, модули, состав модулей, отчёты, порядок групп.

## 4. Что тормозило и что сделано

### 4.1. `NpgsqlOperationInProgressException` при работе с базой

**Причина.** `DocumentationMetadataSeedService.GetActualColumnTypeAsync` выполнял
команду `SELECT data_type FROM information_schema.columns …` **на соединении EF-контекста**.
В этот момент на том же соединении уже шёл другой запрос (посадка метаданных), поэтому
Npgsql выбрасывал «A command is already in progress». Проявлялось при нажатии кнопок
во время загрузки — то есть ровно тогда, когда пользователь начинает работать.

**Сделано.** `Services/DatabaseSchemaCache.cs` — снимок схемы читается **один раз
на отдельном соединении** (`new NpgsqlConnection`), а не на общем:

```csharp
await using var connection = new NpgsqlConnection(connectionString);
await using var command = connection.CreateCommand();
command.CommandText = @"
    SELECT table_name, column_name, data_type, is_nullable, column_default
    FROM information_schema.columns
    WHERE table_schema = 'public'";
```

Дальше все сервисы (`SchemaRepairService`, `MetadataSchemaRepairService`,
`DocumentationMetadataSeedService`) берут данные из этого снимка.
В соединение EF сервисы больше не вмешиваются — гонка невозможна по построению.

Дополнительно снимок кэширует `is_nullable` и `column_default`, что дало следующий пункт.

### 4.2. Достройка колонок: 2–3 команды на каждое поле

**Причина.** `EnsureColumnNullableAsync` для каждого поля выполнял:

```sql
ALTER TABLE ... ALTER COLUMN ... DROP NOT NULL;
UPDATE ... SET ... = '' WHERE ... IS NULL;
ALTER TABLE ... ALTER COLUMN ... SET DEFAULT '';
```

…даже когда колонка **уже была** в нужном состоянии. Полей сотни → сотни round-trip'ов
по VPN по 30–70 мс каждый. Именно это и съедало 20 секунд.

**Сделано.** Ранний выход по данным снимка схемы:

```csharp
if (field.IsRequired && !info.IsNullable)
    return;          // уже NOT NULL — делать нечего

if (!field.IsRequired && info.IsNullable)
    return;          // уже nullable — делать нечего
```

Если состояние не совпадает — выполняется изменение, и снимок обновляется
(`_schemaCache.SetColumn(...)`), чтобы не перечитывать схему.

### 4.3. Колонки таблиц строк: `ALTER` в цикле

**Причина.** `InventoryDocumentSchemaService.EnsureLinesTablesAsync` добавлял
недостающие колонки по одной:

```csharp
foreach (var (column, columnDefinition) in InventoryDocumentModel.LineColumns)
    await _context.Database.ExecuteSqlRawAsync($"ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...");
```

**Сделано.** Одна команда на таблицу:

```csharp
var addedColumns = InventoryDocumentModel.LineColumns
    .Select(pair => $"ADD COLUMN IF NOT EXISTS {QuoteIdentifier(pair.Column)} {pair.Definition}")
    .ToList();

await _context.Database.ExecuteSqlRawAsync(
    $"ALTER TABLE public.{lines} {string.Join(", ", addedColumns)};");
```

### 4.4. Ошибка `42710`: ограничение уже существует

**Причина.** Проверка перед созданием внешнего ключа искала имя
`doc_inventory_incoming_lines_header`, а реальное имя — `fk_doc_inventory_incoming_lines_header`.
Проверка не срабатывала, `ADD CONSTRAINT` выполнялся каждый запуск и падал:

```
42710: ограничение "fk_doc_inventory_incoming_lines_header"
для отношения "doc_inventory_incoming_lines" уже существует
```

**Сделано.** Проверка по реальному имени и по таблице:

```sql
IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'fk_{definition.LinesTable}_header'
      AND conrelid = 'public.{definition.LinesTable}'::regclass) THEN
```

После исправления строка об ошибке из лога исчезла.

### 4.5. Стандартные отчёты: до трёх запросов на каждое определение

**Причина.** `EnsureStandardReportsAsync` в цикле по десяткам определений делал:

- запрос источника (`MetadataObjects` + `Fields`) по имени и типу;
- запрос отчёта по коду;
- запрос отчёта по имени (устаревшие коды).

**Сделано.** Два запроса на весь этап + поиск в памяти:

```csharp
var existingReports = await _context.Reports.ToListAsync();
var reportSources = await _context.MetadataObjects
    .AsNoTracking()
    .Include(metadata => metadata.Fields)
    .ToListAsync();

foreach (var definition in BuildStandardReportDefinitions() ...)
    await EnsureStandardReportAsync(definition, existingReports, reportSources);
```

`FindExistingStandardReportAsync` заменён на синхронный поиск по списку
`FindExistingStandardReport(definition, existingReports)`; новый отчёт сразу
добавляется в список, чтобы следующие определения его видели.

### 4.6. Дерево: последовательные запросы и N+1 по порядку групп

**Причина.**

- дерево читалось через сервисы, построенные на общем `_context` — он в это время
  занят другими операциями;
- пять независимых наборов грузились последовательно;
- порядок групп навигации запрашивался **отдельно для каждого модуля**
  (`GetNavigationGroupOrdersAsync(module.Id)`).

**Сделано.**

1. Каждый набор читается на своём подключении:

```csharp
private static async Task<T> LoadWithIndependentConnectionAsync<T>(Func<AppDbContext, Task<T>> load)
{
    await using var context = await ServiceLocator.InfoBaseManager.GetCurrentDbContextAsync();
    return await load(context);
}
```

2. Пять наборов грузятся параллельно (`Task.WhenAll`) — по VPN задержки складываются
   не в сумму, а в максимум.
3. Добавлен `ModuleMetadataService.GetAllNavigationGroupOrdersAsync()` — один запрос
   на все модули вместо запроса на каждый.

### 4.7. Посадки выполнялись при каждом запуске

**Причина.** `DocumentationMetadataSeedService`, `InvoiceMetadataSeedService` и
`MetadataService.EnsureStandardReportsAsync` идемпотентны, но запускались **каждый раз**,
хотя всё уже создано. Это 6,6 + 1,1 + 2,4 секунды впустую на каждой загрузке.

**Сделано.** `Services/SeedStateService.cs` — отметка о выполнении в таблице
`schema_migrations` (она уже используется механизмом миграций):

```
seed.documentation.2026.10.22.1
seed.invoices.2026.10.22.1
seed.standard-reports.2026.10.22.1
```

Проверка — один запрос; при наличии отметки этап пропускается целиком:

```
Посадка документации уже выполнена — пропуск.
```

Отметка ставится **только после успешного завершения**: если посадка упала на середине,
следующий запуск её повторит. При изменении состава посадки версию в
`SeedStateService` нужно поднять — тогда она один раз выполнится заново на всех базах.

### 4.8. Взаимоблокировка `40P01` при построении дерева (22.10.2026)

**Симптом.** При открытии рабочего окна:

```
40P01: обнаружена взаимоблокировка
  ModuleMetadataService.EnsureSchemaAsync()          (строка 29)
  ModuleMetadataService.GetAllNavigationGroupOrdersAsync()
  MainWorkWindow.LoadWithIndependentConnectionAsync()
  MainWorkWindow.BuildNavigationTree()
```

**Причина.** Пять наборов дерева читаются параллельно на отдельных подключениях (п. 4.6),
а `GetAllNavigationGroupOrdersAsync` внутри себя вызывал `EnsureSchemaAsync` — то есть
выполнял `CREATE TABLE IF NOT EXISTS` и `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.
`ALTER TABLE` берёт `ACCESS EXCLUSIVE` на `MetadataModules`; в это же время другие
подключения читали `MetadataObjects` / `Reports`, и Postgres снимал одну из транзакций
как жертву взаимоблокировки.

**Сделано.**

1. `EnsureSchemaAsync` выполняется **один раз на процесс** для каждой строки подключения
   (статический набор `SchemaEnsuredConnections` + блокировка). Повторные вызовы — no-op.
2. Из читающих методов убраны вызовы DDL: `GetModulesAsync`, `GetItemsAsync`,
   `GetAllNavigationGroupOrdersAsync`, `GetNavigationGroupOrdersAsync`. Чтение больше
   не создаёт и не меняет таблицы.
3. В `MainWorkWindow.BuildNavigationTree` схема готовится **заранее и на своём подключении**:

```csharp
private static async Task EnsureModuleSchemaAsync()
{
    await using var context = await ServiceLocator.InfoBaseManager.GetCurrentDbContextAsync();
    await new ModuleMetadataService(context).EnsureSchemaAsync();
}

// в BuildNavigationTree — до Task.WhenAll
await EnsureModuleSchemaAsync();
```

Порядок стал детерминированным: сначала DDL (один раз, одно соединение), затем пять
параллельных чтений без каких-либо блокировок схемы.

**Правило.** Читающий метод не выполняет DDL. Схема готовится на старте — на отдельном
подключении, до параллельных чтений.

### 4.9. `A second operation was started on this context instance` в редакторе модулей (22.10.2026)

> Подробный разбор аварии — отдельный документ: **`Docs/Ошибка_DbContext_в_редакторе_модулей.md`**.

**Симптом.** В конфигураторе, вкладка «Модули и разделы», при переключении модулей:

```
System.InvalidOperationException: A second operation was started on this context instance
before a previous operation completed. ...
  в ModuleMetadataService.GetItemsAsync()          (строка 141)
  в ModuleManagementView.LoadObjectsAsync()        (строка 75)
  в ModuleManagementView.OnModuleSelected()        (строка 57)
```

В логе записи не было: исключение ловилось обработчиком `DispatcherUnhandledException`
(`App.OnDispatcherUnhandledException`), который помечает `InvalidOperationException`
как обработанное — окно не падало, но и след в логе не оставался.

**Причина.** Редактор модулей работал на **общем** контексте окна конфигуратора
(`new ModuleManagementView(_context)`). Обработчик `OnModuleSelected` — `async void`:
при быстром переключении модулей второй вызов `LoadObjectsAsync` стартует, пока первый
ещё не завершился, и оба работают с одним и тем же экземпляром `DbContext`.
EF Core на это отвечает ровно той ошибкой, что и в стеке. Отдельно: общий контекст
окна в это же время занят деревом и другими редакторами (`AccountingSetupView`,
`UserAccessManagementView`, `ReportDataSetManagementView` — они тоже получали `_context`).

**Сделано.** Редактор модулей больше не берёт общий контекст окна — у него своя строка
подключения, и каждая операция идёт на своём подключении:

```csharp
private AppDbContext CreateContext() => new AppDbContext(_connectionString);
```

1. **Чтение** — три независимых набора (привязки, документы, отчёты) читаются
   параллельно, каждый на своём подключении:

```csharp
var assignmentsTask = LoadOnOwnConnectionAsync(context =>
    new ModuleMetadataService(context).GetItemsAsync());
var documentsTask = LoadOnOwnConnectionAsync(context => context.MetadataObjects.AsNoTracking()
    .Where(item => item.ObjectType == "Document").OrderBy(item => item.Name).ToListAsync());
var reportsTask = LoadOnOwnConnectionAsync(context => context.Reports.AsNoTracking()
    .Where(item => !item.IsPrintForm).OrderBy(item => item.Name).ToListAsync());

await Task.WhenAll(assignmentsTask, documentsTask, reportsTask);
```

   По VPN задержки складываются не в сумму, а в максимум.

2. **Запись** — своя единица работы: `SaveModuleAsync` + `SaveAssignmentsAsync` на одном
   подключении, общий контекст окна не трогаем.

3. **DDL и посадка** — на своём подключении и **до** чтений. `EnsureSchemaAsync` и
   `EnsureDefaultModulesAsync` теперь сериализованы семафором на строку подключения:
   два вызова DDL одновременно давали бы либо взаимоблокировку `40P01`, либо гонку
   по уникальному индексу `Code`.

4. **Устаревший результат отбрасывается**: `OnModuleSelected` — `async void`, новая
   загрузка может начаться раньше старой. Счётчик `_loadVersion` не даёт старому
   результату переписать свежий.

5. **Ошибки пишутся в лог**: `SystemLogService.Error(...)` в редакторе модулей —
   иначе `async void` проглатывал исключение, и в логе не оставалось следа.

**Проверка (стенд на боевой базе).** Гонка воспроизводится и снимается:

| Проверка | Результат |
| --- | --- |
| A. Общий контекст + два параллельных `ToListAsync` | `InvalidOperationException: A second operation was started…` — гонка воспроизведена |
| B. Три набора параллельно на разных подключениях | ОК: привязки=68, документы=28, отчёты=35 |
| C. 20 итераций параллельных чтений | ОК, без ошибок |
| D. 4 параллельных вызова DDL + посадки | ОК, без взаимоблокировки |
| E. `GetConnectionString()` → новое подключение | ОК: читает ту же базу |

**Правило.** Один `DbContext` — одна операция. Параллельные чтения — на разных
подключениях. Редактор, который живёт дольше одной операции, получает своё
подключение, а не общий контекст окна.

## 7. Правила, чтобы не вернуть проблему

1. **Не выполнять команды на соединении EF.** Для служебных чтений (схема, счётчики)
   — отдельное соединение или `DatabaseSchemaCache`.
2. **Не делать запрос на каждое поле/строку.** Сначала снимок/список, потом работа
   в памяти, затем одна пакетная команда.
3. **Идемпотентные посадки — под отметку.** Новая посадка = новая константа версии
   в `SeedStateService`.
4. **Деревья и списки — на своих подключениях.** Общий контекст окна занят
   пользовательскими операциями.
5. **Замер остаётся в коде.** `StartupProfiler` дешёвый; при жалобе на медленный
   старт сразу видно этап.
6. **Один контекст — одна операция.** Параллельные чтения идут на разных
   подключениях; общий контекст окна редакторам не раздаётся (п. 4.9).
7. **`async void` — с логированием.** Исключение из такого обработчика уходит в
   `DispatcherUnhandledException` и может остаться без следа: ловить и писать в лог
   нужно на месте.

| Файл | Роль |
|---|---|
| `Services/StartupProfiler.cs` | замер этапов запуска и запись в лог |
| `Services/DatabaseSchemaCache.cs` | снимок схемы одним запросом (тип, nullable, default) |
| `Services/SeedStateService.cs` | отметки о выполненных посадках в `schema_migrations` |
| `Services/SchemaRepairService.cs` | достройка колонок EF-модели по снимку схемы |
| `Services/MetadataSchemaRepairService.cs` | достройка колонок справочников по метаданным |
| `Services/DocumentationMetadataSeedService.cs` | посадка документации: ранний выход, отметка, кэш |
| `Services/InvoiceMetadataSeedService.cs` | посадка счетов-фактур: отметка |
| `Services/MetadataService.Reports.cs` | стандартные отчёты: предзагрузка вместо N+1 |
| `Services/ModuleMetadataService.cs` | `GetAllNavigationGroupOrdersAsync` — один запрос на все модули |
| `Services/InventoryDocumentSchemaService.cs` | пакетный `ALTER`, исправленная проверка FK |
| `Views/MainWorkWindow.xaml.cs` | замеры этапов, дерево на отдельных подключениях |
| `Views/Configurator/ModuleManagementView.xaml.cs` | редактор модулей: свои подключения, параллельные чтения |
| `Views/ConfiguratorWindow.xaml.cs` | замеры этапов, дерево на отдельных подключениях |
