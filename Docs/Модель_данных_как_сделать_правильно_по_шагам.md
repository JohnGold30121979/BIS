# Модель данных BIS.ERP — как сделать правильно, по шагам

> Дата: 17.10.2026. Статус: рабочий план к исполнению.
> Связанные документы: `Docs/Анализ_структуры_таблиц_и_данных.md` (оценка 6.1/10), `Docs/План_нормализации_модели_данных.md` (краткий план).
> Этот документ — подробная инструкция: что делать, зачем, в каком порядке, с каким SQL/C# и как проверить.
> Правило: код этим документом не меняем, только описываем. Каждую фазу делать отдельным коммитом + бэкап базы.

## 0. Куда идём — целевая модель одной картинкой

```
ЯДРО (EF Migrations — единственный создатель статики):
  Users, InfoBases,
  MetadataObjects/Fields/Calculations/PostingRules (+уникальности),
  MetadataModules/Items, Reports/* (Fields/Filters/Groups/Parameters/UserSettings/ElementMappings),
  ReportDataSets/DataSetFields, AccountingPeriods/ModuleStates,
  AccountOpeningBalances, AccountTurnoverSnapshots, FinancialReportLines(+Accounts),
  TaxJournalRecords, LocalizationEntries, RegulatedReportTemplates
  + DynamicDocuments/DynamicDocumentRows(Data jsonb), DbfMetadata (только импорт DBF)
  + LEGACY READ-ONLY: Organizations, Document/Row/Movement, Postings(static),
    Materials/FixedAssets(static) — [Obsolete], новых ссылок нет

СПРАВОЧНИКИ (только MetadataService.CreateDynamicTableAsync, catalog_*):
  catalog_organizations (ЕДИНСТВЕННЫЙ!), catalog_plan_schetov,
  catalog_currencies, catalog_employees, catalog_assets, catalog_cash_desks, ...

ДОКУМЕНТЫ (только MetadataService, doc_* + doc_*_lines):
  doc_sales_invoice + doc_sales_invoice_lines(invoice_id NOT NULL CASCADE)
  doc_purchase_invoice + doc_purchase_invoice_lines(invoice_id NOT NULL CASCADE)
  doc_cash_orders (order_kind Receipt/Payment, без _lines)
  doc_advance_payment + doc_advance_payment_lines(advance_id NOT NULL CASCADE)
  doc_payment_orders, doc_exchange_diff, ...

РЕГИСТРЫ (только через проведение, руками не пишем):
  doc_postings (document_table + document_id + doc_date + debit/credit + org/curr) + снимки/остатки
```

### Канон имён и типов

| Объект | Имя | PK | Деньги | Даты | Ссылки |
|---|---|---|---|---|---|
| Справочник | `catalog_<сущ>` строчными | `"Id" uuid PK DEFAULT gen_random_uuid()` | — | `created_at timestamptz` | — |
| Шапка | `doc_<сущ>` | `"Id" uuid PK` | `numeric(18,2)` | `doc_date date`, `created_at timestamptz` | `organization_id uuid`, `currency_id uuid` |
| Строки | `doc_<сущ>_lines` | `"Id" uuid PK` | `numeric(18,2)` | — | `invoice_id/advance_id uuid NOT NULL → шапка CASCADE`, `UNIQUE(parent,line_no)` |
| Журнал | `doc_postings` | `"Id" uuid PK` | `debit/credit numeric(18,2)` | `doc_date date NOT NULL`, `created_at timestamptz` | `document_table text + document_id uuid`, `organization_id uuid`, FK или RESTRICT |
| Ядро EF | `PascalCase` как сейчас | `uuid` (кроме `Users.Id int` — оставить, не трогать) | `numeric(18,2)` | `timestamptz` для created/posted, `date` для doc_date | реальные FK + CASCADE как в Reports/* |

Запрещено: `text` для GUID (только `uuid`), `float/double` для денег, `timestamp without tz` для проведения, `varchar` без длины для кодов (коды — `varchar(8..50)` + UNIQUE).

## 1. Фаза 1. P0 — закрыть дыры целостности (1–2 дня, низкий риск)

Зачем: пока FK условные, а DDL без экранирования — любая следующая фаза
может уронить базу или наплодить сирот. Сначала защита, потом красота.

### 1.1. Экранировать все DDL-имена (quote_ident / %I)

Проблема P0-4: `RenameDocumentTableAsync` подставляет `oldTable/targetTableName`
из `MetadataObjects` (редактируется через конфигуратор!) в DO-блок:

```sql
-- ТАК НЕЛЬЗЯ (текущее):
to_regclass('public.{oldTable}'); ALTER TABLE ""{oldTable}"" ...
-- кавычка в имени ломает запрос или хуже
```

Как правильно — только через `format` + `%I`:

```sql
DO $$
DECLARE old_t text := 'doc_fin_abc'; new_t text := 'doc_advance_payment';
BEGIN
  IF to_regclass('public.' || quote_ident(old_t)) IS NOT NULL THEN
    EXECUTE format('ALTER TABLE %I RENAME TO %I', old_t, new_t);
  END IF;
END $$;
```

В C# — аналог `AdvancePaymentService.QuoteIdentifier` (уже есть в проекте):
двойные кавычки удваиваются, имя оборачивается в `"..."`. Применять ВЕЗДЕ,
где имя таблицы/колонки приходит из данных: `RenameDocumentTableAsync`,
`CreateDynamicTableAsync`, патчи `.bispatch`, `RuntimeSchemaFixService`.

Проверка: переименовать тестовый объект в имя с кавычкой `doc_"x` —
должно упасть валидацией, а не исполнением SQL. Плюс `grep -r "ALTER TABLE \"" Services/`
не должен показывать конкатенацию имён.

### 1.2. Безусловные FK шапка → строки (убрать «если шапка существует»)

Проблема P0-2 (`Docs/AdvancePayment-header-table-fix.md`): `EnsureSchemaAsync`
вешает `FK advance_id → шапка` только при `to_regclass(...) IS NOT NULL`.
Если шапки не было в момент вызова — таблица строк навсегда остаётся без FK.

Как правильно — три шага на каждую пару:

```sql
-- 1. Гарантировать шапку (CREATE TABLE IF NOT EXISTS шапки — идемпотентно)
-- 2. Почистить сирот (только после акта с бухгалтером!)
-- DELETE FROM doc_advance_payment_lines l WHERE NOT EXISTS
--   (SELECT 1 FROM doc_advance_payment h WHERE h."Id" = l.advance_id);
-- 3. NOT NULL + FK без условий:
ALTER TABLE doc_advance_payment_lines
  ALTER COLUMN advance_id SET NOT NULL;
ALTER TABLE doc_advance_payment_lines
  ADD CONSTRAINT fk_adv_lines_header FOREIGN KEY (advance_id)
  REFERENCES doc_advance_payment("Id") ON DELETE CASCADE;
-- то же для doc_sales_invoice_lines(invoice_id), doc_purchase_invoice_lines(invoice_id)
```

В коде: ввести отдельный `EnsureForeignKeyAsync(parent, child, fkName, onDelete)`
и вызывать его ВСЕГДА после `EnsureDocumentTableAsync`, а не внутри `if`.
Порядок при старте: `CreateDynamicTableAsync(шапка)` → `EnsureSchemaAsync(строки)` →
`EnsureForeignKeyAsync`. FK переживает перезапуски (ADD CONSTRAINT IF NOT EXISTS
через проверку `pg_constraint`).

Проверка: удалить шапку СФ/аванса в тесте — строки обязаны удалиться каскадом.
`SELECT count(*) ... LEFT JOIN ... WHERE h."Id" IS NULL` — всегда 0.

### 1.3. Запрет удаления справочника при живых ссылках (RESTRICT + UI)

Проблема P0-3: `catalog_organizations`, `catalog_currencies`, `catalog_plan_schetov`
удаляются в один клик, проводки/документы остаются висеть на GUID которого нет.
Отчёты показывают «Без организации».

Как правильно — два рубежа:

Рубеж БД (когда типы уже uuid, см. 3.3):
```sql
ALTER TABLE doc_sales_invoice ADD CONSTRAINT fk_sales_org
  FOREIGN KEY (organization_id) REFERENCES catalog_organizations("Id") ON DELETE RESTRICT;
-- то же: purchase, cash_orders, advance, payment_orders, doc_postings.organization_id
```

Рубеж UI (работает уже сейчас, до смены типов): перед DELETE справочника —
проверка счётчиками:
```sql
SELECT (SELECT count(*) FROM doc_sales_invoice WHERE organization_id::text = :id::text)
     + (SELECT count(*) FROM doc_purchase_invoice WHERE organization_id::text = :id::text)
     + (SELECT count(*) FROM doc_postings WHERE organization_id::text = :id::text)
     AS refs;
```
`refs > 0` → отказ «Есть N документов/проводок» + кнопка «Показать».
`refs = 0` → разрешить удаление.

Проверка: удалить контрагента с документами — отказ; без документов — успех.

## 2. Фаза 2. Один путь создания схемы (2–3 дня, средний риск)

Зачем: сейчас схему создают трое — EF Migrations, `EnsureSchemaAsync` в трёх
сервисах, `CreateDynamicTableAsync` в метаданных, плюс `RuntimeSchemaFixService`
латает ALTER-ами при старте. Результат — дрейф: в одной базе колонка есть,
в другой нет, миграции «зелёные».

### 2.1. Разделить ответственность (таблица решений)

| Что | Кто создаёт | Кто НЕ трогает |
|---|---|---|
| `Users, InfoBases, Metadata*, Reports*, AccountingPeriods*, TaxJournal, Localization, RegulatedReportTemplates, ReportDataSets/Fields, DynamicDocuments` | Только EF Migrations | `EnsureSchemaAsync` удалить оттуда |
| `catalog_*`, `doc_*`, `doc_*_lines`, `doc_postings`, `doc_numbering` | Только `MetadataService.CreateDynamicTableAsync` | EF `DbSet` для них не заводить |
| Старые базы (не хватает колонки) | Миграция EF с `ADD COLUMN IF NOT EXISTS` | `RuntimeSchemaFixService` только логирует дрейф |

### 2.2. Убрать CREATE TABLE из отчётных сервисов

Файлы: `ReportDataSetService.EnsureSchemaAsync` (создаёт `ReportDataSets`,
`ReportDataSetFields`), `RegulatedReportTemplateService.EnsureSchemaAsync`,
`StandardReportDeletionService.EnsureSchemaAsync` (`DeletedStandardReports`).

Шаги:
1. Зафиксировать эти таблицы как часть EF-модели: `DbSet` уже есть для
   `ReportDataSets/Fields` — проверить, добавить миграцию `AddReportDataSetsToEf`.
2. Для `DeletedStandardReports` (PK — строковый `Code`, не `Guid`) — отдельная
   конфигурация EF для строкового ключа, либо смена ключа на `Guid + UNIQUE(Code)`.
3. Удалить вызовы `EnsureSchemaAsync` из отчётности. Проверка — `grep -r EnsureSchemaAsync Services/Report*` пусто.
4. `RuntimeSchemaFixService` перевести в режим «проверка»: сверяет
   `__EFMigrationsHistory` vs `to_regclass`, расхождения — в лог + окно,
   а не тихий ALTER.

### 2.3. Патчи .bispatch — только данные, не DDL вслепую

`schema.sql` внутри патча обязан идти через тот же `CreateDynamicTableAsync`
(с экранированием из 1.1), а не сырым `CREATE TABLE`. Порядок применения:
`schema.sql` → `metadata.json` → `data.json` → `reports.json`, каждый шаг
в транзакции, откат при ошибке.

Проверка фазы 2: две чистые базы, поднятые «с нуля» (миграции + сид),
имеют идентичный `\d` выхлоп. `git grep "CREATE TABLE IF NOT EXISTS" Services/`
показывает только `MetadataService` (+ legacy `DynamicDocuments`, который в EF).
показывает только `MetadataService` (+ legacy `DynamicDocuments`, который в EF).

## 3. Фаза 3. Справочники и документы — убрать дубли, выровнять типы (3–5 дней)

### 3.1. Один справочник организаций: catalog_organizations (детально расписано ранее)

Коротко: `Models/Organization.cs` + `DbSet Organizations` → `[Obsolete]`,
боевой — `catalog_organizations` с `is_primary/director/chief_accountant`.
Перенос остатков `INSERT ... WHERE NOT EXISTS`, сверка `count(*)`,
переключение навигаций `Posting.Organization → OrganizationRef Guid`,
затем `DROP TABLE "Organizations"` (или VIEW для чтения).
Новых `context.Organizations` — ноль, контроль `grep` в ревью.

### 3.2. План счетов, материалы, ОС — тот же приём

- Канон плана счетов — `catalog_plan_schetov` (`Code UNIQUE`), `ChartOfAccount` — legacy `[Obsolete]`.
- Материалы/ОС: аудит `SELECT count(*)` в `Materials` vs `catalog_*` (и `FixedAssets` vs `catalog_assets`), боевой — где данные и `is_active`, второй — obsolete. Не гадать — смотреть цифры.

### 3.3. GUID-ссылки: из text в uuid (главный технический шаг фазы)

Сейчас: `organization_id/currency_id/document_id` местами `text`, JOIN через
`o."Id"::text = p.organization_id::text` — индекс по uuid не используется,
БД ничего не проверяет.

Как правильно — по каждой колонке:

```sql
-- 1. Найти мусор, который не кастуется:
SELECT organization_id FROM doc_sales_invoice
WHERE organization_id IS NOT NULL AND organization_id::text !~ '^[0-9a-f-]{36}$' LIMIT 20;
-- 2. Почистить с бухгалтером (пустые → NULL, битые → акт).
-- 3. Смена типа (переписывает таблицу — делать в окно обслуживания!):
ALTER TABLE doc_sales_invoice ALTER COLUMN organization_id TYPE uuid
USING organization_id::uuid;
-- 4. FK (см. 1.3):
ALTER TABLE doc_sales_invoice ADD CONSTRAINT fk_sales_org
FOREIGN KEY (organization_id) REFERENCES catalog_organizations("Id") ON DELETE RESTRICT;
```

Список колонок: `doc_sales_invoice.organization_id/currency_id`,
`doc_purchase_invoice.*`, `doc_cash_orders.*`, `doc_advance_payment.*`,
`doc_postings.organization_id/currency_id/document_id` (+ `document_table text`
оставить текстом — это имя таблицы, не ссылка).

Проверка: `\d doc_sales_invoice` показывает `uuid`, `EXPLAIN` JOIN без `::text`.

### 3.4. Деньги — везде numeric(18,2)

Сейчас два стандарта: `numeric(18,2)` в остатках/снимках, `numeric(15,2)` в `Posting`.
Унифицировать на `numeric(18,2)`:

```sql
ALTER TABLE "Postings" ALTER COLUMN "Amount" TYPE numeric(18,2);
-- то же для AmountCurrency; проверить doc_postings debit/credit
```

Проверка: `SELECT column_name, numeric_precision, numeric_scale
FROM information_schema.columns WHERE data_type='numeric' AND table_schema='public'`
— везде scale=2, precision=18.

### 3.5. Три модели документа → одна боевая + две read-only

- Боевые: `doc_*` + `doc_postings` (проведение только через них).
- `Document/DocumentRow/DocumentMovement` — `[Obsolete]`, новых проведений нет.
- `DynamicDocument/DynamicDocumentRow` — только импорт DBF, в проведение не входит.
- `Posting.DocumentId Guid` без FK — оставить, но добавить `document_table text`:
  пара `(document_table, document_id)` однозначно указывает на шапку.
  Открытие двойным кликом из журнала — по этой паре (уже работает для СФ/п-п).

Проверка: новый документ нельзя провести через `Document*` — только через `doc_*`.
Проверка: новый документ нельзя провести через `Document*` — только через `doc_*`.

## 4. Фаза 4. Индексы и уникальности (1 день, низкий риск)

Зачем: сейчас есть индексы отчётов/документов, но нет бухгалтерских —
журнал за год и удаление шапки с каскадом делают Seq Scan.

В EF `OnModelCreating` добавить:

```csharp
modelBuilder.Entity<MetadataObject>().HasIndex(m => m.TableName).IsUnique();
modelBuilder.Entity<MetadataField>()
  .HasIndex(f => new { f.MetadataObjectId, f.DbColumnName }).IsUnique();
modelBuilder.Entity<MetadataModule>().HasIndex(m => m.Code).IsUnique();
modelBuilder.Entity<ReportDataSetField>()
  .HasIndex(f => new { f.ReportDataSetId, f.DbColumnName }).IsUnique();
// DeletedStandardReports: Guid PK + UNIQUE(Code), либо строковый ключ отдельной конфигурацией
```

Сырым SQL на динамике (идемпотентно):

```sql
CREATE INDEX IF NOT EXISTS ix_postings_doc ON doc_postings(document_table, document_id);
CREATE INDEX IF NOT EXISTS ix_postings_date ON doc_postings(doc_date);
CREATE INDEX IF NOT EXISTS ix_postings_dc ON doc_postings(debit_account, credit_account);
CREATE INDEX IF NOT EXISTS ix_postings_org ON doc_postings(organization_id);
CREATE INDEX IF NOT EXISTS ix_sales_lines_parent ON doc_sales_invoice_lines(invoice_id);
CREATE INDEX IF NOT EXISTS ix_purch_lines_parent ON doc_purchase_invoice_lines(invoice_id);
CREATE INDEX IF NOT EXISTS ix_adv_lines_parent ON doc_advance_payment_lines(advance_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_adv_lines ON doc_advance_payment_lines(advance_id, line_no);
CREATE UNIQUE INDEX IF NOT EXISTS ux_sales_lines ON doc_sales_invoice_lines(invoice_id, line_no);
```

Проверка: `EXPLAIN ANALYZE` журнала/ОСВ за год — Seq Scan на `doc_postings` исчез.
Удаление шапки с 1000 строк — миллисекунды, а не секунды.

## 5. Фаза 5. Метаданные — из строковых связей в проверяемые (2 дня)

Зачем: сейчас `TableName/DbColumnName/ReferenceCatalog/BalanceTable/ReferenceFields`
— свободный текст. Опечатка = затирание таблицы или ссылка в никуда.

Валидация в `MetadataService` ДО любого DDL:
- `TableName` — regex `^(catalog|doc|reg)_[a-z][a-z0-9_]{0,60}$` + уникальность.
- `DbColumnName` — `^[a-z][a-z0-9_]{0,60}$` + уникальность в пределах объекта.
- `ReferenceCatalog` — обязан существовать в `MetadataObjects` (`ObjectType='Catalog'`).
- `BalanceTable/MovementTable` — обязаны существовать (`to_regclass`) или быть пустыми.
- `ReferenceFields` JSON — оба поля обязаны существовать в объекте.
- `MetadataPostingRule` — выражения проверять на существующие поля объекта.

`CreateDynamicTableAsync` — добавить ветку «колонка есть, но тип другой»:
не пропускать молча, а делать `ALTER COLUMN TYPE ... USING` (с бэкапом) или
отказ с понятным сообщением.

Проверка: нельзя сохранить метаданные со ссылкой на несуществующий
справочник/поле/таблицу. Тест — создать поле `ReferenceCatalog='catalog_nope'` → отказ.

## 6. Фаза 6. Аудит, номера, даты, секреты (1–2 дня)

6.1. Аудит: к `doc_*` и `doc_postings` — `created_by text`, `updated_at timestamptz`,
`row_version bigint DEFAULT 1` (optimistic concurrency в EF). Физический DELETE
из `doc_postings` запретить (только через «распровести»), документы — «распровести → пометить».

6.2. Номера: `UNIQUE(doc_number)` или `UNIQUE(doc_number, doc_date)` на каждой шапке
+ выдача номера в транзакции (`SELECT ... FOR UPDATE` на `doc_numbering`).
Параллельная выдача — без дублей (проверить двумя окнами).

6.3. Даты: дата документа — `date`, проведение/создание — `timestamptz`.
`DateTime.UtcNow` только для `created_at`. Иначе «счёт вчера» из-за UTC.

6.4. Секреты: `InfoBase.Password` шифровать (DPAPI на Windows), в логах/ошибках —
без пароля (маскировать `Password=***`).

## 7. Фаза 7. Приёмка — SQL-контроль (0.5 дня)

Нулевые сироты и баланс — обязательные ворота:

```sql
-- сироты (все нули):
SELECT count(*) FROM doc_advance_payment_lines l LEFT JOIN doc_advance_payment h ON h."Id"=l.advance_id WHERE h."Id" IS NULL;

```
