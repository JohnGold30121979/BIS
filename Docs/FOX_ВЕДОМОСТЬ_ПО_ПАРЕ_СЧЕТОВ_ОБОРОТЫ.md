# Ведомость по паре счетов (обороты)

## Назначение и краткий вывод

Отчёт находится в финансовом модуле `fox/fin_vpf9`. Его рабочая цепочка:

```text
Форма ввода / просмотр пары счетов
  └─ обработчик Command15.When
       └─ OBOR_BP(SC1, SC2)
            ├─ процедуры модулей из PLUS_INF → временная OPER
            └─ PLUS_VP → временная VED
                 └─ PRB1_SCH_V → Excel-ведомость
```

Основное назначение — показать движения и обороты по двум выбранным счетам, с корреспондирующим счётом, документом, текстом проводки и суммами.

Ключевая особенность реализации: `OBOR_BP` не отбирает только прямые проводки между `SC1` и `SC2`. Он последовательно собирает все движения, где встречается первый счёт, затем — все движения, где встречается второй. Корреспондирующий счёт каждой найденной проводки показывается в `VED.KORSCH`.

Например, при выборе `1010` и `3310` в набор попадут:

- `Дт 1010 / Кт 3310` — попадёт при обработке обоих счетов;
- `Дт 1010 / Кт 5210` — попадёт при обработке `1010`;
- `Дт 6010 / Кт 3310` — попадёт при обработке `3310`.

Следовательно, название «по паре счетов» описывает два контролируемых счета, а не ограничение корреспонденции только этой парой.

## Найденные файлы

| Роль | Файл | Что делает |
| --- | --- | --- |
| Сбор данных по паре | `fox/fin_vpf9/obor_bp.prg` | Создаёт временные `OPER` и `VED`, получает проводки от модулей и вызывает накопитель. |
| Наполнение ведомости | `fox/fin_vpf9/plus_vp.prg` | Отбирает проводки из `OPER`, раскладывает на дебетовые/кредитовые обороты и начальные остатки. |
| Выгрузка в Excel | `fox/fin_vpf9/prb1_sch_v.prg` | Формирует лист Excel из `VED`, 9 колонок. |
| Печатный макет VFP | `fox/fin_vpf9/prb1_sch_v.frx` / `.frt` | Сопутствующий FRX/FRT-макет с тем же именем. В найденном PRG-экспорте используется Excel, а не команда `REPORT FORM`. |
| Шаблон структуры ведомости | внешняя таблица `VED_S.DBF` | Из неё копируется структура временной таблицы `VED`. |
| Исходные операции | внешняя таблица `FINSET` | Её структура копируется во временную `OPER`; дальше её наполняют процедуры активных модулей. |
| Реестр подключаемых модулей | внешняя таблица `PLUS_INF` | Используются `PR_AKT`, `PROG`, `NAME_ARM`; код в `PROG` запускается для получения операций. |
| Справочник счетов | внешняя таблица `BUXSCH` | Нужен для признака счета `PRSCH`, который задаёт знак начального остатка. |
| Форма и обработчик | `fm_avtp.scx` / `fm_avtp.sct`, скомпилированная копия в `fin_oper-0611.exe` | В обработчике кнопки `Command15` выбираются два счёта, дата, аналитика и запускается `OBOR_BP`. |

`VED_S`, `FINSET`, `PLUS_INF` и `BUXSCH` лежат во внешней рабочей БД `FIN_OPER`; в исходном каталоге нет их рабочих данных. Поэтому ниже описаны точно установленные поля и алгоритм, но не реальные значения справочников.

## Входные параметры и форма

`OBOR_BP` объявлен так:

```foxpro
PARAM SC1, SC2

IF PCOUNT() < 2
    SC2 = SC1
ENDIF
```

В экранной форме значения берутся из контролов:

```foxpro
dtend = .text2.VALUE
tnm_v = .spid.VALUE
sch_1 = ALLTRIM(.text6.VALUE)
sch_2 = ALLTRIM(.text7.VALUE)

LEN1 = LEN(sch_1)
...
DO obor_bp WITH sch_1, sch_2
```

Значение параметров:

| Параметр / переменная | Источник | Назначение |
| --- | --- | --- |
| `SC1`, `sch_1` | `Text6` | Первый анализируемый счёт. Он же задаёт длину префикса `LEN1`. |
| `SC2`, `sch_2` | `Text7` | Второй счёт; если не передан — равен первому. |
| `DTEND` | `Text2` | Дата отчёта / расчёта положения на дату. |
| `TNM_V` | `SPID` | Аналитика, выбранная на форме; применяется при подсчёте итогов формы. |
| `DATA_OT1` | глобальная дата начала данных | Нижняя граница расчётного периода. |
| `DTPOSL` | ищется в `FINDOC` | Дата последнего документа до `DTEND` по выбранной аналитике. |
| `DTB` | `DTPOSL + 1` | Граница: операции до неё становятся начальным остатком, с неё — оборотом. |

Форма вычисляет границу следующим образом:

```foxpro
SELECT FINDOC
SET ORDER TO AV_DATE DESC
SET NEAR ON
SEEK DTOC(DTEND, 1)
SET NEAR OFF
LOCA REST FOR DATE < DTEND AND TNM = TNM_V

IF FOUND()
    DTPOSL = DATE
ELSE
    DTPOSL = DATA_OT1
ENDIF

DTBEG = MIN(DATA_OT1, DTPOSL - DAY(DTPOSL) + 1)
DTB = DTPOSL + 1
```

Таким образом, дата `DTB` не просто равна дате отчёта: она зависит от последнего найденного документа с выбранной аналитикой. Это нужно учитывать при сверке итогов.

## Как формируются `OPER` и `VED`

### 1. Подготовка временных таблиц

`OBOR_BP` не изменяет рабочие таблицы. Он создаёт временные DBF по структуре шаблонов:

```foxpro
USE (VED_S)
COPY STRU TO VED
USE

USE (FINSET)
COPY STRU TO OPER
USE

USE OPER EXCL
USE VED
```

- `OPER` имеет структуру проводок `FINSET` и наполняется для каждого активного подключённого модуля.
- `VED` имеет структуру `VED_S` и является набором строк, уже подготовленных для отчёта.

### 2. Получение операций из подсистем

Из `PLUS_INF` выбираются только активные записи (`PR_AKT`), а имя программы берётся из `PROG`:

```foxpro
SCAN FOR pr_akt
    progs = prog
    NA1 = ALLTRIM(NAME_ARM)
    IF !EMPTY(progs)
        SCH1 = SC1
        DO &progs WITH 2
        SELECT OPER
        GO TOP
        IF !EOF()
            DO PLUS_VP
        ENDIF

        IF VAL(SC1) # VAL(SC2)
            SCH1 = SC2
            DO &progs WITH 2
            SELECT OPER
            GO TOP
            IF !EOF()
                DO PLUS_VP
            ENDIF
        ENDIF
    ENDIF
ENDSCAN
```

Параметр `2` — контракт, по которому внешняя процедура конкретной подсистемы должна подготовить записи в `OPER` для выбранного `SCH1`. Поэтому полнота ведомости зависит от состава и настроек `PLUS_INF`, а не только от `FINSET` финансового модуля.

### 3. Отбор операций для счёта

`PLUS_VP` берёт только проводки без признака `A_P`:

```foxpro
SELECT OPER
SCAN FOR a_p = 0
    a = TRANSFORM(m.deb, '@L 99999999')
    b = TRANSFORM(m.cred, '@L 99999999')

    IF LEFT(a, LEN1) = SCH1
        && проводка попала по дебету выбранного счёта
    ENDIF

    IF LEFT(b, LEN1) = SCH1
        && проводка попала по кредиту выбранного счёта
    ENDIF
ENDSCAN
```

Сопоставление выполняется по префиксу, а не по точному равенству. Если `SCH1 = '101'`, будут отобраны `101`, `1010`, `1011` и т. п. Вызов с `SC2` повторяет ту же логику для второго префикса.

## Поля, которые переносит накопитель

### Из `OPER` в строку `VED`

| Поле `OPER` | Поле `VED` | Смысл |
| --- | --- | --- |
| `DEB`, `CRED` | `DEBET`, `KREDIT` | Исходные дебетовый и кредитовый счета проводки, в символьном виде. |
| `DEB` или `CRED` | `SCHET` | Выбранный счёт, по которому строка попала в ведомость. В коде устанавливается в `SCH1`. |
| противоположный счёт | `KORSCH` | Корреспондирующий счёт: при совпадении по дебету берётся `CRED`, по кредиту — `DEB`. |
| `SUM`, `SUM_V` | `SUM`, `SUM_V` | Сумма в базовой и валютной величине. |
| `D_KOL` / `C_KOL` | `KOL` | Количество: дебетовое или кредитовое в зависимости от стороны проводки. |
| `KOD_V`, `KURS_V` | `KOD_V`, `KURS_V` | Валюта и курс. |
| `D_NUCH`, `D_TNM`, `D_LISH`, `D_KOD_MAT`, `D_ZAKAZ` | `NUCH`, `TNM`, `LISH`, `KOD_MAT`, `K_ZAKAZ` | Аналитики дебетовой стороны. |
| `C_NUCH`, `C_TNM`, `C_LISH`, `C_KOD_MAT`, `C_ZAKAZ` | `K_NUCH`, `K_TNM`, `K_LISH`, `K_KOD_MAT`, `K_ZAKAZ` | Аналитики кредитовой стороны. |
| `DATE`, `DOK`, `TEX`, `PRS`, `NOM_AV` | одноимённые поля | Дата, номер документа, текст, признак/источник и номер аванса. |
| константа `1` | `VID_ZAP` | Обычная строка движения. |

### Специальные поля оборотов и начальных остатков

| Условие | Записываемые поля `VED` | Интерпретация |
| --- | --- | --- |
| `OPER.DATE < DTB`, счёт дебетовый (`PRSCH = 1`) | `DEB_BEG = SUM`, `DEB_BEG_V = SUM_V`, `VID_ZAP = 0` | Начальный дебетовый остаток. |
| `OPER.DATE < DTB`, счёт кредитовый (`PRSCH = 2`) | `CRED_BEG = -SUM`, `CRED_BEG_V = -SUM_V`, `VID_ZAP = 0` | Начальный кредитовый остаток со знаком минус. |
| `OPER.DATE >= DTB`, совпадение по дебету | `DEBSUM = SUM`, `DEBSUM_V = SUM_V` | Дебетовый оборот периода. |
| `OPER.DATE >= DTB`, совпадение по кредиту | `CREDSUM = SUM`, `CREDSUM_V = SUM_V` | Кредитовый оборот периода. |

Пример из обработчика начального остатка:

```foxpro
IF m.date < DTB
    SELECT buxsch
    SEEK m.deb
    prsch1 = prsch
    SELECT ved
    DO CASE
    CASE prsch1 = 1
        REPLACE deb_beg WITH m.sum, deb_beg_v WITH m.sum_v, ;
                date WITH dtb, vid_zap WITH 0
    CASE prsch1 = 2
        REPLACE cred_beg WITH -m.sum, cred_beg_v WITH -m.sum_v, ;
                date WITH dtb, vid_zap WITH 0
    ENDCASE
ELSE
    REPLACE debsum WITH m.sum, debsum_v WITH m.sum_v
ENDIF
```

После обработки одной подключённой подсистемы `OPER` очищается:

```foxpro
ZAP
```

Именно поэтому конечный набор находится в `VED`, а не в `OPER`.

## Итоги, которые показывает форма

После `OBOR_BP` обработчик открывает `VED` и суммирует поля по выбранной аналитике `TNM_V`:

```foxpro
SUM FOR TNM = TNM_V ;
    deb_beg, cred_beg, debsum, credsum ;
    TO zx1, zx2, zx3, zx4

.TEXT12.VALUE = zx1 - zx2
.TEXT3.VALUE  = zx3 - zx4
```

Значит:

```text
Начальный остаток = Σ(DEB_BEG) − Σ(CRED_BEG)
Оборот за период  = Σ(DEBSUM)  − Σ(CREDSUM)
```

Важная деталь: `CRED_BEG` уже записывается отрицательным при формировании `VED`. Поэтому формула `zx1 - zx2` фактически прибавляет абсолютную величину такого кредита. При проверке отчёта нужно сверять знак именно с тем, как заполнен `VED`, а не предполагать, что `CRED_BEG` всегда хранится положительным.

## Вид отчёта

Исполняемый экспорт — `prb1_sch_v.prg`. Он создаёт новый Excel-файл, лист называет «Ведомость по счету» и выводит шапку `NFIL1`, `SHA1`, `SHA2`, дату печати. Затем сканирует `VED`.

Фактические колонки Excel:

| № | Заголовок в коде | Источник | Выводимое значение |
| --- | --- | --- | --- |
| 1 | Дата | `VED.DATE` | `DTOC(DATE)`; для пустой даты — пусто. |
| 2 | № д-та | `VED.DOK` | Номер документа. |
| 3 | Аналитика | `VED.NAME_KOD`, `VED.KOD` | `NAME_KOD + '(' + KOD + ')'`. |
| 4 | Наименование | `VED.TEX` | Текст / содержание проводки. |
| 5 | Корр. счёт | `VED.KORSCH` | Корреспондирующий счёт. |
| 6 | Дебет | `DEB_BEG` или `DEBSUM` | Если `VID_ZAP` чётный — начальное сальдо, иначе дебетовый оборот. |
| 7 | Кредит | `CRED_BEG` или `CREDSUM` | Если `VID_ZAP` чётный — начальное сальдо, иначе кредитовый оборот. |
| 8 | Дебет (вал.) | `DEB_BEG_V` или `DEBSUM_V` | Валютный эквивалент. |
| 9 | Кредит (вал.) | `CRED_BEG_V` или `CREDSUM_V` | Валютный эквивалент. |

Фрагмент формирования строк:

```foxpro
SELECT ved
SCAN
    .Cells(x,1).Value = IIF(!EMPTY(date), DTOC(date), '')
    .Cells(x,2).Value = ALLTRIM(dok)
    .Cells(x,3).Value = ALLTRIM(name_kod) + '(' + ALLTRIM(STR(kod)) + ')'
    .Cells(x,4).Value = ALLTRIM(tex)
    .Cells(x,5).Value = korsch
    .Cells(x,6).Value = IIF(vid_zap % 2 = 0, deb_beg, debsum)
    .Cells(x,7).Value = IIF(vid_zap % 2 = 0, cred_beg, credsum)
    .Cells(x,8).Value = IIF(vid_zap % 2 = 0, deb_beg_v, debsum_v)
    .Cells(x,9).Value = IIF(vid_zap % 2 = 0, cred_beg_v, credsum_v)
    x = x + 1
ENDSCAN
```

Схематично отчёт выглядит так:

```text
┌────────────────────────────────────────────────────────────────────────────────────────────┐
│ <NFIL1>                                                                                    │
│ <SHA1>                                                                                     │
│ <SHA2>                                                    Напечатано: <текущая дата>       │
├──────────┬────────┬────────────────┬──────────────────────┬──────────┬──────────┬─────────┤
│ Дата     │ № д-та │ Аналитика      │ Наименование         │ Корр.счёт│ Дебет    │ Кредит │
├──────────┼────────┼────────────────┼──────────────────────┼──────────┼──────────┼─────────┤
│ 01.01.XX │ 000123 │ Контрагент (5) │ Оплата по договору   │ 3310     │ 10 000.00│         │
│ <остаток>│        │                │                      │          │          │ 3 000.00│
└──────────┴────────┴────────────────┴──────────────────────┴──────────┴──────────┴─────────┘
                                       + две колонки «Дебет (вал.)», «Кредит (вал.)»
```

Строки, у которых `VID_ZAP <> 1`, экспорт помечает жирным. По логике `PLUS_VP` это, в частности, строки начального остатка (`VID_ZAP = 0`).

## Пример прохождения одной проводки

Пусть в `OPER` есть запись:

```text
DATE = 15.05.2026
DEB = 1010
CRED = 3310
SUM = 10 000
SUM_V = 0
D_TNM = 25
TEX = "Оплата поставщику"
```

При `SC1 = '1010'`, `SC2 = '3310'`, `DTB = 01.05.2026`:

1. Вызов для `SC1` находит запись по дебету и пишет в `VED`: `SCHET = '1010'`, `KORSCH = '3310'`, `DEBSUM = 10 000`.
2. Вызов для `SC2` находит ту же запись по кредиту и пишет ещё одну строку: `SCHET = '3310'`, `KORSCH = '1010'`, `CREDSUM = 10 000`.
3. В выгрузке это будут две строки, если последующая логика формы не накладывает дополнительный фильтр. Такое дублирование является следствием алгоритма «собрать движения каждого счёта», а не ошибкой Excel-выгрузки.

Если бы дата проводки была меньше `DTB`, вместо `DEBSUM`/`CREDSUM` заполнились бы `DEB_BEG`/`CRED_BEG`; такая строка выводится как начальный остаток.

## Что стоит учитывать при сопровождении

- Сравнение счетов префиксное. Для строгого равенства нужно менять `LEFT(a,LEN1)=SCH1` и `LEFT(b,LEN1)=SCH1` на нормализованное точное сравнение.
- Пара `SC1`/`SC2` не используется как совместный фильтр `DEB = SC1 AND CRED = SC2` либо наоборот. Если бизнес-требование именно такое, отбор следует реализовать отдельно.
- `OPER` очищается оператором `ZAP` после каждого обработанного модуля. Доходить до него для итоговой диагностики поздно; диагностировать нужно `VED` либо делать копию до очистки.
- `PRB1_SCH_V` ожидает поля `NAME_KOD` и `KOD`. В `PLUS_VP` они явно не заполняются. Их заполнение должно происходить в иной части формы/подготовки `VED` либо эти колонки могут быть пустыми. Это точка для проверки на рабочей базе.
- В доступном коде у `prb1_sch_v.prg` нет прямого вызова `REPORT FORM prb1_sch_v`; фактический вывод реализован COM Automation Excel. FRX/FRT оставлен как сопутствующий макет, но его использование в этой ветке не подтверждено.
- Код формы хранится в бинарных `SCX/SCT`; вызов `OBOR_BP` и обработчики `Command15.When`, `Click`, `Valid` подтверждены по скомпилированной поставке `fin_oper-0611.exe`. Полная форма идентифицируется как `fm_avtp.scx` по составу проекта и вызову `DO FORM fm_avtp`.

## Минимальная проверка на рабочем месте

Перед изменением логики полезно сохранить набор `VED` после `DO OBOR_BP` и проверить:

```foxpro
DO obor_bp WITH '1010', '3310'
USE ved
BROWSE FIELDS schet, korsch, date, dok, tex, ;
              deb_beg, cred_beg, debsum, credsum, ;
              deb_beg_v, cred_beg_v, debsum_v, credsum_v, vid_zap
```

Проверить следует три вещи: есть ли лишние корреспондирующие счета, возникает ли ожидаемое двойное включение прямой проводки между выбранными счетами, и корректно ли отражается знак кредитового начального остатка.
