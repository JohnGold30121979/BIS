## 2. Разбор и правки

### 2.1. `42703: столбец o.bank_name не существует`

**Что происходит.** SQL-набор отчёта («Счёт-фактура НДС: позиции и реквизиты»,
`Services/ReportDataSetService.cs`) читает реквизиты организации:

```sql
COALESCE(o."bank_name", '')     AS seller_bank,
COALESCE(o."bank_account", '')  AS seller_account,
COALESCE(o."bic", '')           AS seller_bic,
…
COALESCE(bo."bank_name", '')    AS buyer_bank,
COALESCE(bo."bank_account", '') AS buyer_account,
COALESCE(bo."bic", '')          AS buyer_bic,
```

**Причина.** Реквизиты «Банк»/«Расчётный счёт»/«БИК» убраны из **метаданных**
справочника «Организации» (`RemoveLegacyOrganizationBankFieldsAsync`: банки и счета
ведутся отдельными справочниками), но **физические колонки** оставлены — их читают
печатные формы и отчёты. В базе, созданной после удаления полей, колонки никто
не создаёт: `CreateTableForCatalogAsync` строит таблицу по метаданным, а
`MetadataSchemaRepairService` добавляет только колонки, описанные в метаданных.
Итог — отчёт падает на `o.bank_name`.

Проверено на копии локальной базы, созданной после удаления полей:

```
до:    SELECT o."bank_name" FROM catalog_organizations o LIMIT 1;
       ERROR: 42703: столбец o.bank_name не существует
после: ALTER TABLE … ADD COLUMN IF NOT EXISTS "bank_name" varchar(250); …
       ERROR нет, колонки bank_name/bank_account/bic на месте
```

**Правка.** `Services/MetadataService.Catalogs.cs`, в
`EnsureOrganizationsCatalogStructureAsync` — после удаления легаси-полей из
метаданных держим сами колонки:

```csharp
await RemoveLegacyOrganizationBankFieldsAsync(catalog);
await EnsureLegacyOrganizationBankColumnsAsync(catalog);
```

```csharp
/// <summary>
/// Легаси-колонки «Банк»/«Расчётный счёт»/«БИК» в справочнике организаций.
///
/// Из метаданных эти реквизиты удалены (банки и расчётные счета ведутся
/// отдельными справочниками), но физические колонки читают печатные формы
/// и SQL-наборы отчётов. В базах, созданных после удаления полей, колонки
/// никто не создавал — отчёты падали:
/// «42703: столбец o.bank_name не существует». Держим колонки на месте.
/// </summary>
private async Task EnsureLegacyOrganizationBankColumnsAsync(MetadataObject catalog)
{
    if (string.IsNullOrWhiteSpace(catalog.TableName))
        return;

    var table = QuoteIdentifier(catalog.TableName);
    await _context.Database.ExecuteSqlRawAsync($@"
        ALTER TABLE {table} ADD COLUMN IF NOT EXISTS ""bank_name"" varchar(250);
        ALTER TABLE {table} ADD COLUMN IF NOT EXISTS ""bank_account"" varchar(100);
        ALTER TABLE {table} ADD COLUMN IF NOT EXISTS ""bic"" varchar(50);");
}
```

Вызывается при каждом открытии базы (шаг идемпотентный — `IF NOT EXISTS`), поэтому
чинит и уже существующие базы, и новые. Бонусом на таких базах начинает работать
сид «Первичная организация»: его `INSERT` тоже пишет в `bank_name`.

### 2.2. `Заполните обязательные поля: Дебет, Кредит` при добавлении пары

**Что происходит.** В 13:56–14:00 пользователь трижды пытался добавить пару счетов;
диалог считал поля заполненными, а сервис — нет:

```
Ошибка: Ошибка сохранения: Заполните обязательные поля: Дебет, Кредит.
```

Это путь `AddCatalogItemAsync` → `AddCatalogItemCoreAsync`: `DbValueConverter.Convert`
для `uuid`-колонки превращает нераспознанный текст в `DBNull`, и поле попадает
в `missingRequired`. То есть в колонку летел **код счёта**, а не Id — поведение
до фикса контракта (п. 2.2 в `Docs/Пары_счетов_uuid_миграция.md`).

**Правка.** Нормализация при записи больше не зависит от `FieldType` в метаданных:
в старых базах «Дебет»/«Кредит» могли остаться `String`, а колонка уже `uuid`.
Теперь решение принимает **фактический тип колонки**, а принадлежность к счёту
определяется по `ReferenceCatalog`/имени поля.

`Services/MetadataService.cs`:

```csharp
/// <summary>
/// Поле — ссылка на план счетов. Тип поля в метаданных здесь не решает:
/// в старых базах «Дебет»/«Кредит» могли остаться строковыми, а колонка
/// уже uuid. Что делать со значением, решает фактический тип колонки
/// (проверяется в NormalizeAccountReferenceValuesAsync), а этот метод
/// отвечает только на вопрос «относится ли поле к счёту».
/// </summary>
private static bool IsAccountReferenceField(MetadataField field)
{
    if (string.IsNullOrWhiteSpace(field.DbColumnName))
        return false;

    return field.ReferenceCatalog?.StartsWith("План счетов", StringComparison.OrdinalIgnoreCase) == true ||
           AccountAnalyticsRules.IsAccountSelectorField(field);
}
```

Дальше без изменений: для uuid-колонки код ищется в `catalog_plan_schetov` и
подставляется Id (`NormalizeAccountReferenceValuesAsync`), для text-колонки значение
остаётся кодом. Это закрывает и добавление, и редактирование пары даже на базе
со «старыми» метаданными.

### 2.3. `Поле 'Вид операции' обязательно для заполнения`

**Что происходит.** В новом документе ТМЗ не выбран вид операции. Форма это
пропускала, и ошибку выдавал уже сервис при вставке:

```
Документ ТМЗ: Поле 'Вид операции' обязательно для заполнения
```

**Правка.** `Views/Dialogs/InventoryDocumentDialog.xaml.cs`, `OnSaveClick` —
проверка до записи:

```csharp
// Вид операции — обязательный реквизит шапки. Без него сервис
// отвечал «Поле 'Вид операции' обязательно для заполнения» уже
// после нажатия «Сохранить»; проверяем до записи и говорим понятно.
if (_editors.TryGetValue("document_entry_id", out var entryEditor))
{
    var selectedEntryId = entryEditor is ComboBox { SelectedValue: Guid entryValue }
        ? entryValue
        : Guid.Empty;

    if (selectedEntryId == Guid.Empty)
    {
        MessageBox.Show(
            $"Выберите вид операции из справочника «{InventoryDocumentModel.EntryCatalogName}».",
            "Документ ТМЗ", MessageBoxButton.OK, MessageBoxImage.Warning);
        (entryEditor as ComboBox)?.Focus();
        return;
    }
}
```

### 2.4. `Не найдено значение для поля «Вид покупки»: eb608619-…`

**Что происходит.** В поле ссылки оказался **Id** (Guid строкой), а
`ResolveReference` искал только по коду, наименованию и отображаемому тексту:

```csharp
var row = rows.FirstOrDefault(item =>
    string.Equals(Read(item, "Код", "code"), code, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(Read(item, "Наименование", …), text, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(AccountDisplay(item), text, StringComparison.OrdinalIgnoreCase));
```

Guid не совпадал ни с одним из вариантов — «значение не найдено».

**Правка.** `Views/Dialogs/InventoryDocumentDialog.xaml.cs`, `ResolveReference` —
сравниваем ещё и с `Id`:

```csharp
var row = rows.FirstOrDefault(item =>
    // В поле мог оказаться сам Id (Guid строкой) — например, значение
    // подставилось программно. Раньше такой текст не находился:
    // «Не найдено значение для поля «Вид покупки»: eb608619-…».
    string.Equals(Read(item, "Id"), text, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(Read(item, "Id"), code, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(Read(item, "Код", "code"), code, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(Read(item, "Наименование", "ФИО", "Полное наименование", "Наименование материала"),
        text, StringComparison.OrdinalIgnoreCase) ||
    string.Equals(AccountDisplay(item), text, StringComparison.OrdinalIgnoreCase));
```
