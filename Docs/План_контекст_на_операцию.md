# План перехода на «контекст на операцию»

Документ — пошаговый план для самостоятельной работы. Исходная задача: убрать ворота
(`DbContextGate`, `WithContextLockAsync`) и перейти на классический подход
«подключился асинхронно → отработал → уничтожено».

Решение по коду — за вами; здесь только карта работ, классы и правила.

---

## 0. Что уже есть в проекте (важные факты)

| Факт | Где | Вывод |
| --- | --- | --- |
| Новый контекст уже создаётся по вызову: `return new AppDbContext(current.ConnectionString);` | `Services/InfoBaseManager.cs:528` (`GetCurrentDbContextAsync`) | фабрика по сути уже есть, не хватает явного интерфейса |
| 36 сервисов хранят контекст в поле `private readonly AppDbContext _context` | `Services/*.cs` | это главный источник «общего» контекста |
| 6 окон держат поле `_context` | `Views/*.cs` | то же в UI-слое |
| 61 вызов `GetCurrentDbContextAsync()` в окнах (18 файлов) | `Views/*.cs` | здесь контекст живёт на одну операцию, но не освобождается (`using` нет) |
| Транзакции локальны: `BeginTransactionAsync` и `Commit` в одном методе | `AdvancePaymentService`, `InvoiceService`, `MetadataService` и др. | **хорошая новость**: переход не ломает транзакции |
| Ворота: `Services/DbContextGate.cs`, `MetadataService._contextAccess`, `WithContextLockAsync` | `Services/` | временная мера, убирается последним шагом |

Правило, к которому идём: **одна единица работы = один контекст = один `await using`**.
Контекст создаётся в начале публичного метода и уничтожается в конце; вложенные помощники
получают его параметром.

Преимущество: Npgsql держит пул соединений, поэтому «новый контекст» — это не новое
TCP-подключение, а дешёвый объект. Параллельные запросы становятся возможны физически,
и ворота не нужны: параллельные транзакции разруливает СУБД.

## 1. Шаг 0 — инвентаризация (полдня, без правок кода)

Соберите точный список и держите его как чек-лист. Команды — штатный PowerShell
(ripgrep не нужен). Скопируйте помощник один раз в сессию:

```powershell
function Find-Code {
    param([string]$Pattern, [string[]]$Path = '.', [string]$Filter = '*.cs', [int]$Context = 0)
    $root = (Get-Location).Path.TrimEnd('\') + '\'
    Get-ChildItem -Path $Path -Recurse -Filter $Filter |
        Select-String -Pattern $Pattern -Context 0, $Context |
        ForEach-Object {
            '{0}:{1}: {2}' -f $_.Path.Replace($root, ''), $_.LineNumber, $_.Line.Trim()
            if ($Context -gt 0) { $_.Context.PostContext | ForEach-Object { '      ' + $_.Trim() } }
        }
}
```

Дальше — по одному запросу на пункт чек-листа:

```powershell
# сервисы с полем контекста
Find-Code 'private readonly AppDbContext _context' Services

# окна с полем контекста
Find-Code 'private readonly AppDbContext _context|private AppDbContext _context' Views

# точки входа в окнах, где контекст берётся вызовом
Find-Code 'GetCurrentDbContextAsync' Views

# фоновые потоки с базой (главная зона риска)
Find-Code 'Task\.Run\(' Services, Views -Context 4

# транзакции (проверить, что каждая закрывается в своём методе)
Find-Code 'BeginTransaction|CommitAsync|RollbackAsync' Services

# объём работы по каждому сервису (сколько обращений к _context)
Get-ChildItem Services -Recurse -Filter *.cs | Select-String -Pattern '_context\.' |
    Group-Object Path | Sort-Object Count -Descending |
    Select-Object Count, @{n = 'Файл'; e = { Split-Path $_.Name -Leaf } } | Select-Object -First 15
```

Контрольная проверка, что выражение вообще работает (должно вернуть число больше нуля):

```powershell
(Get-ChildItem Services -Recurse -Filter *.cs | Select-String -Pattern '_context\.' | Measure-Object).Count
```

Результат шага: таблица «файл → сколько обращений → нужны ли транзакции → есть ли фоновые вызовы».
По ней формируются волны (раздел 4).

## 2. Шаг 1 — фабрика контекста (один день)

**Новые файлы** (имена — предложение):

`Services/IAppDbContextFactory.cs`

```csharp
public interface IAppDbContextFactory
{
    /// <summary>Контекст текущей информационной базы. Вызывающий обязан освободить.</summary>
    Task<AppDbContext> CreateAsync();
}
```

`Services/AppDbContextFactory.cs` — реализация поверх `InfoBaseManager`:

```csharp
public sealed class AppDbContextFactory : IAppDbContextFactory
{
    private readonly InfoBaseManager _infoBaseManager;

    public AppDbContextFactory(InfoBaseManager infoBaseManager) => _infoBaseManager = infoBaseManager;

    public Task<AppDbContext> CreateAsync() =>
        _infoBaseManager.GetCurrentDbContextAsync();   // уже отдаёт НОВЫЙ контекст
}
```

**Регистрация**: в `Services/ServiceLocator.cs` рядом с `InfoBaseManager` добавить статическое
свойство `DbContextFactory` (по образцу существующих). Если сервисы создаются вручную
(`new MetadataService(context)`) — фабрику можно передавать им так же, как сейчас передаётся
контекст.

**Ключевое**: фабрика не кэширует контекст. Каждый вызов — новый объект.

## 3. Шаг 2 — пилот на одном сервисе (один-два дня)

Цель — проверить подход и выработать шаблон правки, ничего не ломая.

Кандидат для пилота: **`Services/CashDayClosureService.cs`** (31 обращение, нет фоновых
вызовов) либо **`Services/AccountingPeriodService.cs`** (56 обращений). Не начинайте
с `MetadataService` — он самый большой (176 + 164 обращения).

Шаблон правки одного метода:

```csharp
// было
private readonly AppDbContext _context;
public MyService(AppDbContext context) => _context = context;

public async Task<Result> DoAsync(Guid id)
{
    var row = await _context.Things.FirstOrDefaultAsync(x => x.Id == id);
    // ...
    await _context.SaveChangesAsync();
}

// стало
private readonly IAppDbContextFactory _factory;
public MyService(IAppDbContextFactory factory) => _factory = factory;

public async Task<Result> DoAsync(Guid id)
{
    await using var db = await _factory.CreateAsync();
    var row = await db.Things.FirstOrDefaultAsync(x => x.Id == id);
    // ...
    await db.SaveChangesAsync();
}
```

Правила для пилота:

1. Контекст создаётся **в начале публичного метода**, освобождается через `await using`.
2. Вспомогательные методы принимают контекст параметром: `private async Task Helper(AppDbContext db, …)`.
3. Транзакция — внутри того же метода, что и её `Commit` (в проекте так и есть).
4. Чтение без изменения — `AsNoTracking()`: меньше памяти и никаких сюрпризов с трекингом.
5. `SaveChanges` вызывается в том же методе, где объект изменён.
6. Если метод возвращает сущность наружу (в окно) — возвращайте **DTO или словарь**,
   а не сущность EF: иначе она останется привязана к уже уничтоженному контексту.

Проверка пилота: собрать, прогнать сценарий этого сервиса в приложении, убедиться, что
в журнале нет ни `A second operation was started…`, ни `A command is already in progress…`,
и что данные сохраняются.

## 4. Шаг 3 — перенос сервисов волнами

Порядок — от простого к сложному, по данным шага 0. Ориентир по объёму (числа — обращения
к `_context`):

| Волна | Сервисы | Зачем в этом порядке |
| --- | --- | --- |
| 1 (разминка) | `CashDayClosureService` (31), `UserAccessService` (37), `ModuleMetadataService` (38) | мало обращений, нет фоновых вызовов |
| 2 | `ReportService` (51), `ReportDataSetService` (74), `PrintFormService` (32) | здесь идут экспорты PDF/Excel — снимаем главную зону риска (`Task.Run`) |
| 3 | `InvoiceService` (49), `ConfigurationExchangeService` (52), `AccountingPeriodService` (56) | есть транзакции — проверить, что они внутри методов |
| 4 | `MetadataService.*` (`MetadataService` 176, `.Catalogs` 164, `.Finance` 29, `.Reports` 26), `DocumentationMetadataSeedService` (56) | самые большие; делать после того, как шаблон отработан |
| 5 | остальные сервисы с полем `_context` (всего 36 файлов) | по остаточному списку из шага 0 |

Что менять в каждом файле:

1. Конструктор: `AppDbContext context` → `IAppDbContextFactory factory`.
2. Все методы класса: `_context` → локальный `db` из фабрики (правила раздела 3).
3. Если сервис делит один контекст между несколькими методами намеренно (цепочка
   «загрузил → позже сохранил») — такую цепочку надо **свернуть в один метод**
   с одним контекстом; это единственная содержательная переделка.
4. Кто создаёт сервис (`ServiceLocator`, окна, другие сервисы) — передать фабрику.

Признак, что цепочка «разорвана»: объект EF, переданный между методами или в окно,
на втором шаге даёт `InvalidOperationException`/`ObjectDisposedException`. Лечится не
удержанием контекста, а передачей DTO/идентификатора и повторной загрузкой.

## 5. Шаг 4 — окна (2–3 дня)

1. Убрать поля `_context` в 6 окнах: каждое обращение к базе — свой `await using var db`
   из фабрики.
2. В 61 точке `GetCurrentDbContextAsync()` добавить освобождение:
   `await using var context = await ServiceLocator.InfoBaseManager.GetCurrentDbContextAsync();`
   Если контекст передаётся в сервис, который теперь сам берёт контекст, — убрать передачу.
3. Фоновые вызовы (`Task.Run`) — раньше это было опасно; после перехода каждый поток
   работает со **своим** контекстом, и такие вызовы можно оставить как есть.
   Но проверьте, что внутрь `Task.Run` не передаётся контекст из окна.
4. Долгие операции (экспорты) — `AsNoTracking` и снимки данных (`dataSnapshot`) уже
   используются, отдельная работа не нужна.

## 6. Шаг 5 — убрать ворота

Когда обе ошибки перестанут появляться в журнале:

1. Удалить `Services/DbContextGate.cs`.
2. В `Services/MetadataService.cs` убрать `_contextAccess` и `WithContextLockAsync`
   (и все их вызовы — это те самые ~6 блоков).
3. Проверить, что не осталось ссылок:
   `Find-Code 'DbContextGate|WithContextLockAsync|_contextAccess' Services, Views`

## 7. Шаг 6 — проверка результата

```powershell
# не должно остаться хранения контекста в сервисах
Find-Code 'private readonly AppDbContext _context' Services          # ожидаем пусто

# в окнах тоже
Find-Code 'private readonly AppDbContext _context|private AppDbContext _context' Views   # ожидаем пусто

# сколько контекстов создаётся и сколько освобождается (два числа сравниваем глазами)
(Get-ChildItem Services, Views -Recurse -Filter *.cs |
    Select-String -Pattern 'GetCurrentDbContextAsync|_factory\.CreateAsync' | Measure-Object).Count
(Get-ChildItem Services, Views -Recurse -Filter *.cs |
    Select-String -Pattern 'await using var (db|context)' | Measure-Object).Count
```

Сценарии для ручной проверки (минимум):

1. Открыть справочник плана счетов, добавить запись — в журнале нет ошибок.
2. Быстро переключать вкладки MDI, пока идёт загрузка справочника.
3. Сформировать акт сверки и сразу нажать PDF/Excel.
4. Открыть диалог кассового ордера и платёжки (они грузят данные в фоне) и закрыть его.

В журнале не должно быть строк:
`A second operation was started on this context instance…` и
`A command is already in progress…`.

## 8. Подводные камни (список для самопроверки)

| Ситуация | Как правильно |
| --- | --- |
| Объект EF передаётся из сервиса в окно | передавать DTO/словарь, в окне — повторная загрузка |
| Цепочка «загрузил → позже изменил → сохранил» в разных методах | свернуть в один метод с одним контекстом |
| Транзакция с `Commit` в другом методе | свернуть в один метод (сейчас в проекте так и есть) |
| Метод возвращает `IQueryable` | вернуть `List`/`ToArrayAsync()` — иначе запрос выполнится на чужом контексте |
| Кэш сущностей внутри сервиса | кэшировать DTO, не сущности |
| Сервис-одиночка (`ServiceLocator`) | с фабрикой сервис становится без состояния — это нормально |
| Фоновый поток с контекстом окна | создавать контекст внутри потока через фабрику |
| Ошибка «A command is already in progress» после перехода | значит, где-то остался общий контекст — искать по чек-листу шага 7 |

## 9. Оценка и порядок

| Шаг | Объём | Риск |
| --- | --- | --- |
| 0. Инвентаризация | полдня | нет |
| 1. Фабрика | один день | минимальный |
| 2. Пилот | один-два дня | минимальный |
| 3. Сервисы волнами | 2–3 недели (36 файлов, по 5–8 в день в спокойном темпе) | средний: цепочки «загрузил → сохранил» |
| 4. Окна | 2–3 дня | низкий |
| 5. Снятие ворот | час | нет |
| 6. Проверка | 1–2 дня | нет |

Главное правило, чтобы не увязнуть: **не смешивать волны**. Пока идёт волна, ворота остаются
на месте — они совместимы с новым кодом (новые методы просто не берут общий контекст,
а значит не ждут ворот).
