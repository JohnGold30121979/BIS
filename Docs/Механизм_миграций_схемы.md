# Механизм миграций схемы BIS.ERP

Документ описывает единый механизм приведения схемы информационной базы к актуальному
виду при её открытии: что сделано, как устроено и почему выбран именно такой путь.

Дата: 19.10.2026.

---

## 1. Проблема

Клиентские информационные базы создавались в разное время и разными версиями системы.
В результате схема конкретной базы может отставать от кода:

| Что отстаёт | Пример | Чем заканчивалось |
|---|---|---|
| Таблицы EF-модели | нет `Reports.ClosedXmlLayout` | `42703`, падала загрузка главного окна, дерево не строилось |
| Колонки справочников | нет `catalog_organizations.bank_name` | `42703` в SQL-наборах СТ-1 и «счёт-фактура НДС» |
| Динамические каталоги | нет `catalog_plan_schetov.level` | сид плана счетов падал на каждом счёте, таблица оставалась пустой |
| Типы колонок | `organization_id` ещё `text`, а код сравнивает с `uuid` | `42883: оператор не существует: text = uuid` |

Править каждую базу руками нельзя: баз много, они у клиентов, и такой подход не
воспроизводим — следующая база снова «отстанет».

## 2. Рассмотренные варианты

### Вариант A. Только EF-миграции (`dotnet ef migrations`)

Плюсы: штатный инструмент, история версий, генерация DDL.

Почему не подошёл как единственный:

- существующие базы создавались через `EnsureCreated()` и **не имеют истории миграций**;
  `Migrate()` на них пытается создать уже существующие таблицы. Пришлось бы каждый раз
  «усыновлять» базу (`EnsureMigrationBaseline`);
- мастер-база `bis_master` вообще исключена из миграций: `Migrate()` падал на ней с `42P01`;
- EF ничего не знает о **динамических** таблицах `catalog_*` / `doc_*`: они создаются
  из метаданных во время работы, и колонки в них EF-миграциями не описать;
- миграция — это шаг «развернуть версию», а нам нужно «догнать отставшую базу при
  открытии», в том числе без участия администратора.

EF-миграции оставлены для **структурного baseline** (создание новой базы с нуля).
Задача «догнать существующую базу» решается отдельным механизмом.

### Вариант B. Скрипты по каждой базе

Плюсы: полный контроль.

Минусы: не масштабируется, требует ручного труда на каждого клиента, легко забыть
базу или перепутать версию, нет журнала «что где применено». Отказались.

### Вариант C. «Реактивное» самолечение без журнала

То, что было раньше: при старте вызывались разрозненные «починим, если сломалось»
(`RuntimeSchemaFixService`, `SchemaRepairService`, `MetadataSchemaRepairService`,
DDL внутри `AccountingPeriodService`).

Плюсы: база действительно догоняла.

Минусы, из-за которых механизм переработан:

- нет единого места: DDL размазан по сервисам, часть изменений вообще не видна;
- нет версий и журнала: невозможно ответить «что уже применено в этой базе»;
- одни и те же действия выполнялись всегда, включая разовые чистки;
- порядок шагов зависел от порядка вызовов в коде.

### Вариант D (выбран). Единый сервис миграций + журнал `schema_migrations`

Все изменения схемы собраны в `SchemaMigrationService`, пронумерованы и записываются
в таблицу `schema_migrations`. Шаги делятся на два вида:

- **повторяемые** — самовосстановление: достройка колонок, `CREATE TABLE IF NOT EXISTS`.
  Выполняются при каждом открытии базы, потому что база могла отстать снова;
- **разовые** — чистки и разметка данных: выполняются один раз, факт фиксируется в журнале.

Это сочетает плюсы A (версии и журнал) и C (база догоняет сама, без администратора),
не требуя ни ручных скриптов, ни истории EF-миграций в старых базах.

## 3. Архитектура

Точка входа при открытии базы:

```
InfoBaseManager.OpenAsync
  ├─ EnsureMigrationBaseline        (усыновление старых баз для EF)
  ├─ Database.MigrateAsync          (структурный baseline новых баз)
  └─ RuntimeSchemaFixService.EnsureAsync
       ├─ SchemaMigrationService.EnsureAsync   ← единый механизм миграций
       │    ├─ EnsureJournalAsync              (CREATE TABLE IF NOT EXISTS schema_migrations)
       │    ├─ LoadAppliedAsync                (что уже применено)
       │    └─ шаги 2026.10.19.01 … .07
       └─ DetectDriftAsync                     (только диагностика, ничего не меняет)
```

`RuntimeSchemaFixService` больше не содержит DDL: он вызывает миграции и затем
прогоняет детектор дрейфа, который пишет в лог оставшиеся расхождения.

### Журнал

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version     text PRIMARY KEY,
    description text NOT NULL DEFAULT '',
    applied_at  timestamp with time zone NOT NULL DEFAULT now(),
    runs        integer NOT NULL DEFAULT 1
);
```

Запись шага:

```sql
INSERT INTO schema_migrations (version, description, applied_at, runs)
VALUES ('2026.10.19.07', '…', now(), 1)
ON CONFLICT (version) DO UPDATE
SET applied_at = now(), runs = schema_migrations.runs + 1;
```

`runs` показывает, сколько раз шаг фактически выполнялся — по нему видно, что
повторяемые шаги действительно отрабатывают при каждом открытии.

### Шаги

| Версия | Что делает | Тип |
|---|---|---|
| 2026.10.19.01 | Колонки EF-модели в существующих таблицах (`Reports.ClosedXmlLayout` и подобные) | повторяемый |
| 2026.10.19.02 | Колонки справочников и документов по метаданным (`bank_name` и подобные) | повторяемый |
| 2026.10.19.03 | Схема кассовых дней и закрытия периода | повторяемый |
| 2026.10.19.04 | Схема наборов данных отчётов | повторяемый |
| 2026.10.19.05 | Разметка отчётов для окна «Бухгалтерская отчётность» | разовый |
| 2026.10.19.06 | Чистка FRX-отчётов (этап 2) | разовый |
| 2026.10.19.07 | Схема периодов, остатков и финансовых отчётов (перенесено из `AccountingPeriodService`) | повторяемый |

Шаг 07 — это ровно тот DDL, который раньше лежал внутри `AccountingPeriodService`
(`CREATE TABLE IF NOT EXISTS` для `AccountingPeriods`, `AccountingPeriodModuleStates`,
`AccountOpeningBalances`, `AccountTurnoverSnapshots`, `FixedAssetPeriodBalances`,
`FinancialReportLines`, `FinancialReportLineAccounts`, `TaxJournalRecords`, плюс
`ALTER TABLE … ADD COLUMN IF NOT EXISTS` для их колонок). Теперь текст живёт
в одном месте — `SchemaMigrationService.AccountingPeriodSchemaSql`, а
`AccountingPeriodService.EnsureSchemaAsync` вызывает
`SchemaMigrationService.EnsureAccountingPeriodSchemaAsync(_context)` и занимается
только наполнением данных.

## 4. Правила добавления нового шага

1. **Версия** — `ГГГГ.ММ.ДД.NN`, следующая по порядку; менять существующие версии нельзя.
2. **Идемпотентность** — шаг должен безопасно выполняться повторно:
   `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`.
3. **Только аддитивность** — добавлять колонки и таблицы; не удалять и не менять типы
   в повторяемых шагах. Переименования и смена типов — отдельные разовые шаги
   с явным SQL и проверкой условия применимости.
4. **Значения по умолчанию** — для `NOT NULL` обязательны (`''`, `0`, `false`, `now()`),
   иначе шаг упадёт на таблице с данными.
5. **Ссылочные поля** (`Reference`) добавляются без `NOT NULL`: выдуманный uuid
   нарушит внешний ключ.
6. **Изоляция ошибок** — исключение шага логируется (`Миграция <версия> … не выполнена`),
   остальные шаги и запуск приложения продолжаются.
7. **Логирование** — каждый шаг оставляет след: строка в журнале и, при изменениях
   схемы, сообщение `Схема: добавлена отсутствующая колонка …`.

## 5. Проверка

- Сборка `BIS.ERP.csproj`: **0 ошибок**.
- DDL шага 07 прогнан на боевой базе `bis_OsOO_1_20260728_054721`: выполняется,
  повторный запуск даёт только замечания «отношение уже существует, пропускается» —
  то есть шаг идемпотентен.
- Журнал проверен на той же базе: после двух записей одного шага
  `runs = 2`, запись обновляется, а не дублируется (`ON CONFLICT` работает).
- Дрейф метаданных и колонок на боевой базе: **0 расхождений** — механизм там
  ничего лишнего не меняет.
- Тестовая запись из журнала удалена, база осталась в исходном состоянии.

Ожидаемое поведение на отстающей клиентской базе при открытии:

```
Схема: добавлена отсутствующая колонка Reports.ClosedXmlLayout (text).
Схема: в catalog_organizations добавлена колонка bank_name (VARCHAR(255)) по метаданным.
Миграции схемы: выполнено 7, пропущено 0, ошибок 0.
```

## 6. Ограничения и что дальше

- Механизм **не** переносит данные и не меняет типы колонок автоматически: для этого
  нужен отдельный разовый шаг с явным SQL и условием применимости (например,
  `timestamp` → `timestamptz`, план §3.3).
- Динамическая таблица, которой ещё нет, шагом не создаётся — её создаёт
  `MetadataService` по метаданным; шаг 02 достраивает только колонки в существующих.
- EF-миграции остаются для новых баз; журнал `schema_migrations` и история EF —
  независимые механизмы, и это осознанно: у старых баз истории EF нет.
- Откат: шаги аддитивные, поэтому откат — ручной `DROP COLUMN`/`DROP TABLE`
  и удаление строки из `schema_migrations`; автоматического отката нет.
