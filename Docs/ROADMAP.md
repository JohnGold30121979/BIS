# Дорожная карта развития BIS ERP

Дата актуализации: август 2026 года

## 1. Текущее состояние проекта на июне–август 2026 года

### 1.1 Архитектура

- **Технологический стек:** WPF/.NET 8, PostgreSQL (Npgsql + EF Core), PDF — QuestPDF, Excel — ClosedXML, DBF/FRX — DotNetDBF + собственные парсеры.
- **Мета‑архитектура:** справочники, документы, отчёты, модули, поля и правила проводок описываются в базе данных (таблицы `MetadataObjects`, `MetadataFields`, `MetadataCalculations`, `MetadataPostingRules`, `MetadataModules`, `MetadataModuleItems`) и отображаются в рабочем режиме и конфигураторе.
- **Два режима:** рабочее окно (`MainWorkWindow`) и конфигуратор (`ConfiguratorWindow`).
- **Механизм патчей:** зашифрованные `.bispatch` (AES‑GCM) с `schema.sql`, `metadata.json`, `reports.json`, `modules.json`, `data.json`.

### 1.2 Модули

Система поддерживает 8 модулей. По умолчанию активен только модуль **Финансы**. Остальные включаются администратором через `Инфобазы → Модули`.

## 2. Дорожная карта по модулям

> **Принцип построения:** каждый модуль проходит пять стадий:
> 1. **Метаданные** — каталоги, документы, поля, проводки, отчёты в базе.
> 2. **Бизнес‑логика** — проведение документов, расчёты, движения, автоматические операции.
> 3. **UI** — рабочее окно модуля, справочники, формы документов, диалоги.
> 4. **Период закрытия** — сбор оборотов, снимки, проверка сбалансированности.
> 5. **Тесты** — smoke‑тесты и строгие числовые проверки.

**Ключевое решение (переработано):** отдельные XAML‑диалоги под каждый документ ОС **не создаём**. **Единый конвейер добавления документа ОС (на примере «Передача под отчет»):**

```text
ModuleMetadataService.FixedAssetDocumentNames
        │  (имя документа)
        ▼
MetadataObjects: объект типа Document (таблица doc_…) 
        │  + MetadataFields: Номер/Дата/Примечание, реквизиты,
        │    ReferenceCatalog → «Основные средства», «Сотрудники (МОЛ)», «Участки»…
        │  + MetadataPostingRules: правила проводок
        ▼
SynchronizeDefaultAssignmentsAsync / AssignMissingByNameAsync → модуль «FixedAssets»
        ▼
DynamicDocumentWorkView (журнал документов, кнопки Добавить/Провести)
        ▼
DynamicDocumentItemDialog.BuildFormAsync ──► форма документа
   ├─ «Учет движения ОС» → кастомные построители (см. ниже)
   └─ остальные 16 документов → универсальный цикл по _metadata.Fields:
        CreateControlAsync → ReferencePickerControl / ComboBox / Дата / Сумма / Скрытые
        (номер подставляется автоматически, is_posted — скрытое поле)
        ▼
OnSaveClick → ItemData → CreateDynamicRecordAsync / UpdateDynamicRecordAsync
        ▼
Проведение → MetadataService.PostDocumentAsync → ProcessFixedAsset*DocumentAsync
```

## 3. Единый генератор отчётности

### 3.1. Текущее состояние

Сейчас в системе **нет единого генератора отчётности**. Отчёты формируются через разрозненные пути:

| Путь | Компонент | Формат вывода | Статус |
|---|---|---|---|
| FRX → Report | `FrxToReportConverter` | FRX‑макет → native | Рабочий |
| Native table | `ReportPreviewWindow` | Таблица внутри WPF | ❌ Скрыт |
| Native постраничный | (не реализовано) | Native pagination | ⏳ В планах |
| PDF печатные формы | `PrintFormService` + QuestPDF | PDF | ✅ Рабочий |
| Excel | `ClosedXML` | XLSX | ✅ Рабочий (STI‑062_7) |

**Проблемы текущего подхода:**
1. `ReportPreviewWindow` — legacy‑просмотр, скрыт, не используется.
2. Native‑отчёты создаются в метаданных как неактивные (`IsActive = false`) до реализации постраничного вывода.
3. FRX‑варианты актов сверки хранятся отдельными печатными формами, но не должны быть отдельными пунктами меню.
4. Каждый тип отчёта (TrialBalance, GeneralLedger, BankStatement, FixedAssetStatement...) имеет свой код рендеринга в `ReportService`.

**Таблицы и модели отчётности:**

| Таблица | Модель | Назначение |
|---|---|---|
| `Reports` | `Report` | Справочник отчётов |
| `ReportFields` | `ReportField` | Поля отчёта |
| `ReportFilters` | `ReportFilter` | Фильтры |
| `ReportGroups` | `ReportGroup` | Группировки |
| `ReportElementMappings` | `ReportElementMapping` | Элементы FRX‑макета |
| `ReportDataSets` | `ReportDataSet` / `ReportDataSetField` | Источники данных |

### 3.3. Архитектура единого генератора (проект)

```
┌──────────────────────────────────────────────────────────┐
│                    UnifiedReportEngine                   │
├──────────────────────────────────────────────────────────┤
│  IReportDataSource  →  ReportDataSourceService           │
│  IReportTemplate    →  ReportTemplateParser (JSON DSL)   │
│  IReportRenderer    →  NativeReportRenderer              │
│  IReportOutput      →  PdfReportWriter / Excel / HTML    │
├──────────────────────────────────────────────────────────┤
│            UnifiedReportEngine.GenerateAsync             │
│                     (reportId, parameters)               │
│  1. загружает Report + ReportFields + Filters            │
│  2. тянет данные через ReportDataSourceService           │
│  3. парсит шаблон в ReportDocument                       │
│  4. рендерит страницы, применяет пагинацию               │
│  5. пишет вывод (PDF / Excel / HTML)                     │
└──────────────────────────────────────────────────────────┘
```

**Ключевые решения:**
- **Один вход:** `GenerateAsync(reportId, parameters)` для всех типов отчётов.
- **Плагинная архитектура:** новые типы рендеринга и вывода добавляются через `IReportRenderer` и `IReportOutputWriter`.
- **FRX‑совместимость:** существующие FRX‑варианты конвертируются в JSON‑шаблоны и становятся шаблонами внутри `Report`.
- **Постраничный вывод:** движок делит контент на страницы с учётом высоты шапки/подвала и высоты строк.
- **Выражения:** переиспользуется `FoxExpressionParser` для вычисления выражений в ячейках.
