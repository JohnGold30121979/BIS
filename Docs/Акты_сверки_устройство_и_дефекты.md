# Акты сверки: устройство, дефекты и правки

Документ описывает формирование актов сверки в BIS ERP: откуда берутся данные,
как устроены макеты, какие дефекты были найдены и исправлены, и как проверять
результат без запуска приложения.

Составлен по фактической проверке базы информационной базы и кода.
Версия на момент составления: `1.1.64`.

## 2. Путь данных до печатной формы

```
Проводки (doc_postings)
        │
        │  фильтр: is_active, период, при необходимости организация
        ▼
ReconciliationActBuilder.LoadMovementsAsync
        │
        ├──────────────────────────────┐
        ▼                              ▼
OrganizationBalanceService        движения по организациям
(пары счетов, сальдо, обороты)
        │                              │
        └──────────┬───────────────────┘
                   ▼
        ReconciliationActBuilder.BuildTable
                   │
                   ▼
            Таблица акта (73 строки)
                   │
      ┌────────────┴────────────┐
      ▼                         ▼
 Программный вывод          FRX-вывод
 (кодом, без макета)     (по макету из базы)
      │                         │
      │                  PrepareTemplateForReportRendering
      │                         │
      │                  BuildPackedReconciliationFrxTemplate
      │                         │
      │                  SplitTemplateIntoPages
      ▼                         ▼
   PDF / Excel              PDF / Excel
```

**Ключевое:** таблица строится **одним кодом** для обоих путей. Различается
только вывод. Поэтому дефект «одна организация» был невозможен на уровне
таблицы — он возникал при выводе.

## 3. Выбор пути вывода

Два независимых выпадающих списка в интерфейсе:

| Список | Что задаёт |
|---|---|
| **Формат отчёта** | Каким **кодом** выводить |
| **Вариант акта** | Какой **макет** использовать |

Это разные вещи, и их легко перепутать.

| Формат | Код вывода |
|---|---|
| Программный Excel / PDF | `BuildReconciliationActPdf` — кодом, без макета |
| Нативный Excel / PDF | Макет конструктора |
| **FRX FoxPro Excel / PDF** | **`ExportReportTemplatePreview` — по макету из базы** |

Макет выбирается вариантом, а способ вывода — форматом. Поэтому при
«Программном» формате исправления в FRX-упаковке не дают эффекта.

## 5. Найденные дефекты и правки

### 5.1. Печаталась одна организация вместо пяти

**Симптом:** при выборе «Все организации» в акте печаталась одна организация
и одна строка.

**Причина:** макет «Акт сверки вариант 1» обращается к полям строки **без префикса
набора данных**:

| Макет | Выражения строки |
|---|---|
| Акт сверки (77 540 б) | `ved.tex`, `ved.debet`, `ved.kredit` |
| Акт сверки вариант 1 (21 078 б) | `tex`, `debet`, `kredit` |

Код опознания требовал префикс обязательно:

```csharp
// Было: префикс обязателен
var name = Regex.Replace(expression, @"^(?:ved\d*|db_crs?|dbcrs?)[._]", string.Empty);
```

Для `tex` префикса нет, снятие ничего не даёт, поле не опознаётся и уходит
в **обрамление** вместо строк. Отсюда одна строка вместо 73.

**Исправление:** префикс стал необязательным, составные выражения исключены.

```csharp
// Составные выражения (korsch+' - '+kor_sch) не являются полем строки
if (expression.Contains('+') || expression.Contains('('))
    return false;

// Префикс снимается, если он есть, но не является обязательным
var name = Regex.Replace(expression, @"^(?:ved\d*|db_crs?|dbcrs?)[._]", string.Empty);
```

**Проверено:** таблица акта — 73 строки, 5 организаций, 8 секций.

### 5.2. В колонку даты попадало сегодняшнее число

**Симптом:** вместо даты проводки печаталась текущая дата.

**Причина:** в FoxPro `date()` — служебная функция, возвращающая системную дату.
В словаре переменных она хранится под ключом `date()`, а словарь не учитывает
регистр. Поиск снимает скобки, поэтому имя поля `date` попадало на функцию:

```
ExtraFields['date'] = '30.09.2026'   ← правильная дата проводки
Разрешённое 'date'  = '09.10.2026'   ← сегодняшняя (перехват)
```

**Второй источник перехвата** — цикл публикации доп. полей:

```csharp
var normalizedKey = NormalizeFieldName(extra.Key);   // "date" → "date"
variables[normalizedKey] = FormatPlainValue(extra.Value);   // затирает значение
```

**Исправление:** дата строки имеет приоритет, доп. поля её не перезаписывают.
Для строк без своей даты — заголовков, сальдо, итогов — сохраняется системная дата.

**Проверено:** `Разрешённое 'date' = '28.09.2026'` — реальная дата проводки.

### 5.3. Excel обрезал длинный отчёт

**Симптом:** в Excel попадали две строки вместо двадцати, расположение «поехало».

**Причина:** Excel умещал весь отчёт на один лист с фиксированным числом строк:

```csharp
var maxRows = landscape ? 58 : 82;
if (ShouldPackTabularFrxTemplate(...))
    maxRows = Math.Max(maxRows, 45 + rows * 3);   // для акта не срабатывало
```

Проверка `ShouldPackTabularFrxTemplate` для акта всегда ложна — акт идёт другим
способом упаковки. Поэтому `maxRows` оставался 58, и упакованный макет
(десятки тысяч единиц) сжимался в 58 строк.

**Исправление:** Excel использует ту же пагинацию, что и PDF — лист на страницу,
размер листа из пропорций макета, смещение страницы для линий сетки.

### 5.4. Прочие исправления

| Дефект | Причина | Исправление |
|---|---|---|
| Поля данных попадали в полосу `Summary` | Поиск полосы по координате игнорировал `BandType` | Сначала используется объявленный `BandType` |
| Шапка и подписи дублировались | Секция полосы данных повторялась целиком для каждой строки | Строки и обрамление разделены |
| Печаталось `debsum` / `kredit` вместо значений | Неразрешённое выражение возвращало свой текст | Неразрешённое выражение даёт пусто |
| Пустые значения перезаписывали реальные | Пустое значение публиковалось раньше настоящего | Пустые значения не публикуются |
| Пропала колонка «Сумма Дт» в сетке | Служебные колонки попали в `AutoGenerateColumns` | Колонки скрываются при генерации |
| Заголовок «АКТ СВЕРКИ» дублировался | Попадал и в `Title`, и в колонку операций первой строки | Заголовок не пишется в колонку операций |
| Короткий отчёт делился на десятки страниц | Размер листа брался как 2970 единиц A4 | Высота листа из пропорций макета |
| Длинный отчёт не делился вообще | Порог «одна страница» пропускал всё на один лист | Принудительная пагинация от 700 элементов |

## 6. Архитектурное изменение: общий сервис

Логика построения таблицы акта была **продублирована** в `AccountingReportsView`
и недоступна для проверки без запуска окна.

Вынесена в **`Services/ReconciliationActBuilder.cs`**:

| Что перенесено | Назначение |
|---|---|
| `CreateTable` | Колонки отчёта и служебные колонки макета |
| `LoadMovementsAsync` | Загрузка движений за период |
| `BuildTable` | Построение таблицы со следом для диагностики |
| `AddRow`, `AddSection` | Строки и секции акта |
| `AccountInPair`, `SameAccount` | Сопоставление счетов |
| `MatchesMovementOrganization` | Сопоставление организации |
| `ShortenText`, `IsDocumentTitleText` | Сокращение текста, фильтр заголовка |

**Что это дало:**

- Отчёт и диагностический инструмент используют **один код** — расхождение
  между ними невозможно.
- Построение таблицы можно проверить **без запуска приложения**.
- Удалено **277 строк** дублирующего кода из `AccountingReportsView`.

## 7. Как проверять без запуска приложения

### Инструмент ReconProbe

Консольное приложение `\.tools\ReconProbe`, вызывающее **настоящий код**
приложения.

```powershell
dotnet run --project .tools\ReconProbe\ReconProbe.csproj -c Release
```

Позволяет:

| Проверка | Что показывает |
|---|---|
| Состав пар и организаций | Сколько секций построит `OrganizationBalanceService` |
| Загрузка движений | Сколько строк вернёт запрос, по каким организациям |
| Построение таблицы | Все строки с датой, модулем, суммами |
| Вывод в PDF и Excel | Размер результата, наличие ошибок |
| Опознание полей макета | Какие выражения считаются элементами строки |

Подключение — к базе информационной базы, не к мастер-базе.

### Журнал диагностики

При формировании акта пишется файл рядом с программой:

```
bin\Debug\net8.0-windows\reconciliation-trace.log
```

Содержит:

| Раздел | Что показывает |
|---|---|
| Заголовок | Версия сборки, период, режим, выбранная организация, вариант макета |
| Входные данные | Число пар, движений, организаций; пустые даты, номера, модули |
| Движения по организациям | Сколько движений у каждой организации |
| Пары по организациям | Сколько пар у каждой организации |
| След построения | Логика группировки, число строк в таблице |
| Таблица акта | Все строки с значениями колонок |
| Упакованный макет | Состав элементов, подставленные значения |

**Практическая ценность:** журнал различает три случая, которые раньше
были неразличимы:

| Что показывает журнал | Где дефект |
|---|---|
| Таблица мало строк | Выборка данных |
| Таблица полная, макет мало элементов | Упаковка макета |
| Таблица полная, макет полный, печать неверная | Отрисовка или пагинация |

## 10. Выводы о процессе

Работа над актами сверки заняла много итераций. Причины:

1. **Правки вносились до подтверждения причины.** Несколько раз исправлялся
   вывод, тогда как дефект был в другом звене.
2. **Проверка шла по скриншотам.** Скриншот не различает «данные не дошли»
   и «данные не отрисовались».
3. **Не проверялось, что нужный код вообще вызывается.** Долго правилась
   FRX-упаковка, тогда как можно было сразу проверить путь вывода.

**Что исправило положение:**

- Прямое подключение к базе информационной базы — данные стали видны.
- Инструмент `ReconProbe` — проверка настоящего кода без запуска окна.
- Журнал диагностики — различение звеньев потока.

**Правило на будущее:** сначала получить доказательство из данных, затем
править код. Не наоборот.
