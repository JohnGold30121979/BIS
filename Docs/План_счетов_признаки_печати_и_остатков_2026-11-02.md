# План счетов: «Признак печати» и «Сохранять остатки»

Дата: 02.11.2026. Статус: исследование и план; реализация не выполнялась.

## Итог

В BIS.ERP признаки существуют как данные справочника: импортируются, сохраняются, нормализуются и отображаются в карточке и таблице. Использования этих значений в расчёте остатков и формировании бухгалтерских отчётов в проверенных исходниках не обнаружено.

Выявлены две ошибки соответствия эталону:

1. Перепутано назначение полей FoxPro: **PR_PR — печать**, **PR_O — сохранение остатков**. Сейчас импорт BIS.ERP связывает PR_O с `print_mode`, а PR_PR с `balance_mode`.
2. Общий список вариантов BIS.ERP ошибочно трактует код 7 как «по дополнительной аналитике». В основной форме эталона код 7 предусмотрен у PR_O и означает **«не хранить остатки»**. У PR_PR в этой форме всего шесть вариантов.

Простого подключения нынешних полей к расчётам недостаточно: сначала требуется исправить семантику и определить происхождение уже сохранённых значений.

## Назначение в эталоне

Это режимы детализации, а не флажки «да/нет». Связи со справочниками SV_O, SV_T, SV_L, SV_M и SV_V — отдельные настройки, которые не следует заменять этими режимами.

| Код | PR_PR: печать | PR_O: сохранять остатки |
|---|---|---|
| 0 | В отдельных отчётах подменяется на 6 | В FORMOST обрабатывается вместе с 6; также влияет на отбор счетов |
| 1 | По статьям | По статьям |
| 2 | По организациям | По организациям |
| 3 | По табельным номерам | По табельным номерам |
| 4 | По лицевым счетам | По лицевым счетам |
| 5 | По материалам | По материалам |
| 6 | По субсчетам | По субсчетам |
| 7 | В основной форме отсутствует | Не хранить остатки |

Нулевое значение нельзя без проверки объявлять универсальным «выключено»: обработка зависит от процедуры. В `fin_oper.prg` массив n_pr содержит подписи для кодов 0–6; для 7 подпись там не задаётся.

### Доказательство привязки полей

В `fm_sch.scx` запись 76 — `handbook.Form2.pr_pr`, ControlSource = `m.pr_pr`, ButtonCount = 6. Запись 77 — `handbook.Form2.pr_o`, ControlSource = `m.pr_o`, ButtonCount = 7; седьмой вариант в SCT подписан «не хранить остатки». В форме имеются заголовки «ПЕЧАТЬ» и «СОХРАНЯТЬ ОСТАТКИ».

Дополнительное подтверждение — потребители значений: PR_PR используется для выбора аналитики отчётов, PR_O — непосредственно в FORMOST при построении OST.

### PR_PR: как печатать

В `fmb1.SCT` методы читают `PR_PR1=IIF(PR_PR#0,PR_PR,6)` и выбирают аналитический код и наименование по PR_PR: организация, сотрудник, лицевой счёт, материал. Если собственная аналитика отсутствует, отдельные ветви используют аналитику корреспондирующего счёта. Это влияет на подготовку данных отчёта, а не только на оформление печатной страницы.

Там же есть условие формирования отдельных строк `... AND PR_PR=PR_O`. Следовательно, режим печати и режим хранения могут различаться; их сочетание влияет на представление остатков в отчёте. Нельзя свести оба поля к одному общему режиму.

Ссылки на PR_PR найдены также в `fmb2–6`, `fmb14`, `fmb18–20`, `fmb24` и вариантах fmb5. Полная спецификация каждой формы должна быть отдельным этапом переноса. `tnm_sver.prg:23` и `lish_sver.prg:23` отбирают счета по PR_PR=3 и PR_PR=4 соответственно: признак участвует и в специализированных сверках.

### PR_O: в какой детализации переносить остаток

`formost.prg:9–10` отбирает счета по `BETWEEN(pr_o,1,6) OR kod_arm=3`, затем вызывает OBOR_O. После расчёта оборотов:

- Строки 44–54: сохраняет NUCH/KOD_DOG только для режима 2, TNM — для 3, LISH — для 4, KOD_MAT — для 5; остальные перечисленные поля очищает.
- Строки 56–58: K_ZAKAZ сохраняется отдельно по SV_J, независимо от выбранного режима PR_O.
- Строки 59–60: для 0 и 6 код счёта преобразуется в `LEFT(schet,6)+'00'`.
- Строки 70–74: строки сворачиваются по счёту, оставшейся аналитике и K_ZAKAZ. KOD_DOG в действующем ключе TOTAL отсутствует, хотя может сохраняться в данных; переносить его как обязательную отдельную гранулярность без проверки нельзя.
- Строки 85–115: учитывается тип счёта PRSCH; для PR_O=7 очищаются DEB, CRED, DEB_V, CRED_V. Для материалов рассчитывается цена при ненулевом количестве; валютные остатки очищаются при выключенном SV_V.
- Строки 120–153: остатки на целевую дату в OST очищаются и записываются заново; сохраняются строки с ненулевыми денежными остатками. На январскую дату применяется дополнительное ограничение `VAL(SCHET)<60000000`.

Таким образом, «не хранить остатки» означает исключение денежных остатков из переноса этой процедурой, а не удаление проводок или запрет печати оборотов. При режиме 2 останется детализация организаций, при 3 — сотрудников и т. д. Свёртка может изменить развёрнутые дебетовые/кредитовые остатки при сохранении общего нетто.

Похожие ветви PR_O имеются в `av_plat.prg:121–148` и `per_ost1.prg:92–118`; в последней есть особое удаление строк с пустой организацией для PR_O=2. Эти процедуры нельзя автоматически считать полностью тождественными FORMOST.

### На каком уровне задаются признаки

`buxsch.prg:53–58` и `bwrite.prg:9–15` распространяют PR_PR и PR_O внутри группы `INT(SCHET/100)*100`, то есть по первым шести цифрам восьмизначного счёта. В методах формы для записей, не кратных 100, редактируемые значения обнуляются перед сохранением. Это требует отдельного решения о наследовании в BIS.ERP; простое редактирование каждого дочернего счёта не воспроизводит эталон.

## План доработки

### 1. Зафиксировать правила и происхождение данных

Снять read-only выборку текущего плана счетов: код, оба режима, источник импорта, наличие ручных правок. Сопоставить с исходной BUXSCH по коду и нескольким заведомо различающимся значениям PR_PR/PR_O. Проверить источник InitialDataProvider и встроенные начальные данные: они тоже могут содержать прежнее соответствие.

Результат: таблица соответствия «FoxPro → BIS.ERP», список затронутых записей и отдельно список неоднозначных ручных значений. Сейчас такую выборку не выполняли.

### 2. Исправить семантику и справочник вариантов

Целевое соответствие: PR_PR → PrintModeCode/print_mode; PR_O → BalanceModeCode/balance_mode. Разделить списки: печать 1–6, остатки 1–7 с подписью 7 «не хранить остатки». Явно описать обработку 0/пустого значения и наследование по группе счёта. Проверить оба варианта формы эталона: в fm_sch_fed список остатков отличается от основной формы.

Результат: согласованная спецификация и затем изменения импорта, начального заполнения, подсказок и выбора значений.

### 3. Подготовить миграцию существующих значений

Не выполнять безусловный обмен колонок для всей БД. Для записей с доказанным старым импортом — контролируемое исправление по источнику; для ручных и смешанных данных — отдельная сверка. Перед изменением сохранить прежние значения и журнал преобразования. Миграция должна быть повторяемой без повторной перестановки; предусмотреть откат. Не пересчитывать закрытые периоды автоматически.

### 4. Подключить режим печати

Составить матрицу действующих отчётов BIS.ERP и соответствующих fmb-форм. Для каждого описать группировку, выбор собственной/корреспондирующей аналитики, начальные и конечные остатки, сочетания PR_PR/PR_O. Ввести общий механизм чтения эффективного режима счёта, затем подключать отчёты по одному. Экран, печать и экспорт одного отчёта должны использовать одинаковую подготовку данных.

Не менять сами проводки ради группировки печати. Ручной выбор детализации отчёта должен иметь явно определённый приоритет относительно настройки плана счетов.

### 5. Подключить режим сохранения остатков

Сначала определить место аналитических остатков в текущей модели: имеющегося снимка только по AccountCode недостаточно для организаций, сотрудников, лицевых счетов и материалов. Спроектировать хранение аналитического ключа, сумм в основной валюте/валюте операции, количеств и связи с периодом. Разделить полный расчёт по проводкам и свёртку данных для переноса на следующую дату.

Воспроизвести проверенные правила FORMOST: выбор сохраняемой аналитики, группу счёта, SV_J, SV_V, тип счёта, режим 7, повторный сбор на ту же дату. Особенности договоров, года, количественных остатков без суммы и других процедур сначала проверить на контрольной копии эталона. Отдельно решить, какие исторические ограничения FoxPro сохраняются в новой системе.

Результат: проект схемы и алгоритма, затем реализация с транзакционной заменой снимков. Режим 7 не должен исключать проводки из отчёта об оборотах.

### 6. Проверить на контрольных примерах

Минимальный набор приёмки:

- Разные PR_PR и PR_O у одного счёта: печать и перенос используют каждый своё поле.
- Режимы 1–6; отдельная проверка 0 и наследования дочерних счетов.
- Режим 7: обороты видны, денежный остаток не переносится.
- Две организации или два сотрудника с противоположными остатками: сравнить развёрнутые суммы и нетто, исключить случайную свёртку.
- Собственная аналитика отсутствует, у корреспондирующего счёта имеется: проверить правила конкретного отчёта.
- Активный, пассивный, активно-пассивный счёт; SV_V и SV_J; материалы с количеством и ценой.
- Переход года и повторный сбор периода; отсутствие дублей; защита закрытого периода.
- Миграция старого импорта и ручных значений, повторный запуск миграции и откат.
- Сравнить экран, печать и экспорт с эталоном на одинаковых входных данных.

## Порядок выполнения

Сначала сверка данных и спецификация → корректировка соответствия и вариантов → проверяемая миграция → один пилотный отчёт → модель аналитических остатков и перенос → остальные отчёты и сверки. До завершения сверки не подключать существующие поля напрямую к закрытию периода: сейчас их смысл перепутан.
