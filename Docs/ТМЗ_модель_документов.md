# Модель документов ТМЗ: три документа вместо таблицы на каждый признак

**Дата:** 20.10.2026 (уточнено по окну эталонной программы)
**Основание:** окно «Приобретение ТМЗ» эталона, диалог «Ввод нового документа» (Поступление ТМЗ / Выбытие ТМЗ / Внутр.перемещение) и требование «делаем как в счёте-фактуре».
**Код:** `Services/InventoryDocumentModel.cs`, `Services/InventoryDocumentSchemaService.cs`

---

## 1. Решение

| Было | Стало |
|---|---|
| 7 документов, у каждого своя таблица | **3 документа**, вид операции — реквизит шапки |
| один материал в шапке (`material_id`, `quantity`, `price`) | **строки** `<шапка>_lines`, как `doc_sales_invoice_lines` |
| 5 таблиц различались только названием | одна таблица на документ + справочник видов операций |

```
Ввод нового документа (справочник видов)
        │
        ├── Поступление ТМЗ (doc_inventory_incoming + _lines)
        │        ├── Приобретение ТМЗ
        │        ├── Приход из производства
        │        └── Приход по акту
        ├── Выбытие ТМЗ (doc_inventory_outgoing + _lines)
        │        ├── Реализация ТМЗ
        │        ├── Расход в производство
        │        └── Списание по акту
        └── Внутреннее перемещение ТМЗ (doc_inventory_movement + _lines)
                 ├── Передача в подотчет
                 └── Автоматическая передача
```

Окно документа повторяет окно счёта-фактуры: шапка (номер, дата, ЭСФ, счёт, организация,
сотрудник, виды НДС/оплаты/покупки, валюта, итоги) и таблица строк
(материал, единица, дебет, участок, МОЛ, количество, цена, суммы).

## 5. Что происходит со старыми объектами

| Старое | Действие |
|---|---|
| `doc_incoming` («Приход товаров») | таблица → `doc_inventory_incoming`, документ → «Поступление ТМЗ» |
| `doc_outgoing` («Расход товаров») | таблица → `doc_inventory_outgoing`, документ → «Выбытие ТМЗ» |
| `doc_inventory_a37840eb4a68` («Внутреннее перемещение ТМЦ») | таблица → `doc_inventory_movement`, документ → «Внутреннее перемещение ТМЗ» |
| «Приход из производства ТМЦ» | документ и таблица удаляются, роль → вид `INCOMING_PRODUCTION` |
| «Расход в производство» | удаляется, роль → `OUTGOING_PRODUCTION` |
| «Передача ТМЦ в подотчет» | удаляется, роль → `MOVEMENT_ASSIGNMENT` |
| «Инвентаризация ТМЦ» | удаляется, роль → `INCOMING_ACT` / `OUTGOING_WRITEOFF` |
| `number`, `date` в шапках | переименованы в `doc_number`, `doc_date` |
| `invoice_number`, `vat_amount` в шапках | переименованы в `esf_number`, `vat_total` |
| `material_id`, `quantity`, `price`, `vat_rate` в шапках | удаляются, если шапка пустая; иначе остаются с предупреждением |
| `site_id`, `responsible_person_id` в шапках | убираются из метаданных (теперь колонки строк), физические колонки остаются |
| `debit_account`, `credit_account` в шапках | становятся необязательными: заполняются проведением |

Удаление таблицы выполняется только когда в ней нет строк. Если данные есть —
таблица остаётся, в лог пишется предупреждение, метаданные всё равно удаляются
(потеря данных исключена).

Сервис идемпотентен: повторный запуск не делает DDL. Все действия и предупреждения
пишутся в лог с префиксом `ТМЗ:` / источник `Migration`.

### 6.1 Инцидент 20.10.2026: `DbUpdateConcurrencyException` и падение старта

**Симптом.** Шаг `2026.10.21.01` упал с `DbUpdateConcurrencyException`
(«expected to affect 1 row(s), but actually affected 0»). Затем тот же ошибкой
упала загрузка главного окна — уже на `AccountingPeriodService.SeedFinancialReportLinesAsync`.

**Причина.** Виновник — `MetadataField`: поля нового состава были в состоянии
`Modified`, но строк в `MetadataFields` не было. Сервис работал в **общем контексте
старта**: после падения шага эти записи остались в трекере, и первый же `SaveChanges`
другого сервиса пытался их обновить.

**Исправление.**

1. Шаг и вызов из сидинга работают в **отдельном `AppDbContext`** — ошибка шага не
   оставляет мусора в контексте старта.
2. В начале `EnsureAsync` — `ChangeTracker.Clear()`.
3. Поля добавляются явно (`_context.MetadataFields.Add(field)`), а не только через
   навигацию — гарантирован `INSERT`, а не `UPDATE`.
4. Вызов из сидинга обёрнут в `try/catch` и не валит старт.

**Состояние базы после первого инцидента.** «Поступление ТМЗ» переименован, таблица
`doc_inventory_incoming` на месте, но новые поля не записаны; «Расход товаров»
и `doc_outgoing` в базе отсутствуют (следов удаления нашим шагом нет), остальные
документы-признаки на месте.

### 6.2 Повторный запуск 13:56: `42601` на имени индекса

**Симптом.** Шаг дошёл до создания таблиц строк и упал:
`42601: ошибка синтаксиса (примерное положение: "_line")`.

**Причина.** Имя второго индекса строилось приклеиванием суффикса к уже
закавыченному идентификатору: `{indexName}_line` → `"IX_..._parent"_line`.

**Исправление.** Второй индекс — отдельный кавычёванный идентификатор
`IX_<строки>_parent_line`. Проверено на живой базе в транзакции с откатом:
таблица строк (21 колонка), два индекса и FK создаются без ошибок.

Тогда же добавлено **выравнивание существующих полей по модели**
(`AlignFieldAsync`): имя, порядок, ссылка, обязательность и тип приводятся к
определению модели, иначе в шапке оставались старые подписи «Сумма», «Дебет»,
«Номер счета-фактуры» и лишнее поле `description` (теперь «Примечание» — `basis`).
Тип колонки меняется только на пустой таблице.

Дополнительно: старые ссылочные колонки (`organization_id`, `debit_account`,
`credit_account`) переведены из `text` в `uuid` — иначе запись Guid в text-колонку
дала бы ошибку типа; лишние колонки (`material_id`, `quantity`, `price`, `site_id`,
`responsible_person_id`, `description`) удаляются, если таблица пустая.

**Состояние базы после второго запуска.** Три документа созданы
(«Поступление ТМЗ», «Выбытие ТМЗ», «Внутреннее перемещение ТМЗ»), шапки на месте,
по 33 поля (будет 32 после удаления `description` и выравнивания), лишние документы
удалены. Таблиц строк ещё нет; запись `2026.10.21.01` не создана — шаг повторится
и завершит работу: выровняет поля, создаст три таблицы строк и привяжет документы
к модулю.

### 6.3 Третий запуск 14:04: `42804` при смене типа ссылочной колонки

**Симптом.** `значение по умолчанию для столбца "organization_id" нельзя
автоматически привести к типу uuid`.

**Причина.** У старых ссылочных колонок остался `DEFAULT ''::text`; при `ALTER COLUMN
... TYPE uuid` PostgreSQL пытается привести и его.

**Исправление.** Перед сменой типа снимается `DEFAULT`, затем выполняется
`TYPE uuid USING NULLIF(btrim(col::text), '')::uuid`. Проверено на временной таблице:
без `DROP DEFAULT` ошибка воспроизводится, с ним тип меняется на uuid.

## 7. Границы текущего шага

Сделано: **схема и метаданные** (таблицы, 32 поля шапки, 17 колонок строк, справочник
видов, удаление лишних документов, привязка к модулю).

Не сделано (следующие шаги):

1. **Окно документа** — по образцу `InvoiceEditDialog`: шапка, `LinesGrid`, блок итогов,
   кнопки «Добавить строку / Удалить строку / Проводки / Пересчет».
2. **Проводки по видам операций** — Дт из строки (`account_code`), Кт из шапки
   (`counterparty_account`); для каждого вида — свой шаблон.
3. **Остатки ТМЗ** — таблица остатков по складам/МОЛ, аналог `FixedAssetPeriodBalances`.
4. **Перенос данных** — в текущих базах документы ТМЗ пустые; при появлении данных
   нужен скрипт «шапка → строка» (поля уже совместимы).
