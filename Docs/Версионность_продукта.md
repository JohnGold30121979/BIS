# Версионность продукта

Документ описывает автоматическую версионность BIS ERP: как задаётся версия,
как она увеличивается при сборке, где показывается и как попадает в базу данных
при выгрузке конфигурации.

---

## Коротко

| Вопрос | Ответ |
|---|---|
| Где задаётся версия? | Файл `version.json` в корне проекта |
| Кто увеличивает версию? | MSBuild при каждой сборке, автоматически |
| Формат | Semantic Versioning: `Major.Minor.Patch`, например `1.1.15` |
| Что растёт само? | `Patch` и номер сборки |
| Нужны ли ручные правки? | Нет, кроме выпуска новой версии |
| Где видно версию? | Заголовок окна, диалог «О системе», метаданные сборки, файл `version.json` рядом с программой |
| Попадает ли в базу? | Да, при выгрузке конфигурации |

## 1. Единый источник версии

Версия хранится в одном файле — `version.json` в корне проекта:

```json
{
  "Major": 1,
  "Minor": 1,
  "Patch": 15,
  "Build": 15,
  "Semantic": "1.1.15",
  "Informational": "1.1.15+2026-10-09T08:04:27Z#15",
  "LastBuildUtc": "2026-10-09T08:04:27Z"
}
```

| Поле | Назначение | Кто меняет |
|---|---|---|
| `Major` | Несовместимые изменения, требующие миграции данных | Вручную |
| `Minor` | Новая функциональность без ломки совместимости | Вручную |
| `Patch` | Исправления | **Автоматически при сборке** |
| `Build` | Номер сборки, сквозной счётчик | **Автоматически при сборке** |
| `Semantic` | Готовая версия вида `1.1.15` | Автоматически |
| `Informational` | Полная строка версии с датой и номером сборки | Автоматически |
| `LastBuildUtc` | Время последней сборки в UTC | Автоматически |

> **Важно.** Поля `Major` и `Minor` — единственное, что правится руками.
> Остальные перезаписываются при каждой сборке.

## 2. Правила версионирования

Применяется стандарт Semantic Versioning: `Major.Minor.Patch`.

| Что изменилось | Что делать | Было → стало |
|---|---|---|
| Исправление ошибки | Ничего, версия вырастет сама | `1.1.15` → `1.1.16` |
| Новая функция | Поднять `Minor`, `Patch` обнулить | `1.1.15` → `1.2.1` |
| Несовместимое изменение | Поднять `Major`, остальные обнулить | `1.1.15` → `2.0.1` |

**Пример: выпуск версии 1.2.** Открыть `version.json` и заменить:

```json
"Minor": 1,
"Patch": 15,
```
на
```json
"Minor": 2,
"Patch": 0,
```

При следующей сборке версия станет `1.2.1`, а дальше будет расти сама:
`1.2.2`, `1.2.3` и так далее.

## 3. Как работает автоинкремент

Механизм описан в файле `Directory.Build.props` в корне проекта.
При каждой сборке выполняются три фазы.

### Фаза 1. Инкремент версии

Скрипт PowerShell (создаётся в `obj/bump-version.ps1`) читает `version.json`,
увеличивает `Patch` и `Build`, записывает файл обратно и печатает версию для MSBuild.

```powershell
$patch = $patch + 1
$build = $build + 1
$semantic = '{0}.{1}.{2}' -f $major, $minor, $patch
$stamp = (Get-Date).ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ssZ')
```

### Фаза 2. Запись метаданных сборки

Версия записывается в отдельный файл метаданных стандартной задачей MSBuild
`WriteCodeFragment` — она сама формирует корректный код, поэтому экранирование
строк не требуется:

```csharp
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductVersion", "1.1.15")]
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductBuild", "15")]
[assembly: System.Reflection.AssemblyMetadataAttribute("ProductInformational", "1.1.15+2026-10-09T08:04:27Z#15")]
```

Используются **метаданные**, а не атрибуты версии: так значения не конфликтуют
с автоматически созданными атрибутами сборки и не требуют подавления
предупреждений компилятора.

### Фаза 3. Копирование файла версии

`version.json` копируется в каталог вывода рядом с программой — чтобы версию
можно было увидеть даже при подменённых файлах.

### Порядок важен

```
WriteVersionBumpScript      создаёт скрипт
        ↓
BumpProductVersionFiles     выполняет скрипт, получает версию
        ↓
ApplyProductVersion         пишет метаданные сборки
        ↓
GenerateAssemblyInfo        SDK создаёт AssemblyInfo
        ↓
CoreCompile                 компиляция
        ↓
CopyVersionFileToOutput     копирует version.json
```

> **Грабли, которые уже пройдены.** Сначала файл метаданных создавался целью,
> которая зависела от цели вычисления версии. Свойства задавались внутри цели,
> и на момент генерации файла они ещё были пустыми — в сборку уходили пустые
> строки. Сейчас вычисление версии вынесено в отдельную цель-зависимость.

## 4. Доступ к версии из программы

Класс `Services/AppVersion.cs` — единая точка получения версии.

| Свойство | Значение | Пример |
|---|---|---|
| `Semantic` | Версия без номера сборки | `1.1.15` |
| `Build` | Номер сборки | `15` |
| `Full` | Полная версия | `1.1.15.15` |
| `BuildUtc` | Время сборки в UTC | `2026-10-09T08:04:27Z` |
| `BuildLocalText` | Время сборки по местному времени | `09.10.2026 14:04` |
| `Display` | Подробная подпись для диалога «О системе» | `1.1.15 (сборка 15 от 09.10.2026 14:04)` |
| `DisplayShort` | Короткая подпись для шапки окна | `1.1.15 (сборка 15)` |
| `ProductText` | Строка для протокола | `BIS ERP 1.1.15.15` |

Значения читаются из метаданных сборки один раз при первом обращении:

```csharp
var value = Assembly.GetExecutingAssembly()
    .GetCustomAttributes<AssemblyMetadataAttribute>()
    .FirstOrDefault(attribute => attribute.Key == "ProductVersion")
    ?.Value;
```

### Где уже используется

| Место | Что показывает |
|---|---|
| `MainWorkWindow` | Заголовок окна и подпись под названием системы в шапке |
| `ConfiguratorWindow` | Подпись под названием системы в шапке конфигуратора |
| `AboutSystemDialog` | Строка «Версия программы» с номером сборки и датой |
| `AppUpdatePackageService` | `CurrentAppVersion` — версия для проверки обновлений |
| `BisPatchService` | Версия программы в пакете обновления базы |

Раньше эти места читали версию по-разному: одно — из `AssemblyInformationalVersion`,
другое — из `AssemblyName.Version`. Теперь источник один.

### Что показывается в интерфейсе

В шапках окон версия показывается **сокращённо** — версия и номер сборки.
Подробная версия с датой сборки выводится только в диалоге «О системе»:
в шапке длинная подпись перекрывала название системы.

**Рабочее окно.** Под названием системы в левой шапке:

```
BIS ERP
версия 1.1.22 (сборка 22)
ОСОО1 · Администратор (admin)
```

Заголовок окна: `BIS ERP - Рабочий режим — версия 1.1.22 (сборка 22)`.

**Конфигуратор.** Под названием системы и строкой «Режим конфигуратора»:

```
BIS ERP
Режим конфигуратора
версия 1.1.22 (сборка 22)
Инфобаза: ...
Патч: ...
```

> **Не путайте два разных значения.** «Патч» — это версия применённого
> обновления базы данных (`BisPatchService`). «Версия» — версия программы.
> Это независимые величины.

**Диалог «О системе».** Обе версии в одной строке, выравнивание слева:

```
Версия программы: 1.1.22 (сборка 22 от 09.10.2026 14:04)   •   Версия конфигурации: 1.1.22
```

Версия конфигурации читается из таблицы `MetadataConfigurations` — это версия
программы, которой сделана последняя выгрузка или загрузка конфигурации.
Если выгрузок ещё не было, выводится «не задана».

## 5. Версия в базе данных

Версия записывается в базу при **выгрузке конфигурации**. Это позволяет
по файлу выгрузки понять, какой сборкой он сделан.

### Что добавляется в файл выгрузки

Модель `ConfigurationPackage` дополнена тремя полями:

| Поле | Содержимое |
|---|---|
| `ApplicationVersion` | `1.1.15` |
| `ApplicationBuild` | `15` |
| `ApplicationBuildUtc` | `2026-10-09T08:04:27Z` |

В файле выгрузки это выглядит так:

```json
{
  "Format": "BIS.Configuration",
  "Version": 2,
  "ExportedAt": "2026-10-09T08:10:00Z",
  "Application": "BIS ERP",
  "ApplicationVersion": "1.1.15",
  "ApplicationBuild": 15,
  "ApplicationBuildUtc": "2026-10-09T08:04:27Z"
}
```

### Что записывается в таблицу

Таблица `MetadataConfigurations`, поле `Version`. Раньше там было жёстко
зашито `"1.0"`. Теперь при каждой выгрузке и загрузке записывается текущая
версия программы.

```csharp
config.Version = AppVersion.Semantic;
await _context.SaveChangesAsync();
```

### Проверка

```sql
SELECT "Id", "Version", "UpdatedAt"
FROM "MetadataConfigurations"
ORDER BY "UpdatedAt" DESC
LIMIT 5;
```

Поле `Version` должно совпадать с версией программы, которой сделана
последняя выгрузка или загрузка.

## 6. Проверка работы

### Проверить, что версия растёт

```powershell
dotnet build "D:\C#\BIS.ERP\BIS.ERP\BIS.ERP.csproj" -c Debug -v:m --nologo
```

В выводе должна появиться строка:

```
Версия продукта: 1.1.16 (сборка 16)
```

Повторная сборка должна дать `1.1.17` — ровно на единицу больше.

### Проверить метаданные в сборке

```powershell
$dll = "bin\Debug\net8.0-windows\BIS.ERP.dll"
[System.Diagnostics.FileVersionInfo]::GetVersionInfo($dll).ProductVersion
```

### Проверить файл рядом с программой

```powershell
Get-Content "bin\Debug\net8.0-windows\version.json"
```

Содержимое должно совпадать с `version.json` в корне проекта.

## 8. Что важно знать

1. **`version.json` нужно включить в систему контроля версий.** Это источник
   версии, а не временный файл. Он не попадает под `obj/` и `bin/`.

2. **Сборка с ошибкой тоже увеличивает версию.** Инкремент выполняется до
   компиляции. Это осознанный выбор: номер сборки остаётся сквозным счётчиком
   попыток сборки.

3. **Приложение держит сборку в памяти.** Если программа запущена, сборка
   обновит файлы на диске, но работающий процесс продолжит использовать старую
   версию. Версию в заголовке окна можно использовать как признак: она
   показывает, что именно загружено.

4. **`Patch` растёт при каждой сборке, включая отладочные.** Поэтому номера
   могут идти с большими пропусками между выпусками. Это нормально: `Minor` и
   `Major` — то, что несёт смысл для пользователя.

5. **Автоматически создаваемые файлы** лежат в `obj/` и не попадают в
   репозиторий: `bump-version.ps1`, `ProductVersionInfo.cs`.
