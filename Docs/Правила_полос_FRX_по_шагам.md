# Правила вывода FRX-отчётов по полосам

Документ описывает, как макет FRX превращается в печатную форму: какие правила
применяются к полосам, какие из них общие для всех отчётов, а какие относятся
только к акту сверки.

Составлен по фактическому анализу всех 37 FRX-макетов, извлечённых из
`Services/StandardFrxReportTemplates.generated.cs`, и по коду
`Services/PrintFormService.cs`.

---

## Краткий ответ

| Вопрос | Ответ |
|---|---|
| Работают ли другие отчёты по тем же правилам? | Частично: одно правило общее для всех 37 макетов, правила порядка вывода — только для 19 вариантов акта сверки |
| Нужна ли пересборка при загрузке новой FRX-формы? | Для импорта — нет; но способ упаковки выбирается по типу отчёта, и для новой формы его может не хватить |
| Есть ли полосы, которые не выводятся? | Да, и это нормально: три типа полос не содержат элементов ни в одном макете |

## 1. В макете два независимых списка полос

Это первое, что нужно понять: макет хранит полосы дважды, и списки не совпадают.

| Список | Что содержит | Кто использует |
|---|---|---|
| `Bands[]` | Объявление полос: тип, высота, порядок, исходные поля FoxPro | Служба печати строит по нему порядок вывода |
| `Template.Elements[].BandType` | К какой полосе относится каждый элемент | Связывает элемент с полосой при рендере |

### Объявленных полос по всем 37 макетам

| Тип полосы | Объявлено полос |
|---|---|
| без типа (`None`) | 74 |
| `GroupHeader` | 42 |
| `GroupFooter` | 42 |
| `PageHeader` | 24 |
| `Detail` | 24 |
| `PageFooter` | 24 |
| `Title` | 23 |
| `Summary` | 23 |

### Типы полос у элементов

| `BandType` элемента | Элементов |
|---|---|
| `Detail` | 1594 |
| `Title` | 268 |
| `Summary` | 105 |
| `PageHeader` | 28 |

> **Ключевой факт.** У элементов встречаются только четыре типа полос, тогда как
> объявлено восемь. Полосы `GroupHeader`, `GroupFooter` и `PageFooter`
> **не содержат элементов вообще** — ни в одном из 37 макетов.

Отсюда главное следствие: в акте сверки три `GroupHeader` и три `GroupFooter`
**не создают блоков**. Всё их содержимое — заголовок пары счетов, итоги, подписи —
лежит в полосе `Detail`.

## 2. Правила по каждому типу полосы

| Тип полосы | Выводится | Что содержит |
|---|---|---|
| `Title` | один раз в начале | Заголовок отчёта, реквизиты сторон, период, номер листа |
| `PageHeader` | один раз, после `Title` | Шапка таблицы колонок |
| `GroupHeader` | **не выводится** (нет элементов) | В акте — заголовки групп, но лежат в `Detail` |
| `Detail` | по правилу отчёта | Строка данных; в акте — целый блок с обрамлением |
| `GroupFooter` | **не выводится** (нет элементов) | Итоги и подписи, но лежат в `Detail` |
| `PageFooter` | **не выводится** (нет элементов) | Колонтитул |
| `Summary` | один раз в конце | Итоговое описание, задолженность прописью |
| без типа (`None`) | одной полосой целиком | 8 макетов ОС, кассовые ордера, счёт-фактура |

### Почему полосы без элементов не выводятся

```csharp
foreach (var band in bands)
{
    if (!elementsByBand.TryGetValue(band, out var bandElements) || bandElements.Count == 0)
        continue;   // полоса без элементов не выводится
    ...
}
```

## 3. Отпечаток по шагам: как выводится макет

### Шаг 1. Разбор макета

- Из поля `Reports.Template` читается JSON с полосами и элементами.
- Если JSON нет — макет разбирается из FoxPro-формата FRX.
- Результат: список полос и список элементов с координатами.

### Шаг 2. Подготовка профилем распознавания

- Профиль определяется по имени файла и обязательным выражениям.
- Для акта сверки — `foxpro_reconciliation_act`.
- Выполняется выравнивание полей по шаблонам профиля.
- При необходимости нормализуются верхние позиции полос.

### Шаг 3. Определение полосы для каждого элемента

**Правило общее для всех 37 макетов.** Порядок поиска:

1. Берётся объявленный `BandType` элемента.
2. Ищется полоса такого типа; если полос несколько — первая по вертикали.
3. Если тип не задан или полосы нет — поиск по координате *(запасной путь)*.
4. Если и координата не дала результата — последняя полоса выше элемента.

```csharp
private static PrintFormBand? FindBandForElementForOutput(
    PrintFormElement element,
    IReadOnlyList<PrintFormBand> bands)
{
    var declared = FindBandByType(element.BandType, bands);
    if (declared != null)
        return declared;

    return FindBandForElement(element, bands);
}
```

> **Что было раньше.** Координата стояла первой. В макетах FRX верхние позиции
> полос совпадают — в акте сверки они вообще все нулевые, потому что раскладка
> задаётся полем `Order`. Координатный подбор в такой ситуации бессмыслен,
> и элементы уезжали в чужие полосы. Именно поэтому поля данных оказывались
> в полосе `Summary`, а не `Detail`.

### Шаг 4. Карта «полоса → элементы»

- Каждый элемент относится ровно к одной полосе.
- Полосы без элементов исключаются из вывода.
- Внутри полосы сортировка: по вертикали, затем по горизонтали, затем по порядку.

### Шаг 5. Выбор способа упаковки

| Условие | Способ | Кто попадает |
|---|---|---|
| Отчёт — акт сверки | `BuildPackedReconciliationFrxTemplate` | 19 вариантов акта сверки |
| Табличный отчёт известного вида | `BuildPackedTabularFrxTemplate` | Кассовая книга, реестр приходов и расходов |
| Все остальные FRX-отчёты | `BuildPackedStaticFrxTemplate` | Оборотные ведомости, ОС, счёт-фактура, платёжка |

Условие для акта — не структура макета, а **тип и имя отчёта**:

```csharp
return IsFoxProTemplate(template, report) && IsReconciliationActReport(dataTable, report);
```

где `IsReconciliationActReport` проверяет `ReportType == "ReconciliationAct"`
либо наличие «акт свер» в имени или заголовке.

### Шаг 6. Вывод полос

| Способ | Правило вывода |
|---|---|
| Акт сверки | Шапка и шапка таблицы — один раз; обрамление начала блока — один раз; строка операций — на каждую проводку; итоги и подписи — в конце |
| Табличный | Полоса данных повторяется на каждую строку; остальные полосы — по одной |
| Обычный | Каждая полоса выводится один раз, в порядке объявления |

### Шаг 7. Разбиение на страницы

- Высота листа вычисляется из пропорций самого макета, а не берётся как 2970 единиц A4.
- Если содержимое помещается на лист — вывод идёт непрерывным полотном.
- Если элементов после упаковки больше 700 — отчёт принудительно делится на страницы,
  иначе `FitArea` сжимает содержимое в нечитаемое.

```csharp
const int maxElementsPerPage = 700;
if (template.Elements.Count > maxElementsPerPage)
{
    var requiredPages = (int)Math.Ceiling(template.Elements.Count / (double)maxElementsPerPage);
    pageSize = Math.Max(1d, contentHeight / requiredPages);
}
```

## 4. Полоса данных акта сверки: раскладка

Полоса `Detail` акта сверки содержит **не строку таблицы, а целый блок**.
Разбор по вертикальным позициям (макет `pr-vzp`):

| Позиция (`Top`) | Содержимое | Сколько раз выводить |
|---|---|---|
| 23125 — 35312 | САЛЬДО НА начало, «Пара счетов :», коды и название | 1 раз |
| **41562** | `ved.tex`, `ved.debet`, `ved.kredit`, `ved.debsum`, `ved.credsum`, `ved.dok`, `ved.date`, `ved.prs` | **N — по числу проводок** |
| 45729 — 47812 | ИТОГО ОБОРОТОВ, САЛЬДО НА конец по паре | 1 раз |
| 51979 — 54062 | ИТОГО ОБОРОТОВ ПО организации, САЛЬДО по организации | 1 раз |
| 58125 — 60208 | ИТОГО ОБОРОТОВ, САЛЬДО НА конец по организации | 1 раз |
| 67396 — 82188 | NA1, P1, P2, P3, P4 — задолженность прописью и подписи | 1 раз |

Признак строки операций определяется по имени выражения со снятым префиксом:

```csharp
private static bool IsReconciliationRowElement(PrintFormElement element)
{
    var name = Regex.Replace(expression, @"^(?:ved\d*|db_crs?|dbcrs?)[._]", "");
    return name.ToLowerInvariant() switch
    {
        "tex" or "text" or "name_kod" => true,
        "deb" or "debet" or "debit" or "schet" => true,
        "kredit" or "cred" or "korsch" or "kor_sch" => true,
        "debsum" or "sum_deb" or "deb_v" => true,
        "credsum" or "sum_cred" or "cred_v" => true,
        "dok" or "dokum" or "nom_dok" => true,
        "date" or "datobr" => true,
        "prs" or "kod_arm" or "module" => true,
        _ => false
    };
}
```

Всё, что **выше** этих полей, — обрамление начала блока; всё, что **ниже** — обрамление конца.

## 6. Привязка данных: два механизма подстановки

Ключевой момент, без понимания которого правки приводят к пустым полям.

| Механизм | Что заполняет | Откуда берёт значение |
|---|---|---|
| `AddReconciliationAliases` | Строки операций: `ved.date`, `ved.debsum`, `ved.deb_beg` | Из колонок строки данных |
| `AddReconciliationSummaryAliases` | Подытоги: `ved_sch.*`, `ved_obj.*`, `ved_org.*` | Находит строки «САЛЬДО НА» и «ИТОГО ОБОРОТОВ» и читает русские колонки «Сумма Дт» / «Сумма Кт» |

> **Практическое следствие.** Значение сальдо нужно класть **и в русскую колонку**
> (её читает механизм подытогов), **и в каноническую** (её читает механизм строк).
> Если положить только в одну — часть макета останется пустой.

### Три слоя сопоставления имён

1. Каждая колонка строки публикуется под своим именем и под нормализованным.
2. Канонические синонимы: `debsum`, `sum_deb`, `deb_v`, `deb_beg` — всё это группа `debit_amount`.
3. Префиксы наборов данных: `ved.`, `ved_`, `db_cr.`, `db_crs_`, `ksprorg.`, `avt_p.`,
   а также построчные `line1_`, `ved1_`, `db_cr1_`. Одно значение публикуется под всеми префиксами.

### Сопоставление русских колонок акта сверки

| Русская колонка | Каноническое имя | Имя в макете |
|---|---|---|
| «Наименование материала, вид операции» | `operation_name` | `ved.tex` |
| «Дебет» | `debit_account` | `ved.debet` |
| «Кредит» | `credit_account` | `ved.kredit` |
| «Сумма Дт» | `debit_amount` | `ved.debsum`, `ved.deb_beg` |
| «Сумма Кт» | `credit_amount` | `ved.credsum`, `ved.cred_beg` |
| «N докум» | `document_number` | `ved.dok` |
| «Дата» | `document_date` | `ved.date` |
| «Модуль» | `module` | `ved.prs` |

## 7. Скрытие служебных колонок от экранной таблицы

Механизм подстановки ищет значения в канонических колонках, но экранная таблица
строится по колонкам `DataTable` (`AutoGenerateColumns="True"`). Поэтому служебные
колонки добавляются в таблицу и **отменяются при генерации колонок сетки**:

```csharp
private static readonly HashSet<string> ServiceColumnNames = new(StringComparer.OrdinalIgnoreCase)
{
    "operation_name", "debit_account", "credit_account",
    "debit_amount", "credit_amount", "debit_begin", "credit_begin",
    "document_number", "document_date", "module",
    "report_title", "report_summary", "period_start", "period_end"
};
```

```csharp
private static void OnReportGridAutoGeneratingColumn(object sender, DataGridAutoGeneratingColumnEventArgs e)
{
    if (e.PropertyName != null && ServiceColumnNames.Contains(e.PropertyName))
        e.Cancel = true;
}
```

## 9. Ограничения текущей реализации

1. **Группировка по нескольким уровням не реализована.** Полосы `GroupHeader`
   и `GroupFooter` повторяются не по числу групп, а один раз.
2. **Составные выражения макета не вычисляются.** Работает только ссылка на одно поле.
   Например `sha + ' ' + SHA3` вернёт текст выражения.
3. **Откат на координату ненадёжен** в макетах с совпадающими верхними позициями полос.
4. **Способ упаковки привязан к типу отчёта**, а не к структуре макета. Поэтому
   при загрузке новой FRX-формы с иной структурой пересборка может понадобиться.

### Как закрыть ограничение 4

Признак способа вывода стоит перенести из кода в саму форму:

1. Добавить в `Report` поле режима: `Auto` / `Static` / `Tabular` / `RowGroup`.
2. Определять режим автоматически по структуре: если поля-строки собраны
   в одной горизонтали, а выше и ниже есть обрамление — это `RowGroup`.
3. Дать возможность переключить режим в конфигураторе, без программиста.

Оценка: около 2 рабочих дней. После этого новые FRX-формы будут подхватываться
корректно без пересборки проекта.

| В колонку даты попадало сегодняшнее число | Служебная функция FoxPro `date()` перехватывала имя поля `date` | Дата строки имеет приоритет над системной |

## 11. Опознание полей строки: префикс необязателен

Это правило оказалось ключевым: **одни макеты обращаются к полям через префикс
набора данных, другие — напрямую.**

| Макет | Выражения строки |
|---|---|
| «Акт сверки (FRX FoxPro)» | `ved.tex`, `ved.debet`, `ved.kredit`, `ved.debsum` |
| «Акт сверки вариант 1 (FRX FoxPro)» | `tex`, `debet`, `kredit`, `debsum` |

Если требовать префикс обязательно, второй макет не опознаёт ни одного поля строки:
всё уходит в обрамление, и вместо 73 строк печатается одна.

Правило опознания:

```csharp
private static bool IsReconciliationRowElement(PrintFormElement element)
{
    var expression = (element.Expression ?? string.Empty).Trim();
    if (expression.Length == 0)
        return false;

    // Составные выражения (korsch+' - '+kor_sch) не являются полем строки.
    if (expression.Contains('+') || expression.Contains('('))
        return false;

    // Префикс снимается, если он есть, но не является обязательным.
    var name = Regex.Replace(expression, @"^(?:ved\d*|db_crs?|dbcrs?)[._]", string.Empty);
    return name.ToLowerInvariant() switch
    {
        "tex" or "text" or "name_kod" => true,
        "deb" or "debet" or "debit" or "schet" => true,
        "kredit" or "cred" or "korsch" or "kor_sch" => true,
        "debsum" or "sum_deb" or "deb_v" => true,
        "credsum" or "sum_cred" or "cred_v" => true,
        "dok" or "dokum" or "nom_dok" => true,
        "date" or "datobr" => true,

    };
```

## 12. Дата: столкновение с функцией FoxPro

В FoxPro `date()` — служебная функция, возвращающая системную дату.
В словаре переменных она хранится под ключом `date()`, а словарь
не учитывает регистр. Поиск значения снимает скобки, поэтому имя
поля `date` попадало на служебную функцию:

```
ExtraFields['date'] = '30.09.2026'   ← правильная дата проводки
Разрешённое 'date'  = '09.10.2026'   ← сегодняшняя дата (перехват)
```

**Второй источник перехвата** — цикл публикации доп. полей:

```csharp
var normalizedKey = NormalizeFieldName(extra.Key);   // "date" → "date"
variables[normalizedKey] = FormatPlainValue(extra.Value);   // затирает значение
```

Правило: **дата строки важнее системной**. Переменная `date` определяется
по колонкам строки («Дата», `document_date`, `datobr`) и не перезаписывается
доп. полями. Для строк без своей даты — заголовков, сальдо, итогов —
сохраняется системная дата, как было раньше.

## 13. Открытые вопросы

| Вопрос | Состояние |
|---|---|
| **Колонки «Дата» и «АРМ» пусты в макете «Вариант 1»** | Поля опознаются как строки (8 из 52), значение резолвится, но в упакованный макет не попадает. Разрыв между резолвингом и записью — причина не локализована |
| «Сумма Дт» пуста в строках | Счёт дебета проводки не входит в пару счетов — это выборка данных, не подстановка |
| Строки «не своей» пары в акте | Движения грузятся по организации и датам, **без фильтра по счетам пары** |
| Наезды текста, ширины колонок | Работа с координатами макета, не выполнена |
| Привязки элементов (`ElementMappings`) | Заполнены только у 1 из 18 макетов акта. Создаются лишь при сохранении из конструктора; импорт FRX их не делает. **На вывод не влияет** — подстановка работает по выражениям макета |
