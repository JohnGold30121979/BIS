# Связь двух BIIS через интернет

## Точная постановка задачи

Разработать встроенный в поставку BIIS кроссплатформенный фоновый узел обмена. Он должен обеспечивать двустороннее выполнение разрешённых API-операций между экземплярами A и B через интернет. Каждый экземпляр читает и изменяет свою базу через собственный прикладной слой. Связь должна восстанавливаться после обрыва, а повторная доставка команды записи должна возвращать прежний результат без повторного изменения данных. Решение использует штатные средства .NET и собственные компоненты BIIS, работает на Linux и поддерживает развёртывание без внешнего сервиса обмена.

## 1. Выбрать публичную точку

- **A может принимать входящие подключения.** Разместить точку внутри узла A. Назначить A публичный DNS-адрес и открыть TCP 443, при необходимости настроить проброс на маршрутизаторе. B устанавливает исходящее соединение с A. Запросы ходят в обе стороны по одному соединению.
- **Обе площадки за CGNAT или входящие запрещены.** Развернуть собственный компонент BIIS Relay на контролируемом сервере с публичным адресом и TCP 443. A и B устанавливают по одному исходящему соединению с Relay. Если публичный сервер недоступен и входящие подключения на обеих площадках закрыты, для этой схемы потребуется изменить сетевые условия.

Для первого релиза выбрать одну схему по результатам проверки сети. Далее описан вариант с Relay.

    BIIS A ⇄ WSS ⇄ BIIS Relay ⇄ WSS ⇄ BIIS B

## 2. Выделить фоновый узел BIIS

Создать отдельный хост .NET в составе решения, например BIS.ERP.PeerHost. Запускать его постоянно под systemd на каждой Linux-площадке. Он держит соединение независимо от открытия пользовательского интерфейса. Вынести нужные операции в совместимые с Linux прикладные модули. Текущий WPF-клиент может обращаться к узлу через локальный API. Проверить совместимость выбранного драйвера БД с Linux.

## 3. Поднять публичный Relay

Поднять ASP.NET Core с маршрутом /peer по WSS. Настроить TLS и отдельный клиентский сертификат для каждого узла. Проверять доверие, срок действия и сопоставление сертификата с ID узла. В конфигурации задать разрешённую пару A↔B. Relay хранит активные соединения и маршрутизирует пакеты только внутри пары. Идентификатор отправителя брать из аутентифицированной сессии. При отсутствии получателя вернуть статус недоступности.

## 4. Определить протокол и первое API

Согласовать версию протокола и поля сообщения: тип, ID запроса, получатель, операция, срок действия и тело. Для ответа предусмотреть ID исходного запроса, статус и результат. Для записи предусмотреть стабильный ID команды, сохраняемый при повторе. Ограничить размер сообщений, время выполнения и число параллельных запросов. Начать с тестового чтения и одной реальной операции записи после выбора бизнес-сущности.

## 5. Реализовать путь запроса

1. A принимает запрос через свой API и проверяет права локального пользователя.
2. Фоновый узел A отправляет команду через Relay.
3. B проверяет право узла A на операцию, валидирует данные и вызывает прикладной обработчик.
4. Обработчик B выполняет чтение или запись в базе B и возвращает результат.
5. Ответ идёт через Relay к A. A сопоставляет его с запросом. Для вызова из B последовательность зеркальная.

Права задавать на уровне бизнес-операций. Порт базы оставить доступным только локальной инфраструктуре. Для операций записи хранить ID команды и её результат в одной транзакции с изменением данных. Защитить ID уникальным ограничением по отправителю и ID команды. При повторе с тем же ID и изменённым телом возвращать конфликт.

## 6. Восстановить связь после сбоев

Добавить проверку живости соединения, переподключение с растущей задержкой и случайным разбросом, а также тайм-ауты запросов. Тайм-аут записи означает неопределённый результат. Повторять такую команду с тем же ID. Если бизнес требует гарантированной доставки после перезапуска отправителя, сохранять команду в локальном outbox до подтверждения. Логировать ID запроса, узел, операцию, время и статус без содержимого документов и секретов.

## 7. Принять работу на двух площадках

- A и B находятся в разных интернет-сетях. Проверены чтение и запись в обоих направлениях.
- Узлы запускаются автоматически на Linux и работают при закрытом UI.
- Чужой сертификат, запрещённая операция и попытка обратиться к чужому узлу отклоняются.
- После разрыва интернета и перезапуска Relay соединения восстанавливаются автоматически.
- После потери ответа на успешно выполненную запись повтор команды меняет данные ровно один раз.
- При отключённом B узел A получает статус недоступности или тайм-аут за установленное время.
